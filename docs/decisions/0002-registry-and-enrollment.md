# Registry, enrollment, and calibration authority

Status: accepted for implementation; appliance bootstrap implementation and qualification pending.
Date: 2026-09-05. Owner: implementation orchestrator. D03/D04/D10/D12.

**Repositioned by [decision 0008](0008-generic-image-and-serial-identity.md) (2026-09-10).** The baseline is now **serial-based identity** on a trusted LAN with a **generic flashed image** discovered by mDNS. The per-device persistent Ed25519 key described below — nonce challenge, proof-of-possession, hashed token rotation, and retirement — is **not** the baseline; it is the opt-in **certificate tier (I1)** a deployment adopts to gain cryptographic, revocable identity. This machinery is retained wholesale as I1; only its status as the default, and the "identity derives from the public key, never IP/MAC" claim, are changed. The calibration, binding, and geometry sections below are unaffected.

The initial provisioning envelope is a dedicated, operator-controlled wired PXE network. DHCP/TFTP boot is not authenticated against a malicious network operator. We explicitly trust that centrally prepared boot boundary, rather than claim hardware attestation or secure boot. Devices must already have network-capable EEPROM settings; no Photo Wall per-device setup is permitted. Appliance design must load the common root filesystem into RAM and use available persistent storage only for generated identity/cache, so losing the PXE host after boot does not block running binaries. Exact image layout and update A/B mechanics remain a separate design task.

The common image carries only public deployment settings (central HTTPS hostname and CA) and public verification keys. It carries no device or permanent shared enrollment secret. On first boot a Player generates an Ed25519 key and stores it privately on its state volume. Registration uses a short-lived server nonce and proof of possession of that key. The server atomically consumes the nonce, creates/refreshes an **unbound** registry entry, and issues a random Player-specific bearer token over TLS. Tokens are stored hashed centrally. Key proof can rotate a lost/expired token; a retired key cannot enroll again. A reimage that loses its key becomes a new unbound Player. Operational identity derives from the random public key, never IP/MAC/HDMI observations.

Anyone on the allowed enrollment network may initially register, but unbound registration authorizes no Frames and no media. Separately authenticated operators inspect reported equipment and bind Frames centrally. Registration/refresh never changes bindings, desired calibration, or Frame identity. The operator can retire a Player; binding transfer increments the persistent Frame generation. Every plan acceptance, readiness/commit operation, and media request checks active Player authority and current generation. Offline old equipment can hold its previously authorized picture until expiry; immediate revocation cannot cross a network partition. New stale work is rejected, and reconnect replaces its authority. This limitation is explicit rather than claiming instant remote revocation.

Registry geometry uses millimeters on each Surface, with origin at upper left, +x right, +y down viewed from the room. Frame aperture/position and orientation persist independently of replaceable Panel and Output observations. An Output can bind one Frame; a Frame can have one current binding. Initial Output profiles declare pixel dimensions, diagonal inches, and video capability. Replacement preserves Frame geometry and increments generation; equipment calibration requires central revalidation before renewed execution authority.

Calibration is an output-pixel correction associated with the persistent Frame: normalized crop, rotation, four ordered projective corners, and SDR gain. Committed revision is durable. Preview carries a 30-second lease and separate proposed values; expiry/revert returns to committed settings. Binding transfers require the expected Frame generation; an already-current binding is an idempotent no-op. A delayed old transfer cannot undo a newer binding. Concurrent uncommitted previews at the same generation/base calibration use last-writer-wins; committed revisions use optimistic conflict checks. Every calibration operation requires the expected binding generation; a delayed request from replaced equipment is rejected. A separate monotonic configuration revision advances for preview, expiry, revert, commit, and binding changes, so revert never needs to accept an older desired-state revision. Commit requires the expected base revision, increments it transactionally, clears preview, and validates the active binding. Replacement clears preview and marks calibration unvalidated until commit. Operator changes never derive from Player equipment observations.

PostgreSQL migrations are applied serially under an advisory transaction lock. Registry binding/retirement/calibration operations are transactional. Central Runtime snapshots and locked plan records will use their own transaction boundary; the registry does not own logical Scene state. SQL constraints enforce duplicate Output and Frame bindings. All secrets stay in deployment files/volumes outside Git; API errors return bounded codes rather than raw SQL/request bodies.

Evidence required: replayed/expired nonce, invalid signature, retired re-enrollment, token rotation, unbound media denial, concurrent binding claims, stale generation, preview expiry/conflict/revert, replacement preserving Frames, and actual fresh PXE appearance. This record does not establish those tests passed.
