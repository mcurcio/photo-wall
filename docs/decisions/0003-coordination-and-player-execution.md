# Coordination and Player execution contract

Status: accepted for the next implementation slice; not yet implemented/qualified.
Date: 2026-09-05. Owner: implementation orchestrator. D02/D03/D07/D08/D09.

This extends [time/recovery policy](0001-mvp-time-recovery-and-module-contracts.md) and [registry authority](0002-registry-and-enrollment.md). The [Planner](../module-planner.md) selects media; the coordinator owns offers, content locks, commitment and lifecycle feedback; the Player performs only authorized timed work. `contracts/models.py` is the sole wire owner. Central media repository design follows [the media contract](../module-media.md), subject to its declared qualification gates.

## Scope and ownership

Root owns PostgreSQL schema/repositories, central coordinator, session HTTP/WebSocket adapter, media gateway, and integration. A Player execution leaf owns `player/executor.py`, `player/rendering.py` (platform-independent Renderer protocol and recording substitute), focused tests, and its module design. A later native renderer leaf implements that protocol with embedded GStreamer/GTK and persistent surfaces. A later networking leaf performs automatic key enrollment, TLS WebSocket/HTTP, downloading and thread/event-loop adaptation in the same Python Player process. Source/Scene/Program config and live catalog remain central only.

## Plans, locks and revocable readiness

A Player authority epoch changes on proof-backed token rotation; every cold process start establishes a fresh epoch before accepting playback. Within an epoch a stable plan ID has strictly increasing revisions. New configuration checks Player identity, binding generation and configuration revision. New plans may revise arbitration ordering and other still-valid execution metadata without changing content already locked for the same assignment. A locked assignment's exact Variant and media/cycle identity survive ordinary query updates; a cancelled/stale-binding assignment loses execution authority and retains file pins until explicitly released or its recorded lease expires.

The coordinator persists the exact offered Plan and pins all offered central blobs before sending it. A Player atomically secures bytes and pins them before `secured` feedback. Central consumes feedback in increasing `Readiness.sequence` order for the authority epoch; stale, duplicate, mismatched-plan or mismatched-binding messages cannot authorize work. Receipt of secured feedback transactionally creates immutable content locks **before** any formal commit. Old offered revisions remain pinned until explicit Player supersession/release acknowledgment or their execution lease has expired. A 30-second acknowledgment grace triggers reconciliation and degraded health; it does not permit discarding a possibly secured assignment or rerolling its content. Pending offers conservatively preserve byte identity until the Player reports which assignments were secured or explicitly failed/released. A delayed report can lock an identical still-valid assignment from the retained offer but cannot authorize an obsolete plan. Bound outstanding revisions/bytes and apply backpressure when acknowledgment is missing. Network uncertainty never becomes proof that a file was not secured.

Playback preparation is separate from secured files. Prepare only current and imminent work, initially with a 5-second decoder lead. Readiness reports prepared IDs, current clock uncertainty, whole-Player capacity and coded failures independently. Black layers require no bytes but still pass preparation/capacity/equipment checks. Coordinator commitment requires all required participants in the currently due coordinated group; preparation of one Player or one video does not imply group readiness. Missing required preparation at intended start skips that group and retains compatible fallback. A late join explicitly receives current logical position under fresh authorization, rather than replaying an expired command. Tight-sync guarantees remain deferred.

Readiness loss after initial acknowledgment invalidates unexecuted authorization and is reported to both planning and lifecycle ownership. The Player locally refuses an invalidated commit even if central cancellation is delayed. It cannot reroll locked media; it may reacquire those same bytes. Ordinary source outage does not invalidate healthy secured bytes. Failures are immutable bounded records, never raw exception text.

## Player leaf API obligations

The executor accepts externally authenticated configuration, Plan and Commit models; owns state persistence, ordering/generation gates, pin lifecycle, timed rendering and observations; and accepts an injected Clock/TimeMapping and Renderer interface. Network transport is not trusted merely because it deserializes a model: only the networking adapter attached to the authenticated central origin can call acceptance methods.

Expose bounded methods for accepting configuration/plan/commit, supplying acquired byte streams, preparing imminent assignments, reading readiness, advancing output at explicit current time, and applying explicit release/cancellation. Design exact method signatures in the Player module document before code. Do not perform downloads or disk hashing on the GTK main thread. Byte acquisition may run in a background thread; acceptance/publication must recheck current assignment authority after acquisition so a concurrent cancellation cannot resurrect it. All GTK methods run on the main GLib thread. Methods must not hold an executor lock while waiting on a network iterator.

Renderer input contains concrete local Layer records, local file paths and media positions, plus the Output's effective calibration. The Renderer owns composition/transforms and persistent surfaces; it never selects assets, resolves global priorities, or reads upstream configuration. Preparation/preroll, capacity, and observed presentation are separate results. An asynchronous native prepare may initially return pending. Do not clear the current picture before a replacement is prepared and successfully presented. Resource profiles must account for two Outputs, current and replacement decode, overlays and reveal; a recording adapter's capacity is simulated evidence only.

On each output tick, use active committed layers and central ordering `(priority, root_order, admission_order)`. Compute fades against the layer's original interval and media position against its media origin; never restart these because a rolling Plan arrived. Covered assignments advance logically without replaying hidden changes. On reveal, prepare/seek current position. Opaque black and transparent layers remain different. The executor may retain a successfully presented compatible still under a separate per-Output/Frame/generation cache pin; cache presence alone does not establish that it was a valid picture.

During recoverable prepare/decode/network failure, retain current valid composition where possible. After authorized video/overlay/plan validity ends, use the retained compatible still for that authorized Frame or local black fallback, and report fallback rather than falsely reporting active playback. Binding replacement invalidates the old Frame/generation's retained authority. Expired previews locally revert using the committed calibration and explicit preview lease carried in OutputBinding, even without central connectivity.

Durable executor state uses atomic replace/fsync with a private state file, recording accepted epoch/revisions, plans and pin ownership for reconciliation. A process restart does **not** restore execution permission: it begins in black kiosk fallback, validates local cache, establishes fresh clock health and central authority, then accepts current-state plans/commits. Old process monotonic times are never persisted as reboot-stable deadlines. Existing pins are reconciled/released safely rather than blindly erased at boot. A new epoch invalidates old commits and observations; ordinary reconnect within a live epoch preserves increasing feedback sequence.

## Checks required before integration acceptance

Meaningful controllable-clock/recording-renderer tests must cover secured-before-commit pins; acquired versus prepared/capacity; stale/duplicate/reordered plans/commits/readiness; clock step/staleness; current video reveal under a covered assignment; black versus fade; failure retaining old output; expiry beyond horizon; preview expiry offline; cancellation during download; cache pressure/integrity failure; rebind/retirement; and cold restart with no replay before reconciliation. Central PostgreSQL tests additionally prove atomic offer/lock/commit, duplicate activation persistence, epoch/generation checks during delivery, readiness invalidation and exact locked content across restart.

These tests cannot establish GTK/GStreamer, physical continuity, cold boot/HDMI behavior or visible coordination. Native renderer and appliance artifacts still require separate executed integration and physical evidence.
