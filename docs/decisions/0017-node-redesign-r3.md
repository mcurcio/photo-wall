# 0017 — The Node redesign (r3): requirements and current choices

**Date:** 2026-10-06 · **Layer:** system design (what binds the Node programme, and the shape it builds toward) · **Status:** This is a short record of the Node redesign, revision 3, as the owner answered it on 2026-10-05 and 2026-10-06, and the Node API discussion, rounds 1–2, on 2026-10-06. It is amended for what E3b built (2026-10-08): C4, C5, C11, C13, C14, C16 and C18 each cite the E3b design section and erratum they come from. It is checked against [0016](0016-central-and-node-relationship.md), which ranks first. The requirements below bind. Every current choice below can be revised, and each one names the owner answer it comes from. The full design (r3) is working state outside the repository; this page is the version kept in the repository.

## Why this exists

[0016](0016-central-and-node-relationship.md) reopened [0015](0015-player-base-layer-and-health-overlay.md) wherever 0015 assumes Central is in charge. Revision 3 of the Node redesign is the result. It replaces 0015's Authority context, Central link, permits and cursor feeds with a Node that runs itself and reports through one Node API. Where 0015, the [Player architecture](../player-architecture.md) or the r8 design pages (`docs/design/player-health/`) conflict with this page, this page wins.

## Current choices (revisable)

| # | Current choice | Owner answer it comes from |
|---|---|---|
| C1 | **The Player never alters the show.** It plays what Central asked for. When it cannot, it says so: an unplayable item, or a list that has run out, is a fault on that Frame, reported and overlaid. It never skips, loops, substitutes or reorders. A crash guard stays, so content cannot crash-loop the Node, but the guard reports a failure to play and never edits the show. | IQ1, 2026-10-05 |
| C2 | **Central's Planner sends a list per Frame.** A list that runs out is a fault, not a loop. The Planner may author "repeat until E"; the Node never repeats on its own. | Gate Q3; r2 gate OQ3 |
| C3 | **The Node serves its own API over NATS; Central is one client.** Each Node runs a NATS server on loopback, owns every bucket and stream on it, and dials one leaf link to a hub in Central's deployment unit, over WebSocket through the origin. The hub holds one account per Node, with Central as a client inside it, plus one wall-wide account (C14). No Node id appears in any subject. Bulk bytes stay on HTTP. | Gate r3 OQ1 ("nats-leaf"); protocol framing, chat 2026-10-06; API2 note |
| C4 | **Plug-in model.** Each component owns its own micro service (its methods), its buckets and its streams, declares them itself, and announces itself through `$SRV.INFO` and a `birth` key in its own state bucket, carrying its name, version, pipe, release digest, schema majors and slice digest. Birth is state, not an event: every attach re-puts it, so it is present in every epoch of the bus whatever the start order (E3b design §5, §7.2 node; errata E-E3B-R2-4, E-E3B-S5-1). The store is split at two levels. `contracts` fixes each store line's byte total, stream count, pipe and declarer (`contracts.node_link.STORE_LINES`), and the lines fit the store when `contracts` is imported. The split inside a line, a component's `Slice` of names, kinds, caps and key tables, ships with each release, not in shared `contracts`. A slice past its line is refused at construction. Apps declares the Player's line from the held Player releases' slices (E3b design §7.3; errata E-E3B-CUT-4, E-E3B-S5-2). The API never judges and never gates. A component's methods are `<component>.method.<name>`. Central calls only those, besides the Node's JetStream API and `$SRV` discovery, and a component answers each call once. Nothing else crosses the leaf link. A Node program built on `nodeapi` cannot queue anything toward the hub: it reports only by writing its own streams and buckets, which Central pulls (C13). The hub's per-Node users and the Node's own server enforce this for every program that uses the bus as `nodeapi` does; a raw client can still aim a JetStream reply at Central's inbox or churn subscriptions on an import, which no `nodeapi` program does and a bus restart clears (E-W1-CONS-3). The subject lists live in `contracts/node_link.py`. | Artifact comment 2026-10-05; gate Q2 note; protocol framing; leaf rule, 2026-10-06 (the confirm review proved that a stalled hub let a Node program fill the bus's memory); E3b design gate, 2026-10-07 |
| C5 | **The NATS rules are held by structure.** Only `nodeapi` imports the NATS client (import contract, landed in E1). Its own modules point down, `node \| hub` → `documents` → `buffers \| pull \| envelope` → `epoch`, and siblings never import each other (import contract; E3b design §7.1; erratum E-E3B-R2-3). Every connect re-declares. Nothing on a main path waits for a publish acknowledgement. **Every buffer uses the memory store, so every bus start is empty**: a reboot, a crash, an OOM kill and a restart take the same path, and each writer refills what it owns at its next attach. The hub's WALL uses the memory store too. This closes the file store's crash-reload loss (E-W1-CRASH-1) and its unbounded overshoot (E-W1-FIT-2), and with them the flat per-stream block charge and the consumer state files (E3b design §6, §9.5, §12 change 1; errata E-E3B-CUT-3, E-E3B-S3-1). The bus unit is fenced at 256 MiB (`MemoryMax`) with `GOMEMLIMIT` at 140 MiB and a 12 MiB store. The store is heap, charged at the measured heap factor for the smallest `nodeapi` event (5 ×, measured 4.7): 12 MiB × 5 + 17 streams × 12 consumers × 104 KiB + a 48 MiB idle server = 128.72 MiB, under `GOMEMLIMIT`, and `GOMEMLIMIT` plus 4 MiB of headroom is under the fence. `contracts` checks this sum when it is imported, and E3c's fence job re-measures the factor on linux-arm64 with small messages (E3b design §7.2 contracts; erratum E-E3B-R2-5). The Node server refuses a stream past the store limit, an 18th stream, a 13th consumer on a stream, or a stream without a byte cap, always when it is created, never a write. Store lines fit the store, so no `apply` in any order meets that refusal (C4). **Events carry no boot.** The envelope has three headers, each with a named reader: the message id (the server's dedupe and Central's projection dedupe), the schema major (C12) and the writer (C16) (E3b design §7.2 envelope, §12 deletes). Every read position is a cursor (stream epoch, sequence) that its reader keeps (C13, C16). | Gate r3 OQ1 and the measured spike; API8; consumer cap, 2026-10-07 (256 MiB, owner); E3b design gate Q1 = start clean, 2026-10-07 (supersedes STORE1, the file store on tmpfs) |
| C6 | **Three design rules.** (1) Content is held, not leased. Last good is what the consumer accepted, and anything shown, restarted or recovered is read from files. (2) Each component writes only its own namespace. Each kind has one writer. Central records an event or state change before judging it (S1′). (3) Nothing on the show path waits: not on Central, the bus, Content, a publish acknowledgement, or another component's decision at runtime. | Design rules of r3, checked against 0016 |
| C7 | **Kinds of time stay apart.** Each Node's wall clock follows a shared NTP reference through chrony. Show time is a position on the Node's monotonic clock and uses FPP MultiSync's correction curve and freewheel. Clocks are never compared across systems. | Gate Q4 note; r2 gate OQ2 ("ntp-signage") |
| C8 | **Memory: optimise now, with no measurement phase.** The readings from the test Pi show the programs use about 400 MiB. The 2509 MiB preparation peak comes from release roots unpacked as tar. The cuts: the app and App Manager roots become squashfs images, mounted in place (app 1180 → 288 MiB, manager 261 → 62 MiB). Each image is held once, with no unpacked or import copy. Each cap is set from its reading: 2 × the peak, at least the peak + 32 MiB. The Player's cap never falls below its own configured budgets. Double counts are removed. One device-class line table, held by a test, sets every cap. This leaves a content line of about 0.85 GiB on a 4 GB Node (about 1.04 GiB once AppManager is gone). A cap that is too low shows itself through the existing `oom_kill` facts. The plan supersedes the 7 GiB-era budget in the [4 GB memory design](../node-4gb-memory-design.md). | Gate r3 RQ1 note; chat 2026-10-06 |
| C9 | **Tests.** Integration tests that exercise functional requirements are preferred over unit tests of internal code. A test may be deleted when moving or maintaining it costs too much, but never when it is the only proof of a functional requirement, and each deletion is listed. A later epic replaces PR 46's per-module unit tests with a few functional integration tests. | E1 discussion, 2026-10-06 |
| C10 | **The programme, refactor first.** E1 splits the Node codebase so that each context lives in one directory (`appliance/kernel`, `host`, `boot`, `apps`, with `display_host` and `health`). One layers contract holds the split. Retiring code is not moved. The design's recommended order after E1: E2 memory cuts and E3 Node API foundation in parallel; then E4, the tracer (node-pid1 leg `offline`); then E5 Central intent and recording, E6 Content and the local app lifecycle, E7 Frames, faults and overlays, and E8 the Player executor and time, in four parallel lanes; and last E9, removal and qualification. The owner has answered "pursue E1 first". The order after E1 is the design's recommendation. | Gate Q5 note; E1 discussion |
| C11 | **Two kinds of operation, split by lifetime.** Methods (micro service endpoints) for one-shot and live actions: reboot, Identify, calibration preview, resync. Desired-state documents, with reported status, for anything that should stay true: app release, Output layout, Show per Frame, mute. Retention is not a document: it is set per topic in each release's slice (C13; owner answer Q2 = remove; E3b design §7.3, §12 deletes). Every change on a Node emits an event, whoever caused it, so a reply is never the only signal; documents and state are readable by any client. | API1 and its note; guidelines N16, N17; E3b design gate Q2, 2026-10-07 |
| C12 | **Central writes every held major.** Central writes each document in every schema major a held release reads, current and rollback, until the old release leaves. | API3 |
| C13 | **The Node holds its events.** Central reads each event and state stream of a pipe through a **cursor reader**, from its own cursor (stream epoch, sequence) kept in Central's store, and records each message with its cursor in one transaction. The reader's consumer is ephemeral, takes no acknowledgements and is disposable. Any reply proves it alive; silence, `503` or "consumer deleted" means it is lost, never an empty stream. The reader checks the consumer sequence of every delivery: a jump, an incomplete request or a lost consumer is a loss in transit, so it keeps what came before, deletes the consumer best-effort and recreates it from the cursor, and writes no gap row. A gap row is written only when the stream sequence jumps while the consumer sequence is contiguous, and an epoch that ends gets one row with count "unknown". This replaces wave 1's durable consumers and their acknowledgements, which went silent when the store was lost (E3b design §7.2 pull, §8, §9.3, §9.4; errata E-E3B-R2-1, E-E3B-R2-2, E-E3B-S1-1). A component's views of its own desired bucket and of WALL read through the same reader. There is no hub buffer, no hub intent mirror and no direction filter. A link reconciles when it comes up, when a reader is lost, when a new `birth` is drained, and when the bus's stream names (a bounded reply, polled every 2 s) differ from those it last reconciled, so a line created after that is drained within about 2 s (E3b design §9.1, which said "no timer"; errata E-E3B-S4-1, E-E3B-CC-1). Each buffer is circular (records, observations) or sticky (state, desired documents, the wall copy) (C18), and each topic's retention is set in its component's slice and changes only with a release. The per-Node override, its `retention` key and its refusal are removed; dynamic per-Node retention is a future nice-to-have, not a requirement (owner answer Q2 = remove; E3b design §7.3, §12 deletes). `apply` changes a stream's limits only inside its component's store line, which fits the store, so no split can bypass the fit (C4, C5; E3b design §7.2 buffers, §9.7). A loss before Central reads is a counted gap. | API4 note; API5; API8; guideline N19; E3b design gate Q2, 2026-10-07 |
| C14 | **Wall-wide data.** A wall-wide account at the hub holds one stream that every Node account imports; each Node keeps a read-only local mirror. Broadcast is reference data, never a command: a Frame acts on a wall-wide value only when its own per-Node document names it. The wall stream's size, `WALL_STREAM_BYTES` (512 KiB), is a frozen wire constant pinned by a contract test: the hub's WALL and every Node mirror are created from that one number and never updated, and it is charged in the store fit (C4). Growing it is a wire change, so every Node runs a base that carries the new size before Central's WALL grows, and growing the wall table is a two-step release gated on the fleet's reboots (E3b design §10; erratum E-E3B-D1-1). | API2 note; API6; guideline N18; E3b design gate Q3 = freeze, 2026-10-07 |
| C15 | **Show timing rides NATS; clocks ride NTP.** Timing documents (Run anchors, cue instants, the house calendar) travel in the wall-wide stream; each Node's clock follows NTP (C7); there is no sync beat on the bus. | API7 |
| C16 | **Write order.** A write is ordered by the Node's per-key revision with a conditional update (expected revision), and records its writer. The Node never refuses. When another client changed a value, Central adopts the Node's value as the new truth and shows the change to the operator. A revision names a message only inside one creation of its stream, and a Node's store is lost at every bus start, a reboot included (C5): every conditional-write token and read cursor is (stream epoch, sequence), the epoch a fresh id written into the stream's metadata when it is created. A token from another epoch is stale and never applied; Central re-reads. | API9 (chat, after the round-2 page); NATS teardown, 2026-10-06 |
| C17 | **Lead time and late join.** Central writes a document naming a time at least a lead time ahead and watches each Frame's horizon. A Node that is late keeps last good with a late fault on that Frame only, then joins the Run at its current position. | API10 |
| C18 | **Event buffers drop their oldest; documents and state are sticky.** Every Node and hub buffer uses JetStream's limits retention with discard-old, and the server never refuses a write because a buffer is full. Event buffers (records, observations) are circular: when full, the server drops the oldest, and the loss shows as a sequence gap. Keyed buffers (reported state, desired-state buckets, the wall stream and its mirrors) are sticky: each is sized from a key table (keys × history × largest value) carried in the stream's own metadata, keeps per-key history only, and is never evicted by bytes or count. Each writer reads that table from the stream and refuses its own unlisted or oversize write before sending, so the Node never refuses. State is sticky so that a state gap counts revisions Central never saw, never a lost key (E3b design §4 rule 2, §7.2 buffers and documents, §9.3; review round 1, NATS P1). **There is no manifest.** Central owns every key of every desired table it writes, and "none" is a value. An absent key means "unknown" and its reader keeps last good, and a new epoch makes Central put every key again (E3b design §7.4, §12 deletes). | Owner steer on the E3a review, 2026-10-06; owner on the NATS teardown, 2026-10-06 ("some sticky topics may be desireable to configure as excluded from the circular buffer config"); E3b design, 2026-10-07 |

N16–N19 are the Node API page's four guidelines: every change emits an event (N16), documents and state are readable by any client (N17), each Node has its own namespace and Central can broadcast wall-wide data in one message (N18), and the Node holds its own events with retention tuned per topic (N19). The owner called them "reasonable guidelines", open to revising in certain cases, so they sit in C11, C13 and C14 as current choices, not in the requirements table. C18 is a guideline of the same kind: it binds as a requirement only if the owner says so.

## Open

The design recommends these, and the owner has not answered them, so they are recorded as open, not as choices:
- Presence from link events plus `$SRV.PING`, with no heartbeat key.
- A read-only view of each component's own desired bucket in `nodeapi` (F4).
- A reserved Content method for bytes by digest (F5).
- Central as the only writer of desired state, for now.

## Costs

- **Central gains a second transport to the Node.** Nodes now need a NATS hub as well as HTTP. Booting needs both, and they ship as one unit.
- **Central can no longer stop a Node it cannot reach.** The Node plays a deleted or superseded show until it hears from Central again or its list ends.
- **Faults the old design hid are now visible.** Under C1, an exhausted list or an undecodable item tints its Frame, where the old code looped or skipped.
- **There is upstream code on every Node.** nats-server is pinned by version, and its known sharp edges are contained in `nodeapi` and in the bus's 256 MiB fence.
- **The store is heap, and every bus start empties it** (C5). The memory store costs about five times its stored bytes at the smallest event, so the 12 MiB store is charged 60 MiB of the 256 MiB fence. Every bus start, a manual restart included, loses the unread event tail, which Central counts as "unknown"; STORE1's retention across a restart is given up. All 17 streams are assigned to store lines, so a new stream kind needs another line to give one up, or a higher stream cap, which needs the owner. A Player hot-swap cannot add or rename a stream past the Player line's 3 (E3b design §6, §7.3, §13).
- **A `nodeapi` program cannot talk to Central** (C4). It cannot publish an event, call a Central service or push a stream across the leaf; only Central's requests and pulls cross. The outbound queue toward a stalled hub is then bounded by what Central asked for, not by a deadline. The cost is that every Node-to-Central signal is a record Central pulls, so it arrives at Central's polling pace.
- **Three NATS mechanisms are unprobed until E3a:** the WebSocket leaf, same-domain isolation, and the wall-wide mirror across accounts and the leaf. Each has a fallback, and each fallback stops for the owner.
- **Central keeps one adapter per schema major still in the field** (C12).
- **As-run survives Central's absence only so long.** About 10–19 hours of as-run survive Central's absence; longer gaps are counted holes, and a bus start (a reboot included) while Central is away loses the unread tail, count unknown (F7).
- **"A Node never invents intent" weakens for desired buckets,** from held by construction to held by library plus test (F4).
- **One console prompt** when another client changed a value (C16).
- **Clients can lose data** (C18). A full event buffer drops its oldest whatever it is, records Central has not read included. The loss is a counted hole, never a refused write. A sticky document or state key cannot be lost this way, but each sticky buffer holds only its declared keys, each up to its largest value: a new document is a table change, and Central refuses a write that would exceed the table.
- **Memory caps rest on one boot's readings.** A wrong cap is found by an `oom_kill` fact, not ahead of time.
- **The epics are large:** about 33–51 hours serial, or 20–30 hours with the lanes.
