# 2026-09-30 fleet command and recovery slice

**Evidence class:** staged local software and isolated PostgreSQL checks in draft PR #39. **Status:** implementation behind a closed effect gate, not deployed or physically qualified.

The loader OS and application remain separate channels. Migration 051 and the unmounted `FleetCommandLifecycle` compose an operator's frozen maintenance request, an exact target/fallback AppAttempt, an unbound Runtime drain, and immutable command bytes in one transaction. A second transaction records an exact ready-to-stop claim, commits the matching drain and attempt, and inserts one immutable stop permit. New issuance rechecks the effect gate, current T1/T2 session, desired policy and deadlines after lock waits. Neither transaction sends an OS effect. A lost permit response can replay its exact bytes while still valid even if desired policy has since changed; it cannot renew the deadline. A command that has not reached stop cannot replay after its desired policy changes.

Migration 050 and the separate unmounted recovery data adapter allow a newly verified current OS carrier to claim a short CAS lease after a committed stop. It can read only the attempt's retained exact target and fallback bytes and append bounded repair claims. The original issuer remains frozen, an explicit lease revocation is terminal, and historical drains without a fleet drain UUID cannot qualify. Recovery requires the matching immutable command and permit as well as the committed drain. Migration 052 uses a deferred database constraint to reject a newly committed unbound drain without its permit in the same transaction. A committed drain's stored identity and snapshot are immutable.

The read-only operator projection distinguishes desired app policy, T0 serial/boot claims, Central attempt and command records, authenticated OS report claims, and repair leases. It labels command delivery and physical stop as unknown even after a permit expires; it does not expose proof bytes or a nonce. A V2 local app proof can now link a signed applied-control receipt to the current Registry row and OS-observed process, while V1 remains historical. The acceptance assessment is still read-only and cannot promote an artifact. The desired-assets view now retains current-generation accepted base content keys, matching the existing conservative cache-eviction root.

## Focused checks

- The command issuer passed 7 real-PostgreSQL lifecycle cases and a broader 103-case relevant PostgreSQL/contract slice before migration 052. Cases covered atomic rollback, changed Output inventory, exact replay, policy changes after permit issuance, and lock waits crossing session or permit deadlines.
- The recovery adapter passed 22 focused real-PostgreSQL cases before migration 052, including current carrier, CAS, retained roots, revocation and existing OS route regressions.
- The final guard, drain, issuer and recovery slice passed **53 real-PostgreSQL cases** after migrations 050–052 were frozen. It includes a two-transaction prepared-scope tamper, direct stop refusal and historical pre-052 migration test.
- The management projector passed five focused PostgreSQL cases and the console Vite build. Its queries are set-based and its UI labels issuance separately from OS claims.
- The V2 proof transport passed 34 portable and 54 focused PostgreSQL cases. It does not yet have a mounted base-owned report producer or per-Output handoff evidence.
- Whole-repository portable pytest passed **2,846 tests with 1,193 environment skips** after setting uv's cache and tool directories under `/private/tmp`. The first run had 29 release-planning failures because `uvx` attempted to read a restricted user cache/tool directory; one targeted case and then the full suite passed with those two environment paths redirected. Ruff, six import contracts, relative documentation links across 121 Markdown files, `git diff --check`, and the console production build passed.
- Whole-repository PostgreSQL pytest passed **3,692 tests, 346 environment skips and one expected failure** against the already-running local Compose database. The worktree's private `.env` is absent, so the required `scripts/test_local.py -q` wrapper could not be used directly; an in-process runner supplied the database URL from local container configuration without writing or printing the credential, and every database fixture used an isolated temporary schema. This whole run began before the last prepared-drain immutability edit; the final 53-case affected PostgreSQL slice passed afterward. Hosted exact-commit checks remain separate.

These focused results overlap and are not a combined test count.

## Remaining gates

There is no production T1/T2 request verifier, command route, accepted-frontier writer, per-Output first-buffer evidence, deployment gate controller or physical PXE/display qualification. D14 command identity, D16 bound Run/Actuator withdrawal, and D17 serving/rollback image certification remain open. The public bound drain path refuses. A prepared command that never stops the app still needs a separate authenticated no-stop reconciliation that atomically aborts its drain, records the outcome and releases its exact roots; timeout alone cannot do that. Commands therefore remain unmounted and the rollout gate remains closed.

The [implementation map](../player-fleet-implementation-map.md), [red/blue design](../player-fleet-red-blue-refinement.md), and [command rollout audit](2026-09-30-command-rollout-audit.md) own the architecture and deployment boundary. Local database checks do not prove package continuity, physical pixels, or a usable command trust anchor on the deployed network.
