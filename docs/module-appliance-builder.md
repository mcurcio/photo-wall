# Appliance builder and RAM-root bootstrap

Status: accepted design and implementation in progress, 2026-09-05. This implements the [accepted platform](decisions/0005-native-platform-and-registration-fallback.md) and [signed release contract](module-appliance-release.md). A built image, generic VM boot and physical Pi PXE/HDMI qualification are distinct evidence gates.

## Ownership and build API

The builder customizes the signature-verified Ubuntu 24.04.4 Raspberry Pi arm64 input, installs the separately locked Player-only package, and emits a common disk image and PXE bundle. The shared release parser, updater slot state and Player entrypoint have their own owners. The bootstrap invokes those contracts rather than implementing a second release format or A/B state machine.

The reproducible GitHub Actions wrapper and its exact-artifact headless VM gate
are documented in the [CI appliance module](module-appliance-ci.md).

The staged command interface is `python -m appliance.build`. `decompress INPUT OUTPUT` rehashes and bounds the fixed Canonical-signed image, `extract IMAGE ROOT` preserves filesystem metadata, and `packages ROOT EVIDENCE` resolves the runtime packages. `export-source REPOSITORY DIRECTORY REVISION` refuses a dirty checkout and exports exact committed appliance/neutral release files with a checked file inventory and commit timestamp. `prepare ROOT SOURCE WHEELHOUSE PUBLIC PACKAGE_EVIDENCE OUTPUT` checks its executing builder/bootstrap/updater/release files against that export, then produces the unsigned digest-named rootfs SquashFS, canonical `release.json`, common boot tree and inventories. Finalization also checks its executing files against the source inventory inside the authenticated rootfs. Each output directory is new and outside every Git tree. Debian additions resolve through snapshot `20260905T000000Z`, with archive signatures enforced and every downloaded package retained and hashed. Python packages install offline from the [Player-only wheelhouse](module-player-package.md). The inventory distinguishes inherited base packages from changed packages and records tool binaries, native import results, source/file identities and public configuration hash.

`finalize BUNDLE SIGNATURE OUTPUT --trusted-public PUBLICDIR` requires the original four deployment public inputs as an independent trust anchor, compares them byte for byte with the bundle's public copies, and authenticates the 64-byte Ed25519 signature using that external public key. It rechecks payload hashes and compares every staged boot file with `/boot/firmware` inside the authenticated SquashFS before creating output. This binds the kernel, DTBs, configuration and initramfs through the signed rootfs; `build.json` is diagnostic metadata and cannot authorize replacement boot files. Before returning, a deadline-controlled read-only libguestfs child reopens the completed disk, verifies every FAT file's exact length and SHA-256 and checks the state root/marker ownership, modes and empty contents. The private signing key never enters a Docker image or build context. Intermediate and final image files remain outside Git.

Use an isolated Linux arm64 container with copied inputs and a task-owned named volume; this host's Docker bind mounts are excluded because they stalled Desktop during earlier fixture work. libguestfs with the direct QEMU/TCG backend accesses only explicitly supplied image files. Export the root with numeric ownership, extended attributes and ACLs preserved; verify hardlinks, symlinks and capabilities with a small extraction fixture before trusting this path. Linux customization uses the extracted root and prevents package service startup. No host block devices or loop mounts are used by the builder. [libguestfs backend selection](https://libguestfs.org/guestfs.3.html#BACKEND), [metadata-preserving tar export](https://libguestfs.org/guestfish.1.html#tar-out).

The output disk has an aligned 1536 MiB FAT32 common boot partition and a 4096 MiB ext4 partition labelled `PWSTATE`. Both are generated as bounded regular files, populated with userspace filesystem tools and copied into a new regular image at checked offsets. The state filesystem root is root-owned 0755; apart from ext4's filesystem directory it contains only root-owned 0444 `.photo-wall-state-v1` with exact bytes `photo-wall-state-v1\n`. It contains no generated identity, private credentials, cache or update state. The common signed release remains below `appliance/` on the boot partition so disk boot also works without a prepared update slot. [mke2fs directory population](https://man7.org/linux/man-pages/man8/mke2fs.8.html).

The boot ABI is the hash of a canonical sorted inventory of the fixed kernel, kernel modules, firmware and DTB contents plus the exact bootstrap logic staged into the guest: `appliance/__init__.py`, `bootstrap.py`, `updates.py`, `contracts/__init__.py`, `release.py`, the initramfs hook and the mountroot script. Generated initramfs and its embedded expected ABI are excluded from that digest to avoid a self-reference. All of these artifacts, including initramfs, still receive independent hashes in the build inventory. A fixed-ABI userspace update must keep the same covered components. SquashFS size is bounded by the shared release contract's 1 GiB limit. The first common artifact budgets a 512 MiB writable root overlay on an 8 GiB Pi; this is a configured bound, not measured capacity.

OverlayFS upper and work directories are created under a private mode-0700 tmpfs; the upper root itself is mode 0755 so the merged root remains traversable by non-root OS services. Bootstrap verifies the merged root's mode and root ownership before publishing it as the selected root and cleans all mounts if that check fails. This is bootstrap and initramfs logic, so the corrected common boot artifact must be rebuilt and replaced; a userspace A/B update cannot repair an older disk initramfs or its embedded bootstrap.

Before computing that ABI, the `pi5-onboard-wired-v1` firmware profile preserves Broadcom, Cypress, Synaptics, Raspberry Pi and rtl_nic firmware, top-level firmware/license files, and every required symlink target. Required unresolved links fail the build. Root-aware resolution handles distro `/etc/alternatives` links and records their selected target as a direct relative link within firmware, so selection is covered by the ABI. Exact removed/retained byte inventories and rewritten links are recorded and distribution licenses remain present. Unrelated add-on vendor devices are outside this first onboard-wired/dual-HDMI profile; kernel modules are retained. This profile follows an executed size failure with the generic firmware payload, not a relaxed rootfs limit.

## Initramfs flow

An initramfs-tools `boot=photowall` mountroot hook establishes wired DHCP and runs `/usr/bin/python3.12 -I -m appliance.bootstrap`. The initramfs contains the selected distribution interpreter/stdlib and its library dependencies, OpenSSL 3, required filesystem/network tools and modules, `appliance.bootstrap`, `appliance.updates`, their empty package initializer, and `contracts.release` with its initializer. It includes neither GI/Pydantic nor central/media/build code. In the final root these minimal modules live in distro `dist-packages`, after the Player venv's complete wheel on its import path; the hook explicitly copies only the five required modules into initramfs stdlib. The native Player import smoke runs after staging these modules to catch package shadowing. The public configuration, public CA, release verification key and expected boot ABI are installed at fixed paths; manifest values never become shell commands. OpenSSL verification uses `pkeyutl -verify -rawin -pubin` against small regular manifest/signature files. [OpenSSL Ed25519 command semantics](https://docs.openssl.org/3.0/man1/openssl-pkeyutl/#ed25519-and-ed448-algorithms).

Bootstrap discovers only ext4 volumes labelled `PWSTATE`, first mounts a candidate read-only and validates the exact nonsymlink ownership marker. Zero valid volumes means volatile persistence; multiple valid volumes fail closed rather than choosing an arbitrary identity. It never formats, repairs or initializes attached media. A validated writable state mount remains at `/run/photo-wall-state`; its updater directory is root-owned 0700 and its Player directory belongs to uid/gid 10001 with mode 0700. A new Player directory is configured and fsynced privately before rename, then its state parent is fsynced before durability is reported. Existing identity bytes are preserved on validation or fsync failure. A state fault still allows the signed common release to boot and report volatile registration as defined by decision 0005.

With usable state, the shared slot store selects and durably consumes any trial attempt before it can be booted. Every selected filesystem is rechecked against its authenticated length and SHA-256 while being copied into RAM. A bad candidate falls back through the shared active-slot policy; the signed common disk/network release is independent of per-device state. Network fetches require HTTPS with the embedded public CA, bounded length/deadline, no redirect/proxy and a usable clock established from configured provisioning time sources. Trust/time failure never enables insecure TLS.

The common release is fully verified into RAM before optional seeding of the slot store. A seed failure preserves the verified common boot with durable Player storage, `update_storage` fault and no trial/slot authority; it cannot mark a candidate good. Corrupt common disk bytes fall back to the trusted HTTPS release. The bootstrap has a 120-second whole-acquisition timer which interrupts slow header/body reads as well as checking byte counts. The initramfs time client runs explicitly as root using a minimal root passwd/group and files/DNS NSS configuration; it does not depend on a missing `_chrony` account.

The verified RAM copy is mounted read-only as SquashFS. A separate bounded tmpfs supplies OverlayFS upper/work directories; the overlay becomes initramfs-tools' root mount. Failed mount attempts try every owned mount in reverse order; unsuccessful cleanup stops boot rather than attempting another release over a partial mount. RAM payload, state and bootstrap boot-selection report remain below `/run`, which moves into the selected root. The selection report identifies the boot and release for the updater's exact mark-good check; it conveys persistence status to the Player without any old execution authority. Failure before a usable root is available reports only a bounded code and reboots according to the boot policy, without exposing an interactive console on the displays.

The root `photo-wall-accept-trial.service` starts after the Player and invokes `python3.12 -I -m appliance.updates --state-root /var/lib/photo-wall accept-current --config-dir /etc/photo-wall`. It derives the current release from the protected boot report and loads the current ABI/configuration policy; no release ID is embedded in its own rootfs. It reuses the updater's exact report validation and continuous 30-second health gate, after signed-image verification under its separate 300-second deadline, with a 180-second health observation deadline and a 510-second service timeout. The update lock spans verification, fresh health observation and promotion. Common fallback, volatile, faulted and stale reports cannot promote a trial. A failure invokes `photo-wall-trial-recovery.service`, whose bounded root predicate permits reboot only for the actual durable unaccepted trial when a distinct authenticated active fallback exists; nonqualifying and corrupt states skip recovery without reboot. The unit can write only owned persistent state; it receives no Player execution authority.

## Acceptance gates

Unit/fault tests cover strict build inputs, checked partitions, public-only configuration, signed exact-byte manifests, no traversal/symlink escapes, bounded downloads and partial cleanup, unknown/multiple/unwritable state, wrong markers, corrupt selected candidates, shared slot fallback, and mount-command ordering. Real Linux tooling tests must produce and reopen FAT/ext4/SquashFS artifacts, preserve extraction metadata, inspect initramfs contents, run distribution-native Python imports and verify the Player-only package boundary. Tests using generated bytes do not establish an Ubuntu image build.

The exact final artifact must have an external manifest/checksum report and clean source revision. A QEMU generic-arm64 boot may qualify userspace/bootstrap and fault behavior with a separate compatible test kernel; it does not qualify the Pi 5 firmware, onboard Ethernet, dual HDMI, seat permissions or PXE LAN. Those remain the physical bench gate.

Executed evidence so far: 18 tests passed in the pinned Linux tooling container, including completed-disk FAT hash/state-marker verification, generated SquashFS reopen, and preservation of hardlinks, symlinks, mode, user attributes and file capabilities through libguestfs export. The exact upstream image was rehashed, boundedly decompressed and fully extracted (about 2.4 GiB root). Runtime snapshot package installation completed with an empty dpkg audit, retained package hashes and offline Player installation. Post-staging imports passed with GTK 3.24, GStreamer 1.24.2 and required decoder factories. `systemd-analyze verify` reported no diagnostics for the Weston, Player and trial-accept units.

An interim generated initramfs is 74,229,385 bytes. Reopening it and executing its own isolated interpreter verified bootstrap/updater/SSL imports, public configuration digest, CA context creation, localhost NSS resolution and OpenSSL 3.0.13. Its actual chronyd 4.5 started as root in query-only mode and exited on a deliberate no-server timeout; no system clock was changed. Configured DNS/NTP responses, DHCP and a complete boot remain unqualified. Noble initramfs source explicitly moves `/run` into the final root before `run-init`; its `panic=10` path disables the recovery shell and reboots. Source inspection is not a boot test. The portable bootstrap/build/updater/release suite passed 133 tests with the two Linux tooling cases explicitly skipped locally. That interim root used an earlier Player revision and was not the final artifact.

The [final image benchmark](evidence/2026-09-05-appliance-image.md) supersedes the interim build status: appliance and Player revision `073f57d7547507de452a2fd273088d7542a6d070` produced a signed 672,448,512-byte rootfs and 5,906,628,608-byte disk, with matching common PXE tree. External signature verification, signed boot-tree comparison, completed-disk reopening and copied-image checks passed; the latest Linux appliance suite passed 138 tests. Run source-export commands with `PYTHONDONTWRITEBYTECODE=1` so interpreter caches do not change the strict source inventory. Boot and physical qualification remain separate pending gates.
