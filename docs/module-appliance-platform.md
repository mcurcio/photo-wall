# Native Player and appliance platform

Status: platform accepted in decision 0005 on 2026-09-05. Native Renderer and Player service are implemented with Linux software-rendering and network integration evidence. Image/bootstrap construction is in progress; no final appliance or physical boot qualification is claimed. The design below retains the remaining platform qualification gates. This extends [registry/enrollment trust](decisions/0002-registry-and-enrollment.md) and the [execution module](module-player-execution.md).

## Proposed platform and pinned inputs

Use **Ubuntu Server 24.04.4 arm64 for Raspberry Pi**, with the distribution's Python 3.12, GTK 3, GStreamer 1.24 and Weston 13. Ubuntu explicitly supports Pi 5 in its 24.04 arm64 images. The current official server image is `ubuntu-24.04.4-preinstalled-server-arm64+raspi.img.xz`; its published SHA-256 is `790652faeb4f61ce7bb12f5cb61734595c61d3cd882915b8b5f9918106c80d37`. This is the upstream input's published identity, **not** a built Photo Wall artifact. The local download was subsequently authenticated against Canonical's signed checksum file; the dated core evidence records its bytes and signing identity. [Ubuntu support/release notes](https://documentation.ubuntu.com/release-notes/24.04/), [image directory](https://cdimage.ubuntu.com/ubuntu/releases/24.04/release/), [published checksums](https://cdimage.ubuntu.com/ubuntu/releases/24.04/release/SHA256SUMS).

The official image package manifest was fetched during research. Its baseline contains `python3.12 3.12.3-1ubuntu0.11`, `linux-image-6.8.0-1047-raspi 6.8.0-1047.51`, matching kernel modules, `linux-firmware-raspi 12-0ubuntu1.1`, `initramfs-tools 0.142ubuntu25.8`, and systemd `255.4-1ubuntu8.12`. Preserve matching kernel/modules/DTBs from the selected build; do not combine Pi OS firmware and an unrelated Ubuntu kernel by assumption. [Official server manifest](https://cdimage.ubuntu.com/ubuntu/releases/24.04/release/ubuntu-24.04.4-preinstalled-server-arm64+raspi.manifest).

Resolve package additions and public security updates against Ubuntu snapshot **`20260905T000000Z`**. Its `/ubuntu/.../dists/noble/InRelease` was fetched successfully and lists arm64; SHA-256 of that fetched metadata was `cdb2f31d809f589719a53c6ad15f255b27569c4059542ada282aaa21b8e164b0`. Signature verification and a complete dependency solve remain build gates. Record every resolved Debian package/version/architecture and downloaded `.deb` hash, retain the required archive inputs outside Git, and pin that closure for rebuilding. A snapshot date alone does not guarantee indefinite upstream retention. [Ubuntu snapshot service](https://snapshot.ubuntu.com/).

Required runtime package families: `python3.12`, `python3.12-venv`, `python3-gi`, `python3-gst-1.0`, `python3-opengl`, `gir1.2-gtk-3.0`, GStreamer core/base/good/libav packages, the parser package if the explicit pipeline requires it, Mesa EGL/GLES/DRI, Weston, systemd and chrony. Noble's GI bindings explicitly require Python `>=3.12,<3.13`; its GStreamer Python package links `libpython3.12`. Use `/usr/bin/python3.12 -m venv --system-site-packages /opt/photo-wall/venv`. Do not point a separately downloaded Python interpreter at another Python ABI's system GI modules. [PyGObject package](https://launchpad.net/ubuntu/noble/amd64/python3-gi/3.48.2-1), [GStreamer Python package and arm64 availability](https://packages.ubuntu.com/fr/noble/python3-gst-1.0), [OpenGL Python package](https://packages.ubuntu.com/python3-opengl), [Weston package](https://packages.ubuntu.com/noble/weston).

Build a **Player-only distribution** containing `player` and neutral `contracts`, plus its locked dependency closure. The current all-module Photo Wall wheel also contains central/media implementation and must not be copied wholesale into the appliance. No Immich client, queries, credentials or central source models enter its filesystem. This requires a packaging boundary before image construction. Neither Bookworm's Python 3.11 nor Trixie's Python 3.13 is an assumed substitute for the current project constraint; Ubuntu avoids needing a custom CPython/PyGObject build for this slice.

## Native renderer contract

Implement `Renderer` with one Python process and two persistent GTK 3 top-level windows, each containing one `Gtk.GLArea`. The process also owns networking, cache workers, clock mapping and Executor. GTK/GL object access stays on the GLib main thread; network iterators, hashing and blocking file work stay on workers. GStreamer streaming callbacks transfer bounded frame data to the main loop and never call GTK. [GTK GLArea](https://docs.gtk.org/gtk3/class.GLArea.html), [PyGObject threading rules](https://pygobject.gnome.org/guide/threading.html).

Choose explicit local-file GStreamer decode pipelines feeding `appsink`, with at most two queued RGBA samples per decoder and a bounded mailbox that replaces stale samples. On the chosen 1.24 API use `max-buffers` and `drop`, not newer unverified `leaky-type` APIs. Respect negotiated stride/offset, bound dimensions before allocation, and retain buffer ownership until copying finishes. Video uses the declared silent SDR H.264 profile; stills decode once. No subprocess renderer, browser, `gst-launch` process or media URL selection belongs in the production Player. [GStreamer appsink](https://gstreamer.freedesktop.org/documentation/app/appsink.html).

`gtkglsink` is a supported embedded GTK sink and useful for the first package smoke test. It does not by itself implement the required arbitrary multilayer projective calibration. A GLArea with appsink gives the renderer direct ownership of composition, retained textures and homography; CPU-to-GPU copies are an explicit initial cost. A later GLMemory path can replace the transfer layer after context-sharing qualification. [gtkglsink](https://gstreamer.freedesktop.org/documentation/gtk/gtkglsink.html), [official GTK integration example](https://gstreamer.freedesktop.org/documentation/tutorials/basic/toolkit-integration.html).

For each Output, render ordered LocalLayers into a persistent composition target. Decode media with its declared SDR transfer interpretation; apply normalized crop, rotation and aspect-preserving cover layout, then the Frame's four-corner projective transform and SDR gain. Use a tested inverse 3×3 homography to map output pixels to the logical aperture, rejecting singular/nonfinite transforms. Composite premultiplied alpha with an explicit transfer/encoding convention; black is opaque content and pixels outside the aperture remain black. Preserve the previous successful target until the replacement's complete texture set and shaders are available. Calibration preview/expiry uses the binding's effective calibration already supplied by Executor. This matrix/colour convention needs acceptance and CPU-reference render fixtures before coding; it is not yet measured colour accuracy.

Preparation maintains per-assignment pipeline state and returns pending during decode/preroll/seek. A covered video may pause its pipeline while logical position continues; a reveal seeks to the supplied current position, never its paused position. Seek completion and the matching decoded sample precede presentation. Avoid repeatedly flushing an already-playing pipeline on every tick; compare desired position with its known segment/clock state. [GStreamer seeking semantics](https://gstreamer.freedesktop.org/documentation/additional/design/seeking.html).

**Implemented Executor integration:** asynchronous `PresentationResult('pending')` must preserve the grant and previous picture while awaiting the exact requested draw's completion. Executor preserves prepared/committed state during pending presentation and correlates fresh actual draw acknowledgments; regression tests cover that boundary. A pending result is not readiness failure. Apply authenticated control snapshots and their immediate tick in one GLib callback, so a stale queued draw cannot run between authority revocation and replacement. A renderer reports presented only after its corresponding draw acknowledgement, rather than when a texture is merely queued. Application draw evidence still does not establish panel scanout or photon timing; physical measurements remain separate.

Resource accounting includes all resident textures, current and replacement decoders, both Outputs, overlays and reveal. Start qualification at two 1080-class Outputs on a Pi 5 with 8 GiB RAM and active cooling. A four-slot recording profile is not a physical budget. Pi 5 supports dual HDMI and GLES, but **its H.264 decode is software**, so CPU load, dropped frames, upload bandwidth and thermal behaviour must be measured with the complete workload. Do not claim four simultaneous videos or dual 4K performance from connector specifications. [Pi 5 specifications](https://www.raspberrypi.com/products/raspberry-pi-5/), [Pi engineering explanation](https://www.raspberrypi.com/news/optimising-raspberry-pi-5s-software-environment/).

## Two Outputs and kiosk supervision

Run Weston 13 with its DRM backend and `kiosk-shell.so`, black background, no desktop shell, display manager or login/getty on presentation VTs. Disable screen blanking; hide the cursor and suppress splash/console output where supported. Keep both GTK windows and Weston alive across Scenes; switching assignments only changes renderer state. A Player process restart exposes the compositor's black background while fresh authority is established, rather than a Linux desktop.

Give each realized Wayland window its own app ID, using the shared `output_app_id` helper, such as `photo-wall-HDMI-A-1` and `photo-wall-HDMI-A-2`, and map these via each Weston's `[output] app-ids=` setting. GTK 3.24 declares `gdk_wayland_window_set_application_id`; Noble lacks the GdkWayland typelib, so the adapter uses the pinned C API through ctypes. Native Wayland smoke verifies the distinct IDs before each first content buffer; one GtkApplication ID for both windows is insufficient for deterministic placement. Report actual DRM connector identities centrally; do not assume GDK monitor enumeration index is a persistent Output identity. [Weston kiosk placement](https://wayland.pages.freedesktop.org/weston/toc/kiosk-shell.html), [pinned GTK Wayland header](https://raw.githubusercontent.com/GNOME/gtk/3.24.41/gdk/wayland/gdkwaylandwindow.h).

Use dedicated systemd units for the compositor and Player under a non-login account, with logind/seat permissions limited to DRM/input/render nodes. Service restart/watchdog policy must be tested without killing the compositor during ordinary Player recovery. Physical checks must include unplug/replug, both connector orders, portrait calibration and a failed decoder during a transition.

## Common PXE path, state and trust

The supported initial envelope remains an operator-controlled wired PXE LAN and Pi 5 devices with network-capable EEPROM configuration already present. EEPROM network mode is `0x2`; neither changing EEPROM on a fresh device nor running Imager interactively is part of initial Photo Wall registration. Serve the same boot content for all devices. The EEPROM can prefix TFTP paths using its serial; implement and test a server-side prefix-to-common-root mapping, preserving traversal protection. A serial/MAC lookup here is routing metadata, never enrollment authority. Pi 5 requires `config.txt`; use the selected image's Pi 5 kernel/DTB and an explicitly named common initramfs. [Pi bootloader configuration and TFTP prefixes](https://www.raspberrypi.com/documentation/computers/raspberry-pi.html#bootloader-configuration), [Pi boot file configuration](https://www.raspberrypi.com/documentation/computers/configuration.html).

The common initramfs loads a **signed, bounded rootfs SquashFS into RAM**, verifies its length/hash/signature, mounts it read-only with a bounded tmpfs writable overlay, and switches root. Include required onboard Ethernet, squashfs, loop and overlay support before network/root mounting. The full runtime root is neither NFS-dependent nor demand-fetched after boot. Use ordinary kernel+initramfs transfer; do not try to place the complete OS inside firmware `boot.img`, whose documented size ceiling is much smaller. Initramfs hooks and the mount flow require an actual boot test. [Initramfs stages](https://manpages.ubuntu.com/manpages/focal/man7/initramfs-tools.7.html), [Linux OverlayFS](https://www.kernel.org/doc/html/latest/filesystems/overlayfs.html), [firmware boot ramdisk limit](https://github.com/raspberrypi/documentation/blob/master/documentation/asciidoc/computers/config_txt/boot.adoc).

A centrally specified release manifest contains only bounded public artifact names, byte sizes, hashes and a boot ABI; detached signature verification uses the public deployment key embedded in the common bootstrap. No manifest field is shell-evaluated. Establish time from the controlled provisioning network/RTC before HTTPS validation. Missing time/trust fails closed, and no insecure TLS bypass becomes normal recovery. TFTP bootstrap still depends on the accepted trusted-LAN boundary; signing the fetched filesystem does not retroactively authenticate an attacker-replaced EEPROM/TFTP bootstrap.

Use an ext4 `PWSTATE` volume for private generated identity, cache/index/executor journal and cached immutable update artifacts. State must never be embedded in the common image: clear machine ID, logs, SSH keys, cloud-init instance data and all credentials at build time; disable Ubuntu's interactive first-boot account setup. The Player generates its Ed25519 key, persists it atomically with mode 0600, then performs existing nonce/proof enrollment over the pinned central TLS origin. Fresh registration remains unbound; calibration/Frame permission stays central.

Automatic state initialization needs a documented supported-storage policy before implementation: mount an existing Photo Wall-owned volume, or initialize only deployment-authorized factory-empty storage using an explicit common policy. Do not erase arbitrary attached media or treat “no recognizable partition table” as proof that data may be destroyed. A device with unusable persistence should still appear centrally as unbound with a storage fault using a volatile registration attempt; it must not claim stable replacement identity or execution capacity. This failure path requires a small explicit amendment to the persistent-key decision and central health handling, or the supported-device specification must require usable owned state storage. No individualized image or device-local secret entry is acceptable.

## Build artifacts and scoped rollback

Use an isolated Linux arm64 builder. On this host Docker Engine was queried successfully as `linux/arm64 29.1.3`; the host is arm64 macOS. Prefer a disposable VM/libguestfs image-building environment with access only to its own disk files, rather than mounting arbitrary host block devices. Extract/customize the verified Ubuntu server image, install the pinned package closure, install the Player-only locked package, add common public configuration and services, and build a deterministic rootfs SquashFS plus matching Pi boot tree. Rootfs image size and peak RAM must be explicit manifest limits; a provisional 1 GiB compressed ceiling on an 8 GiB Pi needs measurement.

The build interface should take a Git revision, snapshot/package lock, public deployment config and public signing key; release signing consumes a private key from outside Git. Emit outside Git:

- `photo-wall-pi5-<revision>-<config-hash>.img` and its PXE boot tree/rootfs bundle;
- exact rootfs/kernel/initramfs/DTB/file checksums and detached release signature;
- revision/dirty-tree status, build recipe/tool versions, base image identity, public configuration hash, package/version/architecture/hash manifest and Python dependency inventory;
- machine-readable verification and boot reports linked to the produced artifact hashes.

Before publishing, re-open the artifact, verify manifests against its actual contents, verify the Player-only boundary, import GI/GTK/Gst with its own Python and smoke-test decode plus offscreen composition. Freeze apt inputs and dependency wheels in an external build cache. Disable unattended in-place package mutation; updates produce another reviewed image revision.

For the MVP's scoped rollback, keep the Pi bootstrap/kernel/module ABI fixed and replace the immutable userspace/rootfs image. Cache signed A/B candidates on PWSTATE, write a bounded trial record atomically before reboot, and have the common bootstrap select/verify/copy the candidate into RAM. The previous validated image remains cached. The candidate becomes good only after a timed health check covering state persistence, Python/native imports, control reconciliation and required Output initialization. Failure/watchdog/reboot before that mark consumes the attempt and selects the previous image. Reject cross-ABI images in this scoped updater. Kernel/EEPROM upgrades require a separate verified boot fallback design. Inject corrupt signatures, truncated rootfs, failed startup and interrupted trial writes; verify rollback preserves identity/cache and never restores old execution authority.

## Evidence and remaining infrastructure

See [the core benchmark](evidence/2026-09-05-core-benchmark.md) and [native Renderer](module-native-renderer.md) for executed source/download/native evidence. The verified upstream Ubuntu input and software-rendered two-output smoke are not the required Photo Wall artifact or Pi boot evidence. Final image, generic userspace boot and physical boot gates remain open.

`qemu-system-aarch64` and `qemu-img` are absent on the host. QEMU's current official Pi machine list stops at Pi 4 and does not provide Pi 5/RP1/dual-HDMI qualification. A generic arm64 VM may boot the **same rootfs bytes** with a compatible generic test kernel and exercise initramfs/state/update/network faults. Label that userspace integration evidence; it cannot satisfy the exact Pi boot-path gate. The checksum-identified Pi artifact still must boot on actual Pi 5 hardware through the documented PXE path. [QEMU supported Pi models and missing devices](https://www.qemu.org/docs/master/system/arm/raspi.html).

The workspace and temporary directory share an APFS volume with approximately **15 GiB free** at inspection. Root subsequently verified approximately **778 GiB free on `/Volumes/Dock`**. Use a new isolated artifact/scratch directory on that external volume, subject to filesystem access and Docker file-sharing setup, rather than treating local free space as a build blocker. Budget at least 25 GiB of dedicated scratch and keep intermediate image copies bounded; do not delete user data to create space. An isolated external artifact directory now holds the verified upstream input and dedicated build scratch; no final Photo Wall image is claimed. A Linux PXE host on the physical broadcast LAN, two Pi 5 Players, two panels attached to one Pi, a panel on the second, controllable power/serial logs and visual capture remain unavailable. Docker Desktop localhost networking is not evidence of DHCP/TFTP reachability on that LAN.

Accepted module work and remaining gates: (1) Player-only packaging plus Noble native import/GLArea smoke environment; (2) native Renderer with deterministic shader/reference and async-present tests; (3) common image/bootstrap builder and artifact verifier; (4) signed userspace A/B update harness; (5) exact-artifact Pi boot/PXE/dual-output qualification when the bench is supplied. Each needs independent upward review and executed evidence. Native implementation has its own verified module evidence; packaging/build/boot and physical qualification remain tracked separately.
