# Isolated appliance boot fixture

Status: isolated HTTPS/DNS/NTP service integration passed, 2026-09-05; the first generic VM reached the signed root but failed service startup. This fixture supplies a signed common release, central HTTPS, DNS and test time to a generic ARM64 VM. It is not a production PXE server or physical Pi qualification. The image/bootstrap contract owns verification and mount behavior; the fixture supplies only its explicitly configured inputs.

Run a dedicated central instance with an isolated test database and no public host ports. The existing central application keeps its own lifespan, migrations, enrollment and scheduler. An added `/appliance/{filename}` route exposes exactly the canonical release manifest, detached signature and digest-named rootfs from one read-only public bundle. Before serving, verify the signature, public-configuration hash, exact rootfs size/hash and nonsymlink file boundary. No directory listing, private configuration, arbitrary path or unrelated file is exposed. Use the ordinary Uvicorn TLS support with the fixture's server certificate/key in a separate private volume; those private files never enter image-builder context or the appliance.

The task-only Docker network gives the TLS service the common public hostname `photo-wall.test`. A small synthetic NTP responder shares its network namespace and serves host UTC solely for the VM test. It accepts bounded client packets and returns fixed-size replies; it never adjusts host time. QEMU user networking supplies guest DHCP and forwards DNS through the fixture network. The VM may use a compatible generic test kernel with the exact signed rootfs bytes; record that kernel substitution explicitly. No DHCP/TFTP broadcast-LAN or Pi firmware/HDMI result follows from this path.

Generated fixture credentials, TLS keys, database configuration, public artifact copies and VM state remain outside Git in marked task-only directories/volumes. Cleanup removes only that fixture's recorded resources. Acceptance must record the release/rootfs/configuration identities, actual served TLS verification, VM boot identity and central enrollment when observed. Network time, signed disk boot, signed network fallback, state/update faults and physical PXE remain distinct claims.

Recurring inventory, release and media probes run in a separately bounded observer container using the same pinned derived image and helper source inventory. Its 0.5 CPU and 192 MiB allowance is separate from Central's unchanged 0.5 CPU and 384 MiB limits. The observer runs as UID 10001 with a read-only root, dropped capabilities, no-new-privileges, a 64-process limit and a 32 MiB non-executable temporary filesystem. It joins only the internal front and database networks, with IP forwarding disabled. It receives the fixture's database/operator credentials and read-only public configuration, without the TLS private key, rootfs bundle, media files or upstream network. Read-only evidence queries observe central decisions; staging and configuration still use authenticated central APIs. Creation and cleanup pin the observer's owned container and derived-image identities in both smoke and full scope.

Central's three-second HTTPS/database healthcheck loads only the Python standard library. Artifact and application imports belong to initialization and the signature-verifying bundle probe, so repeated liveness checks do not rebuild that import graph inside the measured server's CPU allowance. Probe cadence, clock rejection rules, release-health dwell and all acceptance deadlines remain unchanged. This resource boundary does not establish exact-image or hardware acceptance by itself.

The opt-in [Docker regressions](../tests/test_boot_fixture_runtime_docker.py) use `PHOTO_WALL_OBSERVER_TEST_IMAGE` as an immutable local Central image ID and require the pinned PostgreSQL image locally. They check the actual derived health helper without application imports, then exercise the real fixture, authenticated Player time/control loops and central release-health dwell during three-second observer polling. The test client stages and hashes current Player/contracts sources, receives only public configuration, and uses a `RecordingRenderer` with a signed nonbootable payload. Run `.venv/bin/python -m pytest -q tests/test_boot_fixture_runtime_docker.py` with the image variable set. These checks cover the service/observer boundary, not native guest rendering or guest clock discipline.

The ordinary [Player boot-health integration regression](../tests/test_player_boot_health_integration.py) uses real ASGI handlers, authenticated enrollment and PostgreSQL with a controllable clock. Individual retained good/bad RTT and offset measurements enter the actual Player transport receipt boundary. A constructed recurrence proves clock rejection clears central dwell, and recovery requires a fresh uninterrupted 30 seconds. It neither replays a complete hosted trace nor establishes the cause of the hosted timeout.

## Reproduce the isolated services

Supply a finalized signed public bundle, deployment directory containing separate `public/` and `private/` inputs, and the immutable local central image ID. Use a new absolute state directory for each distinct bundle. The harness snapshots and hashes its inputs; changing a running fixture's bundle is refused.

```sh
.venv/bin/python scripts/boot_fixture.py --state "$BOOT_FIXTURE_STATE" prepare \
  --bundle "$SIGNED_BUNDLE" --deployment "$FIXTURE_DEPLOYMENT" \
  --central-image "$CENTRAL_IMAGE_ID"
.venv/bin/python scripts/boot_fixture.py --state "$BOOT_FIXTURE_STATE" up
.venv/bin/python scripts/boot_fixture.py --state "$BOOT_FIXTURE_STATE" probe
.venv/bin/python scripts/boot_fixture.py --state "$BOOT_FIXTURE_STATE" down
```

The selected Docker daemon must already contain the declared central and pinned PostgreSQL images. There are no host port publications or host bind mounts. `up` creates task-labeled internal networks and bounded services, then runs the real TLS/DNS/NTP probe. `report.json` records public identities and results; private state remains outside Git. A probe download uses a bounded disk volume rather than memory proportional to the rootfs. `down` verifies every recorded resource's identity before removing any resource; a replaced or unrelated resource stops cleanup.

The real release was subsequently served and downloaded through the same fixture: release ID `f8322e1329a1dc8e11f66f3c31bb4fa074f9d1638c4dd82b9e8b925bfa78bb60`, rootfs SHA-256 `39dfacd85871c51d81934c45b785f8a3e1cbf8d4d36a1601042e0719a2dcc413`, size 672,448,512 bytes. Its probe passed the same signature, CA/hostname, DNS, database, scheduler and denied-file checks; the measured NTP offset was -0.000138 seconds. The initial `up` attempt and repeat probes failed at the original 192 MiB probe limit; Docker later confirmed exit 137 with `OOMKilled=true`. A bounded 384 MiB retry passed. The corrected harness records this memory limit and bounded exit/OOM diagnostics, without private command output. This is an actual signed payload transfer. The separate [first VM attempt](evidence/2026-09-05-appliance-boot.md) records its partial boot and service failure; no physical Pi boot is claimed.

Independent lifecycle review corrected stale initialization after teardown, interrupted-probe scratch accumulation, private configuration integrity and container image checks. Every probe now replaces its checked scratch volume after removing a stale probe container; only this fresh volume uses image copy-up from a uid/gid 10001-owned mode 0700 directory. Public bundle/configuration volumes remain read-only with copy-up disabled. An actual synthetic-bundle `up → down → up` cycle passed TLS/DNS/NTP, database and scheduler checks after these changes, and final cleanup succeeded. This replay verifies service lifecycle independently of appliance boot.
