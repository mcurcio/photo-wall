# Isolated appliance boot fixture

Status: integration design, 2026-09-05. This fixture supplies a signed common release, central HTTPS, DNS and test time to a generic ARM64 VM. It is not a production PXE server or physical Pi qualification. The image/bootstrap contract owns verification and mount behavior; the fixture supplies only its explicitly configured inputs.

Run a dedicated central instance with an isolated test database and no public host ports. The existing central application keeps its own lifespan, migrations, enrollment and scheduler. An added `/appliance/{filename}` route exposes exactly the canonical release manifest, detached signature and digest-named rootfs from one read-only public bundle. Before serving, verify the signature, public-configuration hash, exact rootfs size/hash and nonsymlink file boundary. No directory listing, private configuration, arbitrary path or unrelated file is exposed. Use the ordinary Uvicorn TLS support with the fixture's server certificate/key in a separate private volume; those private files never enter image-builder context or the appliance.

The task-only Docker network gives the TLS service the common public hostname `photo-wall.test`. A small synthetic NTP responder shares its network namespace and serves host UTC solely for the VM test. It accepts bounded client packets and returns fixed-size replies; it never adjusts host time. QEMU user networking supplies guest DHCP and forwards DNS through the fixture network. The VM may use a compatible generic test kernel with the exact signed rootfs bytes; record that kernel substitution explicitly. No DHCP/TFTP broadcast-LAN or Pi firmware/HDMI result follows from this path.

Generated fixture credentials, TLS keys, database configuration, public artifact copies and VM state remain outside Git in marked task-only directories/volumes. Cleanup removes only that fixture's recorded resources. Acceptance must record the release/rootfs/configuration identities, actual served TLS verification, VM boot identity and central enrollment when observed. Network time, signed disk boot, signed network fallback, state/update faults and physical PXE remain distinct claims.

## Executed component checks

The public bundle adapter passed eight focused tests for exact permitted responses, detached signature/configuration/rootfs integrity, truncation and symlink rejection. The NTP helper passed eight focused tests, including a real loopback UDP exchange, oversized datagram rejection and SIGTERM shutdown. Review corrected two packet-boundary issues: receive one byte beyond the maximum to detect truncation, and report the fixture clock's leap status independently of an unsynchronized client's flag. Scoped Ruff and documentation link checks passed.

On 2026-09-05 at 23:46 UTC, the customized Ubuntu root's actual chronyd 4.5 successfully queried the isolated helper over Docker networking. It ran as root in query-only mode (`chronyd -Q -d -u root -t 15 'server ADDRESS iburst'`), with no clock-setting capability and the builder volume mounted read-only. It reported a 0.000030-second offset, explicitly ignored it and exited zero after 6.769 seconds. This checks interoperability with the appliance binary, using a numeric address; it does not establish DNS, DHCP, clock adjustment or boot. The [chronyd 4.5 manual](https://chrony-project.org/doc/4.5/chronyd.html) defines `-Q` as measuring the offset without correcting the clock. The temporary client, responder and isolated network were removed. An earlier fixture startup failed because Docker refuses copying a script into a read-only container root; the successful probe supplied the public script in memory.

The signed synthetic payload used to qualify TLS serving is explicitly nonbootable; it must never be cited as an appliance image.
