# Original-to-variant preparation

Status: implementation contract, 2026-09-05; executable and physical qualification results must be recorded separately. This leaf implements the preparation responsibility in [the media module](module-media.md) and preserves [the central media boundary](requirements.md#central-media-boundary). It neither selects assets nor authorizes execution.

## Interface and ownership

`media/prepare.py` owns one recipe per kind since the render redesign ([0029](decisions/0029-render-planes.md)), so a change to how videos are encoded never renames a photo's copy: `StillRecipe` (version 3 since the photo follow-ups of 2026-10-11: HEIC, AVIF and wide colour; version 2 came with delivery [4](roadmap.md#4-real-photo-sources)) and `VideoRecipe` (version 4: HEVC; 1 to 3 were the one recipe both kinds shared, H.264), `PreparationRecipe` their union by `kind`, `HouseRecipes` (the recipes prepared by now, one per kind) and `stored_recipe` (the one reader of a stored recipe; a recipe the current models refuse answers None, so an old variant's name fails `variant_inputs_unknown`), `STILL_MEDIA_TYPES` and `STILL_FORMATS` (the one home of "Photo Wall can read this file": the rendition choice and the Immich client read them), `PreparationLimits` (the one home of the size bounds; the Immich client's fetch reads its defaults from it), `BuildIdentity`, `PreparedMedia`, and `Preparer`. The photo it prepares is a pool photo, `LibraryAsset` ([central/photo_library/model.py](../central/photo_library/model.py)), with the file the worker fetched for it, `FetchedRendition` ([media/library_client.py](../media/library_client.py)); `Variant` remains in [contracts/models.py](../contracts/models.py). The central composition owns dependency pins, PostgreSQL, Procrastinate task execution, blob publication/references, and the gateway. This leaf owns only preparation code, its tests, and this document.

`Preparer(ffmpeg="ffmpeg", ffprobe="ffprobe", *, recipes=HouseRecipes(), limits=PreparationLimits(), clock=SystemClock())` accepts trusted executable locations and an injected Clock. `await prepare_rendition(asset, rendition, destination: Path) -> PreparedMedia` accepts a pool photo, the **copy** the worker fetched for it (Immich's preview when it holds every Frame output, else the edited full-size copy or the original; a video's original; which one, and when, is the [media module's](module-media.md#original-validation-and-preparation-recipe)), and a private, absent staging destination. The result contains `path`, an exact `variant`, `original_sha256`, a deterministic `recipe_id`, `build: BuildIdentity`, and `made_from` (the copy it was made from, written to `media_jobs.made_from`). It establishes validated bytes, not a Player's playback readiness, capacity, authority, or observed presentation. Expected failures use the existing bounded `MediaError` codes; no raw file names, EXIF, subprocess stderr, or input content enters returned errors.

`await describe_recipe() -> tuple[str, BuildIdentity]` exposes the same bounded inspection and canonical hash calculation used by `prepare`. The worker registers this recipe before selecting or enqueuing jobs and requires `result.recipe_id == lease.recipe_id` before publication. Serialize the build with `build.model_dump(mode="json")`; restore with `BuildIdentity.model_validate`. The recipe digest covers sorted compact JSON containing `recipe` (the recipe model), `threads` (the configured encoder thread count), and `build` (the complete build model). The worker must call this API instead of deriving a second identity. Executable and preparation-source bytes are rehashed before reusing cached inspection and after conversion; a mid-conversion change fails with `preparation_build_changed`. Installed code, Python, linked libraries, and Pillow must remain immutable for a worker process lifetime, with process restart on deployment changes.

The parent worker reserves the original plus the maximum derivative against central aggregate quota before calling preparation. Preparation independently checks the original size, staging bound, and per-output cap. It never downloads, copies an entire source query, retries, edits an original, changes a Frame, or publishes a PostgreSQL ready row. A worker publishes the returned file by its digest using the media repository contract.

## Checks before conversion

Read only regular nonsymlink files, bound size, and verify the fetched file's own SHA-256 and size against the `FetchedRendition` the download measured (`asset_integrity` otherwise). Immich's checksum is of the original, never of the rendition, so it is not compared. A video whose measured duration differs from the pool's by more than 0.15 s fails with `metadata_mismatch` before encoding. The caller supplies only private staging paths; original filenames and upstream paths are never used to choose destinations. Exclusively create the destination and leave an existing file/symlink untouched. A failed conversion removes its own output; failed cleanup keeps the caller's reservation accounted.

Pillow 12.3.0 is the still metadata/decoder inspector, with pillow-heif 1.8.0 (libheif 1.23.4) registered for HEIC/HEIF and Pillow's own libavif for AVIF (owner, 2026-10-11: "lean on strong foundational libraries"). Run it in a separate process with memory/CPU/file/output/time bounds because native decode cannot be safely cancelled by abandoning a Python thread. Restrict accepted formats to opaque JPEG/PNG/WEBP/HEIF/AVIF (8-bit as decoded), verify a complete decode, and reject animation/alpha/CMYK. The size and EXIF orientation 1–8 are the fetched file's own: a preview is already upright, a JPEG full-size copy may carry EXIF, and libheif applies a HEIC's own turn on decode. A PNG's IHDR bit depth is inspected explicitly because Pillow may expose 16-bit truecolor data through an 8-bit RGB mode. Reject PNG HDR signaling (`cICP`, `mDCv`, `cLLi`) and a PQ or HLG transfer: a HEIC's or AVIF's `nclx` colour box (read from its `meta` box) or an ICC profile's `cicp` tag. A JPEG gain-map photo (Ultra HDR, Apple's adaptive HDR) is read as its base image. Check EXIF color-space, PNG gamma/chromaticity, and ICC data rather than inferring color from a filename.

Still color policy accepts untagged ordinary 8-bit sRGB under the declared initial convention. A supplied ICC profile must be valid RGB; it is sRGB when it maps a fixed dense RGB/gray test grid to sRGB through LittleCMS with at most two 8-bit code values of difference, and any other RGB profile (Display P3, Adobe RGB) is **converted** to sRGB by LittleCMS with the perceptual intent. Profile names are not authority. A HEIC or AVIF with no ICC profile must name BT.709 or unspecified primaries. Conflicting PNG gamma/chromaticity and PQ/HLG are rejected; no tone mapping is claimed.

A HEIC, an AVIF, or a still whose profile is converted reaches FFmpeg as **one lossless PNG intermediate** (FFmpeg reads only JPEG, PNG and WebP here): the bounded inspector decodes it, applies its orientation and the conversion, and writes upright sRGB pixels with no metadata to `<destination>.png` in the job's private staging directory (file limit: the staging budget). The intermediate is inspected again (PNG, orientation 1, sRGB) and always removed. Plain sRGB JPEG, PNG and WebP keep the direct path. The inspector emits bounded normalized facts only. Pillow/LittleCMS metadata behavior is grounded in [Image](https://pillow.readthedocs.io/en/stable/reference/Image.html), [ImageCms](https://pillow.readthedocs.io/en/stable/reference/ImageCms.html), and [tagged PNG parsing](https://github.com/python-pillow/Pillow/blob/12.3.0/src/PIL/PngImagePlugin.py).

FFprobe inspects MP4/MOV containing exactly one H.264 or HEVC video stream. Audio may exist in the input and is discarded; no audio/subtitle/data stream appears in the derivative. Reject invalid or excessive dimensions/duration, unsupported color transfer/primaries, HDR/Dolby Vision signaling, and nonorthogonal display matrices. Normalize supported original sample-aspect ratio and rotation into upright square-pixel output while preserving display aspect ratio. Original pixel quality remains based on the original raster, so resampling never makes a low-quality original eligible. Untagged ordinary HD video uses the declared BT.709 convention; tagged conflicting/unsupported color is rejected. This initial scope assumes static stream color metadata; broader changing-color formats require qualification. [FFprobe](https://ffmpeg.org/ffprobe.html), [FFmpeg options](https://ffmpeg.org/ffmpeg.html).

## Encoding and validation

Disable automatic rotation and apply the validated original transform exactly once. All eight still EXIF transforms follow the mapping in [the media design](module-media.md#original-validation-and-preparation-recipe). Remove residual orientation and inherited private metadata. Keep calibration/cropping/Frame placement in the Renderer; media preparation does not bake them into the original or derivative. Since delivery 5a every photo is cropped to fill its Frame, and the crop still happens only on the Player: Central chooses it ([`Layer.crop`](execution-contract.md#what-a-frame-shows-its-crop-and-when-a-photo-is-on-screen)) and preparation only scales (owner, 2026-10-11: "we only ever scale those images — never anything that would change the proportions like crop — because crop happens directly on the Player"). One derivative therefore serves every Frame and every crop.

The default JPEG recipe uses a maximum 3,840-pixel long edge, no upscaling, fixed quality, and a single sRGB image. The video recipe makes one copy per video (owner, gate answer Q5, 2026-10-18: "HEVC now, one 1080p copy per video"; in chat: "1080p at 30 is fine"): it preserves aspect ratio within a 1,920-pixel long edge and 2,073,600 pixels, uses even dimensions/SAR 1, caps 30 fps, and encodes silent HEVC Main (8-bit 4:2:0) level 4.1, Main tier, BT.709 limited range, in an `hvc1` MP4 with faststart, with libx265: what the Pi 5's hardware decoder plays (H.264 decodes only on its CPU). Defaults use CRF 24 (x265's scale: more bits than its default 28, because a 1080p copy is shown on 4K Frames), medium preset, and a two-second GOP. x265 gets `PreparationLimits.video_threads` (default 4) threads and the encode a CPU limit of `cpu_seconds` times that, so a video's preparation keeps about the reach the H.264 encode had; a video longer than the budget allows fails `preparation_timeout` (an open finding: the budget is flat, well under `max_video_seconds`). The output check refuses any copy that is not `hevc`/`hvc1`. A video's copy is named by the video recipe alone, never by the photo copy ladder. These are conversion settings, not Pi capacity guarantees. The 3,840-pixel long edge is not judged against a crop: [the photo fit rule](module-planner.md#the-photo-fit-rule)'s pixel floor is judged on the original, so a wide panorama prepared at 3,840 pixels can show its window at fewer pixels than a 4K Frame has (not addressed in 5a). The Planner still checks derivative compatibility; a derivative below its required quality floor cannot authorize an unsuitable presentation.

Reprobe and fully decode the result; verify its dimensions, upright orientation, stream count, codec/profile, duration/rate bounds, color tags, and exact byte cap. JPEG has no duration; video has a measured positive duration. Compute the immutable output SHA-256 and fsync before returning its `Variant`. Do not return output on a timeout, partial decode, exceeded limit, or mismatched probe.

Recipe identity covers every conversion setting plus preparation-module/executable SHA-256, executable version/configuration output, the Python/Pillow/LittleCMS/libheif/JPEG/zlib inspector versions, and platform identity. A changed build/settings combination has a new recipe identity. Production package/image manifests are still required alongside this fingerprint; a host executable fingerprint does not establish a reproducible Linux appliance build.

## Process and byte bounds

One preparation call has a 180-second wall deadline. Probe/inspector calls have shorter 15-second deadlines. Original bytes are capped at 256 MiB, original dimensions at 16,384 per edge/64 million pixels, video at 300 seconds, JPEG output at 16 MiB, MP4 output at 256 MiB, and original-plus-output staging at 512 MiB by default. Settings are validated finite positive values. Standard output/error are drained concurrently with a 64 KiB bound each; an overproducing tool fails and is killed rather than filling memory or blocking forever.

Use argument arrays without a shell and a fresh process group. A small internal launcher sets resource limits in its own process before running the inspector or executing a trusted FFmpeg/ffprobe binary; avoid `preexec_fn` inside a threaded Python worker. Apply CPU and output-file limits. Linux additionally applies an address-space limit; macOS tests do not claim that Linux memory enforcement was qualified. The deployed worker must also have a read-only runtime filesystem, private staging volume, and container memory/CPU limits. No media-supplied protocol is enabled: input protocols are local files only and allowed demuxers are narrow JPEG/PNG/MOV handlers. Never accept a filter graph or executable argument from source metadata.

Deadline/cancellation/output overflow kills and reaps the whole process group before deleting staging output. A native decoder error is returned as a bounded preparation failure. An explicit clock check supplements asyncio deadlines so fault simulation can detect clock expiry; a stationary fake clock cannot disable the real process deadline.

The preparation failure vocabulary is `preparation_tool_missing`, `preparation_build_changed`, `preparation_timeout`, `preparation_io`, `preparation_limit`, `preparation_invalid`, `unsupported_media`, `unsupported_color`, `metadata_mismatch`, `asset_integrity`, `destination_exists`, `staging_cleanup`, and `clock_invalid`. Unsupported profiles, limits, malformed decodes, and metadata disagreement are incompatible results; I/O, deadline, integrity, build-change, clock, and cleanup errors are unavailable results. The media domain classifies permanent versus retryable results; Procrastinate owns retry scheduling. Cancellation propagates after process reaping and staging cleanup; it is not converted into a successful or empty result.
