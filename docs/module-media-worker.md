# Central media worker

Status: implementation contract, 2026-09-05. The worker connects [source/job metadata](module-media.md), [preparation](module-media-preparation.md), and [durable storage](module-media-store.md). It owns execution of requested acquisition and refresh work, not source selection, scheduling, Player authority, or gateway delivery.

## Configuration and interfaces

`load_connections(path) -> dict[str, ConnectionConfig]` reads a private JSON document with `schema: 1` and at most 128 `connections`. The file must be a nonsymlink regular file owned by the executing user with mode 0600, no larger than 1 MiB. Duplicate keys/IDs, nonfinite JSON, changed files, and unknown fields fail with bounded codes. The existing ConnectionConfig validates owner UUID, trusted API base, TLS/HTTP policy, and runtime secret. Credentials remain only in this process and adapter memory; diagnostics never include file contents, connection IDs, URLs, tokens, or raw exceptions. Updating the private configuration restarts the worker.

`MediaWorker(repository, store, connections, *, preparer=None, client_factory=None, limits=WorkerLimits())` accepts injected adapters/preparation for fault tests. `await run(max_cycles=None, stop=None) -> WorkerReport` owns the exclusive store writer lock for its complete lifetime. Finite cycles are job polling cycles; source refresh and heartbeat continue independently during a long download or conversion. The central scheduler alone enqueues acquisition requests.

The worker registers `Preparer.describe_recipe()` before selecting jobs and checks each result against the leased recipe before publication. One due source refresh runs at a time, independently of the single active acquisition. Refresh uses a 65-second outer deadline within the repository's 90-second refresh lease; the adapter keeps its own tighter bounds. Heartbeat runs every 10 seconds. One acquisition claims an existing full reservation, creates its private staging paths, downloads the exact original, prepares it, then publishes through MediaStore. No database transaction spans upstream I/O or native preparation.

## Failure, pressure, and shutdown

Each job attempt has a 330-second outer deadline, with the adapter's 120-second and preparer's 180-second limits inside it. Default job leases last 600 seconds; configuration requires at least 30 seconds between the outer job deadline and the lease bound. Source refresh and heartbeat use separate tasks so acquisition does not starve them. Blocking store/repository calls run in awaited threads; cancellation waits for an in-flight blocking operation to finish before releasing the writer lock. A stale attempt cannot publish or overwrite a newer attempt during failure cleanup.

Original integrity, oversize, invalid metadata, and unsupported/invalid preparation profile failures are permanent for that original and recipe. Permission, source availability, schema/version, deletion/change, local I/O, and other operational failures retry after 5, 15, then at most 60 seconds according to the persisted attempt count. Each retry is a separate lease and finite operation, never an immediate recursive retry. Permanent failure and retry cooldown remain visible to the Planner through the repository. A new original or preparation recipe gets its own job.

On storage pressure, collect unreferenced cache to `max(0, quota - worst_original_and_derivative_reservation)` and try claiming once more. Referenced blobs and failed-cleanup accounting remain protected. A collected ready job becomes `evicted` and stays dormant until the scheduler explicitly requests it again, subject to the active-job cap; historical result metadata never grants readiness. Maintenance recovery runs only between jobs, when no acquisition or native process is active. Recovery is retried after cleanup faults and periodically for pending local cleanup.

Cancellation first waits for the adapter/preparer to cancel and reap their work, then records `worker_cancelled` with a short retry if the same attempt still owns the job. It cancels and joins background tasks, closes every opened adapter, and releases the writer lock last. Normal stop and finite-cycle completion use the same cleanup boundary. Expected output is a bounded WorkerReport of counts and codes, with no private configuration.

The command entrypoint is `python -m media.worker`; it reads `PHOTO_WALL_DATABASE_URL`, `PHOTO_WALL_MEDIA_ROOT`, and `PHOTO_WALL_CONNECTIONS_FILE` and applies the shared database migrations before starting. `--once` or `--cycles N` makes polling finite. SIGINT/SIGTERM request graceful cancellation. Container/image/package setup and the gateway remain orchestrator-owned integration work.

## Acceptance evidence

On 2026-09-05, the combined worker, store, and repository command passed 83 tests against real PostgreSQL and local files: `.venv/bin/python scripts/test_local.py -q tests/test_media_worker.py tests/test_media_store.py tests/test_media_repository.py`. Coverage includes valid/private configuration and malformed/oversized/nonprivate/symlink rejection, publication with generated bytes and injected adapters, concurrent refresh/heartbeat during a held job, typed permanent versus delayed retry policy, pressure with pinned bytes, dormant eviction and bounded explicit requeue, recipe drift, cancellation after partial download/preparation and during a database claim, stale-attempt cleanup refusal, bounded adapter close, nonfinite clocks, finite loops, and restart lock reacquisition. Generated byte fixtures test orchestration and storage; native conversion and real Immich behavior retain their separate evidence.
