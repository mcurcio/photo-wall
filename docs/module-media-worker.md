# Central media worker

Status: Procrastinate-backed central worker implementation. It connects [the photo library and preparation design](module-media.md), [preparation](module-media-preparation.md), and [media variants and their cache](module-media.md#the-asset-tables). PostgreSQL and the task queue are central-only dependencies. Delivery [4](roadmap.md#4-real-photo-sources) (pull request [#81](https://github.com/mcurcio/photo-wall/pull/81)) replaced its Source refresh, unsaved-Source preview, tag-list tick and connections file with connection checks and pool checks against connections kept in Central's database.

## Boundary and queue ownership

Preparing a photo is not a media-queue task. Coordination publishes a `PrepareMedia` job (kernel job `media_variant.prepare`, `central/kernel/job_types.py`) for each variant the Planner's plan needs, and the AssetReader publishes the same job when a Player's read misses; every worker process runs the kernel job runtime, whose `MediaMaker` handler (`media/media_maker.py`) makes the variant ([preparation](module-media.md#original-validation-and-preparation-recipe)). The job's record and the request commit together in the runtime's own transaction; production has no in-process fallback queue and no second polling dispatcher.

Procrastinate owns dispatch, its worker heartbeat state, task attempts, retry timing, queueing locks, and stalled-job detection. Photo Wall adds one task on top: the [media queue's rescue](#the-media-queues-rescue), because Procrastinate detects a dead worker's job but never frees the lock it holds. Preparation is the kernel job runtime's: a variant's record carries its state, a file is never overwritten, and a retry never grants media readiness by itself.

The worker app uses queue `photo-wall-media`. Maintenance runs under `photo-wall-media-storage`, so one pass runs at a time while independent tasks stay concurrent. A variant's job is keyed by the variant's name, so duplicate requests converge. A connection check runs under `photo-wall-library-connection:<connection_ref>` and a pool check step under `photo-wall-library-pool:<pool_key>`, each as both lock and queueing lock: one step per connection or pool runs at a time, a queued duplicate coalesces, and independent pools do not block each other. Periodic ticks use their queueing lock to coalesce pending ticks and have no execution lock. The default worker concurrency is four.

## Connection and pool checks

The worker reads Immich only through `LibraryChecks` (`media/library_checks.py`), built at entry from the photo library store (`PgPhotoLibrary`), a client factory (`ImmichClient.for_connection`) and the clock. One rule decides when a client is reused: `LibraryClients` (`media/library_clients.py`) keeps one client per connection and reuses it while the connection's address and key are unchanged; the checks, preparation (`MediaWorker`) and the thumbnail origin all use it. A corrected address or a new key gets a new client at its next use: **changing a connection needs no restart.** What a check reads and decides is the [media module's](module-media.md#live-discovery-pagination-and-metadata); this section is how the worker runs it.

- **The tick.** The 30-second periodic task (`photo_wall.media.refresh`) calls `LibraryChecks.tick`, which queues a contact for every due connection (`due_contacts`: 15 minutes since its last contact started, by the database clock; a cut-over row with no key is never due) and a check step for every due pool (`due_pools`: wanted, its connection has a key, and either not checking and 15 minutes since its last check finished, never checked or a check requested; or **checking with no step begun for 15 minutes**, `policy.STALE_CHECK_SECONDS`, by the database clock). The second half is the staleness rule: a step lost with its worker never leaves a pool checking, because the tick resumes the check from its stored progress.
- **A contact** (`photo_wall.library.check_connection`, argument `connection_ref` only). `begin_contact` hands out the next contact number and the connection's secret; the client contacts Immich; `record_contact` applies the result only when its number is newer than the last applied one. After a passing contact the worker lists albums, people, places and tags and stores each with `record_list`; one list's failure is recorded beside that list only.
- **A check step** (`photo_wall.library.check_pool`, argument `pool_key` only). `begin_check` returns a lease (None for an unwanted pool) that starts the next check or resumes the running one with its stored progress; the worker does **one** bounded Immich request (up to N, one exclusion page or one include page), then `record_step`, which writes the step's rows and marks and queues the next step in the same transaction, or `finish_check`. A connection failure finishes the check as failed (`connection`), a deleted album, person or tag as failed (`chosen_item_gone`), more than 1,000 photos at one instant as incomplete; a complete finish removes the rows the check marked, and a step of the Re-check phase asks Immich about one row the walk did not see (`LibraryChecks._recheck`, `still_matches`) and removes it only if Immich no longer answers it. A failure in that step raises before anything is recorded, so it removes nothing.
- **Who asks.** Central queues a contact when a connection is added or changed and on Check now, and a check when a draft is made or its query changes, on Save and on Check now. A queued request coalesces with one already queued; a running step is fenced by its check number, so a newer check makes an older one's late step a no-op.

Each step and each contact is its own task, so a big first check is many short tasks rather than one long one, and a worker restart, or the staleness rule, resumes from the stored progress. No database transaction spans upstream I/O. Photos play from the first page: the Planner reads what a pool holds, whether or not its check has completed.

<a id="library-tag-lists"></a>

Lists replace the old tag-list tick: they are re-read with each passing contact (every 15 minutes; tags were every 5 before delivery 4), stored one row per item with no cap, and read by Central's list routes only from the store.

## Key content

Smart crop (delivery [5a](roadmap.md#5a-photo-fit-and-order)) needs to know what each photo holds. Its **key content** is the faces Immich found, each kept whole, and an **interest grid**, a coarse map of where the eye goes (16 columns, rows by the photo's aspect, weights summing to 1). It is measured once per photo revision and analysis version, never per Frame: [the photo fit rule](module-planner.md#the-photo-fit-rule) judges it against each Frame at planning time.

- **Who asks.** The Planner lists the unmeasured photos its Scene lines rank first (`Projection.measurements`, at most 64 per pass); Central's scheduler passes them to `MediaRepository.request_measurements`, and `PgKeyContent.request_in` queues `photo_wall.media.measure` for each photo with a revision row and no current measurement. The queueing lock `photo-wall-measure:<asset_id>` coalesces a repeat; the task has no execution lock, so measurements run beside preparation.
- **The task.** `MediaWorker.measure(asset_id)` reads the photo's connection and, within 30 s (`WorkerLimits.measure_seconds`), asks Immich for its faces (`GET faces?id=<asset id>`, permission `face.read`) and its small thumbnail (the one delivery 4 already fetches), then measures off the event loop (`media/key_content.py` `measure`). Faces become fractions of the size Immich measured them on, so they hold on any scaled copy; each box is kept as Immich found it (clamped to the photo; a degenerate box is left out). The interest grid is OpenCV's static saliency (spectral residual, Hou and Zhang): only the map's salience above its mean counts (the method marks an object where its map passes its mean), summed into the grid and normalised; a map with nothing above its mean gives an even grid. The map's **spread** (its highest value less its lowest) is stored beside the grid. A very tall photo's rows stop at 64. No tuning value is applied here: the room kept around a face, the smallest face that counts and the spread below which a photo counts as even are [photo fit settings](module-planner.md#the-photo-fit-rule), applied when a photo is judged, so changing one needs no new measurement (follow-ups 2026-10-11; `ANALYSIS_VERSION` "2").
- **Results.** A measurement is stored in `photo_key_content` (migration 082): one row per photo, replaced by a new measurement, deleted with the photo's revision row. An image that does not decode records `failed/decode`, a timeout `failed/timeout`; a thumbnail Immich cannot give at this revision (too large, an unsupported type, a refused permission) also records `failed/decode`, while one Immich is only not ready to give is retried; a failed photo is not placed and is measured again after an hour (`MEASURE_RETRY_SECONDS`). Immich unreachable is a retryable task failure and records nothing. A key without `face.read` (Immich answers 403) gives no faces.
- **Without face detection.** When Immich's face detection is off (`server/features`), every photo has no faces and crops ignore faces; the connection shows the `no_face_detection` note ([media module](module-media.md#connections-and-health)). Owner, 2026-10-11: "If immich face detection is unavailable, then smart crop doesn’t take into account faces."
- **Versions.** A row at an older analysis version is still read (the wall keeps its content) and is measured again as the Planner asks, so changing a measurement constant bumps `ANALYSIS_VERSION` and re-measures every photo without blanking a Frame.
- **Faces found late.** Immich detects faces in a background job after the upload, so a photo's first measurement that found no face is measured once more after `FACELESS_REMEASURE_SECONDS` (6 hours, a placeholder); that measurement is final.
- **Immich never answers.** On the queue's last attempt a failure that would be retried (Immich out of reach, a thumbnail not ready) is recorded as `timeout`, so the photo leaves the Planner's requests until its retry (an hour) and the photos ranked after it are measured. Changing a fit constant re-measures nothing. Faces come from Immich 2.5.x; from 3.x only `/faces` carries boxes.

A brand-new pool shows nothing new for the seconds its photos take to measure and prepare; Frames keep what they show meanwhile. Each measurement is one Immich face request plus one thumbnail.

## One media clock

Every media time that another process compares (Central, or another worker process) is stamped and compared on the database clock, read on the connection the transaction already holds: `TransactionClock.now_in(conn)` (`central/db.py`), whose production implementation, `DatabaseTransactionClock`, runs `clock_timestamp()` on that connection and cannot hold a pool of its own. Central and every worker process compose it into `MediaRepository` (`times=`, required) and into `PgPhotoLibrary` (`times=`). It covers the worker's check-in, the media-library job and variant writes, the catalog retry cooldown, a contact's start and the health's `checked_at` and `since`, a check's start and finish and every "due" judgement, a list's `checked_at`/`observed_at`, and a draft's age; the worker container's healthcheck (`media.healthcheck`) ages the check-in with `MediaRepository.worker_age()`, which reads `worker_seen` and `now_in(conn)` in one plain read transaction (no settings insert, no media lock) and is composed by the same `build_repository(dsn)` as the worker entry; its freshness window (`WORKER_FRESH_SECONDS`, 660 s, equal to the console's worker-quiet window) follows the worker's guaranteed check-in cadence, which is boot (recipe registration) and every maintenance pass ([runbook](runbook.md#local-launch)); the operator console ages media facts against the media read's own `read_at`. Relative dates in a Photo source ("last 3 years") are counted back on the house calendar at the start of each check (`media/pool_check.py`): the check's lease carries the house zone (`central/infra/house_store.py` `house_time_in`, read in the lease's transaction), and "last 1 month" from 12 Oct 23:30 house time starts at 12 Sep 23:30 house time (roadmap 2b). The process clock also stays for monotonic budgets and process-local decisions. The worker never reads `media_references.expires_at`: Central writes it (Runtime layer ends, transfer grants) and only Central expires it, on its own clock (the coordinator's `expire_pins_in` every pass, a read lease's close), so storage collection treats any reference row as protecting its blob. If Central stops running coordination passes, pins stay and their blobs are never evicted: safe for playback, at a cost in disk ([console design §42](operator-console-ddd.md#42-backend-gates)).

## Configuration and tasks

The worker has no connections file and no connection environment variable: connections, their keys and their health are rows in Central's database, added in Settings › Photo library ([runbook](runbook.md#connecting-immich), [decision 0020](decisions/0020-immich-key-in-central-database.md)). The key reaches the worker only through the store's worker side (`begin_contact`, `connection_secret`, `begin_check`) and lives in process memory and the client; job arguments carry the connection ref or pool key, never the key, and diagnostics exclude URLs, tokens and raw exceptions. The media-health projection no longer carries connection names (`connection_ids` is gone): the console reads connections from `/v1/operator/library/connections`.

`MediaWorker.media_maker(...)` composes the `PrepareMedia` handler over the worker's library, its Immich clients and its `Preparer`. `MediaMaker` reads the variant's inputs from its name (`MediaRepository.variant_inputs`: the photo revision, and the recipe and need in `media_recipes`), reads the connection's secret, fetches the smallest copy that holds the need (`fetch_plan`, with the copy sizes it already knows, `copy_sizes()`), records the copies it measured (`record_copies`), prepares the file (`prepare_rendition`) and installs it by digest (`CacheStore.install_by_digest`, never over an existing path); the runtime records the `MediaReady` facts with the outcome ([preparation recipe](module-media.md#original-validation-and-preparation-recipe)). Each pool check writes its in-pool photos into `asset_revisions` with their connection, Immich id and `updatedAt`, so a name always stands for one revision; an unedited photo keeps the asset id it had before delivery 4. No database transaction spans upstream I/O or native preparation. A variant whose file is on disk and whole is not made again.

`media.task_queue.create_worker_app(dsn)` defines these tasks:

- `photo_wall.media.refresh`: every 30 seconds, queue due connection contacts and due pool check steps (`LibraryChecks.tick`).
- `photo_wall.library.check_connection(connection_ref)`: one contact, then the lists after a passing one.
- `photo_wall.library.check_pool(pool_key)`: one bounded step of a pool's check.
- `photo_wall.media.measure(asset_id)`: measure one photo's key content ([key content](#key-content)).
- `photo_wall.media.rescue`: every 30 seconds, [the media queue's rescue](#the-media-queues-rescue).
- `photo_wall.media.maintenance`: every five minutes under the storage lock, sweep the thumbnail directory, check the worker in, keep [the media cache under its budget](#the-media-cache-budget), retire unsaved drafts older than a day, pools nothing wants, and the thumbnail records outside wanted pools (`retire_unwanted`), and sweep their files from `previews/`.

Thumbnail fetches are not media-queue tasks: every worker process also runs the asset layer's job runtime, and its `FetchLibraryThumbnailHandler` (Central's) calls the worker's injected `LibraryThumbnailOrigin` (`media/library_thumbnails.py`), which re-checks that the photo is in a wanted pool, reads the connection's secret, fetches Immich's edited thumbnail and re-encodes it without metadata.

Photo Wall records bounded last-activity/error status when these domain tasks run; it does not maintain an independent liveness loop. Procrastinate's own worker state is the queue-worker liveness source.

The entry point is `python -m media.worker`. It reads `PHOTO_WALL_DATABASE_URL` and the single `PHOTO_WALL_CACHE_ROOT` (optional; baked default `/var/cache/photo-wall`, from which the variants' `media/` subdir is derived as a constant — [decision 0013](decisions/0013-unified-cache-root.md) retired the per-domain `PHOTO_WALL_MEDIA_ROOT`), applies Photo Wall migrations and Procrastinate's versioned schema, creates the cache root's `previews/` subdirectory if an existing volume lacks it (`ensure_previews_directory`), runs maintenance, checks the worker in, then runs the Procrastinate worker. SIGINT/SIGTERM use the task runner's graceful shutdown behavior.

### Storage ownership on shared-storage platforms

The image runs the worker as the baked non-root `wall` user (uid 10001), and the media directory it creates (`ensure_media_directory`, `media/blobs`) is `0700`. Under Compose the `media` volume is seeded from the image's `wall:wall 0700` path, so the worker owns its root and nothing further is needed. On a platform that mounts a pre-existing, differently-owned export over the media root — a Kubernetes NFS PVC root is owned by uid 0 — the worker cannot take ownership of its own storage and would otherwise crash at startup with `media_io`.

The supported shared-storage deployment runs the worker container **as root and lets it drop itself**: the `media-worker` image ships `docker-entrypoint.sh` (installed with `gosu`) that wraps the `python -m media.worker` command, plus two environment variables:

- `PHOTO_WALL_PUID` — worker uid to own storage and run as (default `10001`).
- `PHOTO_WALL_PGID` — worker gid (default `10001`).

The entrypoint is conditional on the container's starting euid:

- **Started as root** (a `securityContext` choice, not a Compose one — e.g. `runAsUser: 0` on the pod): it validates that `PHOTO_WALL_PUID`/`PHOTO_WALL_PGID` are canonical positive decimals (empty, non-numeric, bare `0`, or any leading-zero spelling is refused with a message and a non-zero exit, so a misconfiguration can never silently keep the worker running as root or chown storage to an unintended owner), then (0013) runs `install -d -o "$PUID" -g "$PGID" -m 0700` for each derived cache subdir (`media/`, `apps/`, `os-images/`, `previews/`) under `PHOTO_WALL_CACHE_ROOT`, and drops to that uid via `gosu` before exec'ing the command. The dropped worker now **owns** its cache subdirs (it is the single writer), so the directories it makes are its own and `0700`. This is the path a Kubernetes deployment on shared storage should use.
- **Started non-root** (Compose keeps the baked `USER wall`, `cap_drop:[ALL]`, `no-new-privileges:true`): it execs the command directly with no chown, no gosu, and no new privilege — byte-for-byte the prior behavior.

**A pure non-root + `fsGroup` deployment is not sufficient on its own.** a media root that is root-owned and group-owned is safe only when it carries no OTHER-access bits, but kubelet's `fsGroup` recursively *adds* group access (`g+rwxs`, i.e. `0o2770`) and never *clears* existing OTHER bits. On storage that arrives with OTHER access (a pre-existing export, or a driver/`fsGroupChangePolicy` that leaves the world bits set), a non-root worker can neither tighten the root (it does not own it) nor safely keep variants in it. Starting as root and dropping via the entrypoint sidesteps this entirely: after the chown the worker owns the root and enforces `0700` itself, independent of how the volume arrived.


## The media queue's rescue

A worker killed mid-task leaves its Procrastinate row `doing`, and that row keeps its lock: `photo-wall-media-storage` (every preparation and the maintenance pass) or one connection's or pool's check lock. Nothing else frees it, since the content runtime's own rescue covers only its own queue. `photo_wall.media.rescue` (`media.task_queue.rescue_stalled`) runs every 30 seconds with no lock of its own. For each `doing` job on `photo-wall-media` whose worker has not beaten for 30 seconds (Procrastinate's stalled-worker default), it first queues one copy of the job (same task, arguments, lock and queueing lock; an already queued copy absorbs it), then finishes the stalled row `failed`, which frees the lock. A periodic task's row is only finished, since its schedule queues the next run. So a dead worker's lock is free again within about a minute.

Preparing a variant is not on this queue: the job runtime's own rescue returns a dead worker's `PrepareMedia` job (central/infra/queue_ops.py), and a file the dead worker left half-written is a temp file the media cache budget removes once it is idle past its grace. The rescue here follows the content runtime's order (copy first, then finish) with one difference, written down in its docstring: the copy starts at attempt 0.

## Retry and failure behavior

A `PrepareMedia` job has a 330-second outer deadline (`WorkerLimits.job_seconds`), with tighter adapter and preparation bounds. An original that fails its integrity or size check, invalid metadata, and unsupported preparation results are permanent for that variant (`media_maker.PERMANENT`). Operational failures are retried by the job runtime's delivery with its backoff; nothing recurses and no separate `retry_at` dispatcher exists. A retry never grants media readiness by itself: a variant is ready only when its record carries the `MediaReady` facts and its file is on disk.

## The media cache budget

A variant's file can always be made again from its name, so the cache is ephemeral and correctness never depends on a file being there (follow-up to 5a, slice S5). `MediaCacheBudget` (`central/assets/maintenance.py`) runs on every maintenance pass and keeps `media/blobs` at or under `CacheSettings.media_budget_bytes` (default 4 GiB; `PHOTO_WALL_MEDIA_CACHE_BYTES`, a whole number of bytes):

- **Kept:** every file a live pin holds (an offer, a secured lock, a transfer), by variant name through the record's produced digest.
- **Evicted:** the others, least recently served first (`assets.last_served_at`, the database clock; never served goes first), until the directory fits. A file no record names (a re-make's predecessor) goes first.
- **Grace:** a temp file is removed only once idle past `TEMP_GRACE` and counts against the budget until then; a final file installed within `SERVE_GRACE` (by the cache filesystem's clock, `CLOCK_MARKER`) is spared, because the maker installs before it records and a making just finished has not been served yet.
- **Race-free with a pin:** each unlink runs in a transaction holding the media lock, after re-reading the file's pins. Every pin is written under that lock, so a pin committed first spares the file, and a read granted after finds it gone and re-makes it (the AssetReader's miss).

Between writing a file and measuring it the directory may briefly exceed the budget. The release-file cleaner (`MaintainCacheHandler`) never touches `media/`. If Central stops running coordination passes, pins stay and their files are never evicted: safe for playback, at a cost in disk.

Cancellation waits for adapter/preparer cleanup before the job ends, and a file is placed only by `install_by_digest` after it is whole, so no journal is needed: an interrupted making leaves a temp file the cache budget removes, or an unrecorded file it evicts first.

## Acceptance boundary

Focused tests cover the variant path (follow-up to 5a): `tests/test_frame_media_read_path.py` (a first making served by its name; a secured lock granting its variant; refusals for another Player's media, unknown names and retired Players; a stale epoch answering 401), `tests/test_media_variant_remake.py` (a deleted or corrupt file made again under the same name, a reader keeping the bytes it started on, the Player accepting a re-made copy, a legacy variant served but never made again, the recipe id naming only the recipe values and the need), `tests/test_media_worker.py` and `tests/test_media_repository.py` (variant names and inputs), `tests/test_upgrade_087.py` (migration 087 on a store from before it), `tests/test_cache_maintenance_media.py` (pinned files survive over budget, least recently served go first, temp and just-installed files get a grace period, an evicted file is made again on its next GET, migration 088) and task registration and Procrastinate consumption for the media queue. The check fold is proven pure (`tests/test_pool_check.py`), `LibraryChecks` over a fake client and the fake store (`tests/test_library_checks.py`: phase order, an excluded photo never becoming a row, a failure removing nothing, a miss removed only by the Re-check (`tests/test_pool_recheck.py`), a new key making a new client), the rescue (`tests/test_media_queue.py`), and the fake store and the PostgreSQL store are held to one behaviour suite (`tests/test_library_store_conformance.py`). Against real Immich (the CI `photo-sources` leg): `tests/test_source_filters.py`, `tests/test_source_no_ceiling.py`, `tests/test_preparation_rendition.py`, `tests/test_immich_connection.py` (a worker started before the connection exists sees it with no restart) and `tests/test_source_preview_matches_plan.py`. Key content (5a): `tests/test_key_content.py` (recorded face answers; thumbnails drawn in the test), `tests/test_key_content_store.py` and `tests/test_media_worker.py` (DB), and `tests/test_immich_faces.py` against real Immich.
