# Pure rolling Planner

Status: implementation contract accepted for the first MVP; its source input became the photo pools in delivery [4](roadmap.md#4-real-photo-sources) (pull request [#81](https://github.com/mcurcio/photo-wall/pull/81)); delivery [5a](roadmap.md#5a-photo-fit-and-order) (pull request [#82](https://github.com/mcurcio/photo-wall/pull/82)) made it plan the whole wall an hour ahead, one photo per Frame, never on two Frames at once; the follow-up to 5a made it read only the top of each Scene's line from the database each pass, never a whole pool (below). This is a central domain module; it does not acquire media, change Runtime, establish readiness, issue execution authority, or call devices. [The time/recovery decision](decisions/0001-mvp-time-recovery-and-module-contracts.md) and [execution contract](execution-contract.md) remain authoritative.

## Inputs, state and output

`project(runtime, now, *, bindings_by_player, lines, authored_candidates, locked_assignments, history, horizon_seconds=300, plan_seconds=PLAN_SECONDS, max_clock_uncertainty=0.1, limits=PlannerLimits()) -> Projection` is stateless; `PLAN_SECONDS` (3,600) is the one home of the plan horizon's default, which coordination's `plan_seconds` also takes. Inputs are current `Runtime`, a finite UTC instant, Player-to-`OutputBinding` sequences, a `SceneLines` reader (`central/wall_plan/order.py`; in production `PgSceneLines` over the photo library's `ScenePoolReader`) that answers, in the coordination transaction, each Source revision's pool key, readiness and emptiness (`sources`) and the top of a Scene's line (`line`, below), so the Planner never loads a pool, asset-reference-to-`Candidate` mappings for authored media, assignment-ID-to-exact-`Layer` locks already accepted by central coordination, and the wall's shown history (`WallHistory`, read by coordination; the Planner never reads it itself). Each pool candidate carries its key content (`Candidate.analysis`: measured, failed, or not measured yet), hydrated from the media worker's measurements. Shared catalog and transport models have their sole definitions in `central/catalog.py` and `contracts/models.py`.

`Projection` names `now`, `horizon_end`, and `valid_until` separately. It returns per-Player `PlayerProposal.layers` (each media layer carrying its crop, [execution contract](execution-contract.md#what-a-frame-shows-its-crop-and-when-a-photo-is-on-screen)), central-only `AcquisitionRequest(asset_id, assignment_ids, earliest_start)` entries, measurement requests (`Projection.measurements`), the whole wall plan (`Projection.plan`, every slot over the plan horizon), central-only asset/assignment selection records (each new placement naming its Scene and pass), and coded diagnostics (each naming, when it is about one Intent, its Scene and Run, and a `reason` where one applies). It does not construct a `Plan`: epoch, revision, commitment, transactionality, current Frame authority and persistent locks remain coordination responsibilities.

A pass never refuses the wall for one Scene. The unit of isolation runs through every phase: each Intent is placed on its own (`add`), each Scene reads its line on its own (`_read_line`; in PostgreSQL inside its own savepoint, `PgSceneLines.line`), and each placed slot builds its layer on its own (`_settle_slot`). Whatever fails in one of them is left out alone, with the diagnostic `intent_refused` naming its Scene, Run and a reason in plain words (a `PlanningError`'s own message, else "Central could not build its showing (<error type>)", never the error's text), and every other Frame is planned as without it; a refused showing is no cue member, so no other Frame's cue waits on it. A budget shortens the plan instead (`plan_shortened`, below). Only inconsistent caller input (a Frame bound twice, a pool keyed by another Source, a non-finite time) raises `PlanningError` from `project`, and a Runtime that cannot settle even `now` within its transition budget raises `RuntimeBudgetExceeded`: an empty plan would withdraw every offered layer, so that pass fails and the offers stand. The wall assignment itself (`plan_wall`) still runs once for the whole wall. Coordination keeps each pass's diagnostics as the planning outcome the operator reads ([coordination](#coordination-and-the-scheduler)).

Runtime gains `timeline(start, end, max_events=10000) -> TimelineCut`: it restores a copy, reconciles the start, and returns settled immutable views at the start and every discrete lifecycle boundary before the end. It never samples at one-second intervals. An explicit transition/event budget includes catch-up and generated descendants, so tiny cycles and excessive child work stop instead of hanging: the answer is then a prefix, the views of every boundary processed in full, with `until` the last of them (the requested end when complete). It never raises for its budget. Timeline projection cannot affect current Runs, admissions, queues or recorded Actuators. Intent retains sampled opacity for current observation and also exposes authored base opacity and fade durations for execution layers.

## Preparation horizon and execution intervals

The configured preparation horizon bounds **assignment start times**, not a Scene's total lifetime. Include a currently active assignment or a future assignment whose true start is strictly before `now + horizon_seconds`; preserve its full half-open natural cycle/outro interval and media origin. A cycle is as long as its Scene says (an hour, a day): the Planner plans any cycle the Scene accepts, from its start or midway through it. The **plan horizon** (`plan_seconds`, an hour from coordination) is longer than the preparation horizon: [the wall plan](#the-wall-plan) chooses photos for every slot up to it, so no photo is placed on one Frame now that another Frame needs later in the hour without the plan seeing both, but only slots inside the preparation horizon become layers.

`valid_until` is the greater of the preparation-horizon end (the cut, when a budget cut the plan earlier) and included complete assignment ends, and can therefore extend by the longest included layer. Ongoing assignments can start before `now`; Players must seek their true cycle media origin. No polling-dependent clipping changes IDs, fade timing, pinned locks, or authorization intervals. The host Plan validator permits a Layer that overlaps Plan validity and still requires its end to be inside the Plan's validity. This distinction is an MVP choice, not a numerical outage guarantee.

Assignment identity hashes Run ID, typed target, phase and original cycle interval. Selection does not participate in that identity: an unsecured assignment may change exact bytes, but a secured lock retains its exact variant/media identity and interval. Root/descendant arbitration metadata can be revised under a new Plan revision and renewed readiness; it is not a content lock. Root admission order and descendant order must both remain represented in per-Player layer stacking. A later descendant of an old background must not overtake a newer independent overlay. Unrelated and actuator-only targets never become implied display commands.

## Eligibility, selection and fallbacks

This module is the single owner of original-media eligibility, through [the photo fit rule](#the-photo-fit-rule) below: a photo goes only on a Frame it fills with its key content kept, judged by the ratio of its sides, never by orientation labels. Videos require the Frame's **Shows videos** (`frames.video`), and originals with fewer than 1080 pixels on their shorter side are excluded on a large Frame (`central/wall_plan/fit.py` `large_frame`, the one home: a Frame whose diagonal, worked out from its physical size, is at least the photo fit setting `large_frame_inches`, default 40; a Frame whose Display states no size counts as large, so "A 720p video must never be assigned to a 40-inch Frame" holds). A large derivative cannot rehabilitate an unsuitable original. Exact variants must have compatible media type and usable video duration; malformed prepared candidates are diagnosed rather than sent to a Player. Authored asset alternatives follow the same checks and stay on their authored Frame/role. Authored candidates are considered in authored order; source candidates are considered only for a dynamic contribution without authored alternatives.

A dynamic contribution's candidate pool is the union of the pools of the Sources it names, in the contribution's order, one candidate per asset ID (the first seen). Each Frame's contribution names its own Sources (Runtime's `source_refs` per target), so one Frame's Sources never mix into another's; the console writes the same Sources on every Frame of a Scene, so for every Scene it makes this is the Scene's pool. The Planner reaches every photo in those pools: no photo is cut by a window or a count (owner, 2026-10-09: "i dont want any limit on the count of a source"), and it reads only the top of each Scene's line each pass, fresh, with capture time and readable size read at query time (follow-up to 5a, design rule 3: only what the plan needs). `_read_lines` asks `SceneLines.line` for the first `slots x hydrate_factor` members (`PlannerLimits.hydrate_factor`, default 4) of each Scene's line, ranked in SQL by the Scene's tier and order, and doubles the batch while every member read is refused for the Frames (`useful_for`), up to the whole line; it reads the next pass's top too when this pass could end in this plan. So a photo the fit rule refuses for every slot never starves the wall, and every photo stays reachable as the line ranks it. Each Scene's line then orders its photos ([order and passes](#order-and-passes)) and [the wall plan](#the-wall-plan) places them on every Frame together. A check's newly confirmed photos enter the next unsecured cycle within the same Run. A source reference denotes an immutable authored query version; new query results remain live data. A pool whose check has not completed, or whose last check failed, still offers what it holds: the last pool keeps playing while Immich is down or the key is rejected (C7), because a pool row is a photo a check confirmed and a check removes photos only when it completes ([media module](module-media.md#live-discovery-pagination-and-metadata)). The diagnostics are `source_missing` (no pool for the reference), `source_not_ready` (no complete check yet and nothing found so far), `source_empty` (a complete check found nothing: truly empty), `no_eligible_candidates` (no photo of the pool fits the Frame), `no_photo_free` (every photo that fits is on another Frame at that time; the Frame keeps its previous photo when it still fits) and `authored_no_eligible_alternative`; `preparation_pending` and `variant_incompatible` are retired, since a slot that cannot use a photo's prepared copy takes another photo. The connection's own health says why a check failed.

`candidate_standing(candidate, target, settings)` is the planner's one per-candidate verdict for an eligible candidate, in its exclusion order: `failed_to_prepare` (a recorded preparation failure; the media repository's candidate hydration also records one for a failed job whose retry is not yet due), `preparing` (no variant yet), `no_compatible_variant` (a variant the Frame cannot use), or `usable`. The line drops `failed_to_prepare`; inside the preparation horizon a slot takes only `usable` candidates, and the wall plan requests acquisition for the `preparing` ones its lines rank first. The operator candidates route serves the same verdict ([authored media](module-authored-media.md)), so no caller restates the variant rule.

A selected eligible candidate without exact prepared bytes creates a bounded central acquisition request and no playback-ready Layer. A missing/empty/error contribution emits no replacement display command and a fallback diagnostic; the executor retains its authorized compatible still or configured local fallback under the recovery policy. The Planner never substitutes a different target or relaxes eligibility. Explicit authored opaque black produces an exact black Layer independently of media availability. Covered contributions remain in proposals for current-state reveal and transparency; only Runtime's target union is not sufficient to create a Layer.

## The photo fit rule

One home: [`central/wall_plan/fit.py`](../central/wall_plan/fit.py) (`judge`, and `shape_fit` for the checks that need only the photo's size). The Planner, the hand-placed authoring check, the operator candidates route and [the fit analysis](#the-fit-analysis) all ask it; the media worker only measures and the Player only draws. The requirement is [requirements › compatibility](requirements.md#live-media-compatibility-and-preparation). The rule judges a Frame as a `FitTarget`, built only by `fit.fit_target` (the Planner, authoring, the Source preview, the fit analysis and the rendition choice all ask it): its **Frame output**, the Frame's Position box on its screen as it hangs in output pixels (owner, 2026-10-11: compatibility "measuring against the Frame output and not the Display"; `contracts.models.frame_output`, read by `central.infra.display_store.frame_outputs_in`), whose ratio is the Frame's shape; whether it shows videos; and its physical size, the box's share of its Display's EDID size (`contracts.models.frame_size_mm`; None when the Display states none). Nothing else gives a Frame a shape: there is no Frame profile ([0030](decisions/0030-frame-box.md); owner, 2026-10-19: "diagonal inches is a weird concept when we already have width and height"). **No Frame output, no photos:** a Frame whose screen size is not known (no mode from its Pi, no preferred mode from its Display; `central/displays/model.py` `screen_px`) has no `FitTarget`, so its slots take no photo (the empty-pool rule: the last still stays, else the fallback), no copy is sized for it, authoring a photo onto it is refused `authored_frame_size_unknown`, the Source preview for it answers `frame_size_unknown` and the fit analysis lists it as `unsized`. A photo fits a Frame when some **crop window** (the part of the photo the Frame shows: the Frame output's aspect, slid along the photo's one free axis) passes four tests:

1. It removes no more than the Scene's **crop limit** of the photo's area (a backstop whatever the content). A Scene without its own crop limit follows the house crop limit (default 35 %, from 5 % to 60 %). At 35 %, 3:2, 4:3 and 5:4 photos on a 16:9 Frame (16, 25 and 30 % cut away) go on to the content tests; a portrait photo on a landscape Frame (the nearest pair, 4:5 on 5:4, cuts 36 %) and a square photo on 16:9 (44 %) do not fit. `fit.band` is the ratios a Frame accepts at a crop limit.
2. It holds at least the Frame output in the pixels of the largest copy Photo Wall can read (`contracts.frame_fit.window_holds`, the one test the rendition choice also asks; the readable size of [the copy ladder](module-media.md#original-validation-and-preparation-recipe), which for an unedited RAW photo with full-size copies off is its preview, never its original; a photo whose readable size is not measured yet is judged by shape only and its preview is measured). A photo with more pixels than the Frame needs is never refused (owner, 2026-10-26: "the too-large picture being rejected is ridiculous"): Central scales its copy only when it is substantially larger than its Frames need ([the copy ladder](module-media.md#original-validation-and-preparation-recipe)), and the Player cuts the Frame's window and scales it to the Frame ([plane renderer](module-plane-renderer.md#finishing)). A Frame whose box is 40 % × 40 % of a 3,840 × 2,160 screen has a Frame output of 1,536 × 864, so a 1,600 × 900 photo fills it; a box 25 % wide and 50 % high on a 1,920 × 1,080 screen is 480 × 540, a 9:10 Frame, which a 16:9 photo does not fit at a 30 % crop limit.
3. It keeps every face whole: each face Immich found of at least the smallest face that counts (0.2 % of the photo's area), with room kept around it (10 % of the face's own width and height on each side).
4. It cuts no key content: the share of the photo's interest it removes is at most 1.75 times the share of the area it removes. A plain side may go; a side holding a face or the subject may not; an even spread of interest passes, and so does a photo whose map of what stands out spans less than 0.05 (nothing stands out; `fit.interest_judged`, the one home of "even").

Every number above is a **photo fit setting** (owner, 2026-10-11: "Agreed that these should be configurable, and not hardcoded."): `central/wall_plan/fit_settings.py` `FitSettings` is their one home, with each value's range (`FIT_SETTING_RANGES`); the house's are one row (migration 086, `central/infra/fit_settings_store.py`), served by `GET` and `PUT /v1/operator/settings/photo-fit` (`central/photo_fit_routes.py`) and read once per planning pass and authoring check. The defaults are the values above, with when a photo gets a smaller copy (`scaled_copy_ratio`, 1.5 times its largest Frame need by default) and the coarse steps of that copy (`copy_ladder_px`, 1,920, 2,560 and 3,840 by default, [the copy ladder](module-media.md#original-validation-and-preparation-recipe)); the rest are the crop positions tried (64 steps) and the large-Frame video floor (40 inches, 1,080 rows).

Among the windows that pass, `fit.place` picks one. On a photo with faces the faces keep their **place in the photo** (owner, 2026-10-25: "A lone face should sit “in the same relative position within the image as the original (if possible), and cropped only as much as needed to fit the scaled image into the frame."; asked what scaling against cropping should change, he picked "Nothing: least crop", so the window stays the largest and only its position follows the rule). The faces' centre, weighted by their area so a bigger face pulls harder, lies at a share F of the photo along the cut; the window at offset F holds it at the same share of the window, and the passing window nearest that one wins, so a face too near the photo's edge moves only as far as keeping it whole needs (ties: nearest the centre, then the lower offset). Then the **skew toward what stands out** (`FitSettings.interest_skew`, default 0.33, 0 to 1; owner, 2026-10-25: "It could bias towards face centering but also allow a skew to include extra content"): with G the interest grid's centre of mass along the cut, the window aims at o0 + skew x (G - F), in offset units, where o0 is the faces' window above; but its edge moves at most skew x r, where r is the least room in o0's window between a face and the edge the faces move toward. The window taken is the passing one nearest that aim between o0 and the aim, never past it. So every face keeps at least 1 - skew of the room the faces' window gave it (at 0.33, two thirds), a face already near an edge barely moves, and a person's own body below a face counts as content. Skew 0, or an even grid (no side to lean toward), is the faces' window alone. The interest is what stands out, U-2-Netp's map ([media worker](module-media-worker.md#key-content)), not spectral-residual saliency, which scored texture such as a floor or foliage and slid windows off the faces (owner, 2026-10-25: "The last two photos on the frame were oddly cropped"). On the fireplace Frame Mickey's photo moves from 0.344 to 0.375 (more of the family's legs, the hat inside), and the Easter photo stays at 0.328 (the dad's face is already at the top of every window keeping all faces whole). A photo with no faces keeps the window holding the most interest (ties: nearest the centre), at any skew. Its **crop** (`PhotoCrop.offset`, 0 keeps the left or top edge, 1 the right or bottom) goes on the layer. A refused photo has one reason (`FitRefusal`), which the Frame page counts in plain words: `beyond_crop_limit` "doesn't fit this Frame's shape", `below_frame_pixels` "too small for this Frame" `face_cut` "a face would be cut", `interest_cut` "the interesting part would be cut", `no_video_here` "this Frame shows no videos". Videos take a centred window, test 1 and the 40-inch floor above; their key content is not measured. A photo whose key content is not measured yet, or whose measurement failed until its retry, is placed only as a last resort (content first: see [the wall plan](#the-wall-plan), step 4); measurement is the [media worker's](module-media-worker.md#key-content) and is requested by the Planner (`Projection.measurements`, at most 64 per pass: the unmeasured highest-ranked first, then the photos whose key is due a new measurement, the placed ones first). A due key (`Measured.due`: an older analysis version, or a provisional faceless measurement past its retry; the key-content store's one rule) is judged and placed meanwhile, so a new analysis version re-measures the wall without emptying it. Without Immich's face detection there are no faces, so crops ignore faces (owner, 2026-10-11: "If immich face detection is unavailable, then smart crop doesn’t take into account faces").

Fit is judged at read time against the stored key content, which holds Immich's face boxes as found, the grid of what stands out and its map's spread (`ANALYSIS_VERSION` "3"): face room, the smallest face, the flat-map threshold and the skew are applied when judging, so changing a setting or a Scene's crop limit takes effect at the next pass with no re-measurement. A ratio near square can fit either way: a 1.05 : 1 photo fits a 0.95 : 1 Frame (about 9.5 % cut).

### The fit analysis

One read answers how a selection of photos fits the Frames, at every moment the console asks it (owner, 2026-10-11: "this preview idea could apply at a few different moments"): `POST /v1/operator/photo-fit/analysis`, `central/wall_plan/fit_analysis.py` `analyse` over `central/infra/fit_analysis_store.py` `PgFitAnalysisReader`. Every input may be saved or a draft: the selection (saved Sources and unsaved Photo source drafts, each photo once), the Frames (saved, or one Frame's draft Position box, judged against its saved screen and Display size; a Frame with no Frame output is listed under `unsized`, "Its screen size is not known yet, so no photo is judged for it.", and judged nowhere), the crop limit and the settings. Two tiers, both through the fit rule above: **shape and size**, complete, judged once per (kind, width, height) group with each Frame's band, the ratio bins (the Shape map) and, for a Frame nothing fits, the nearest crop limit at which something would; **faces and subject**, sampled, up to 64 measured photos per Frame in a seeded order ("checked N of M"), with up to six samples that fit (their crops) and up to six per refusal, and one lead photo per Frame, never the same photo for two Frames. Tier "shape" answers only the first (the console's slider drags). Budget: 50,000 photos and 8 Frames, the full tier in about 1 s on the lane's machine, a bench measurement (`tests/test_fit_analysis_budget.py` prints the time and gates the work done, never the time).

## Order and passes

One home: [`central/wall_plan/order.py`](../central/wall_plan/order.py). Each Scene with photo slots has one **line**: its photos in the Scene's **order** (`SceneSelection.order`): **shuffle** (the default; a keyed hash of Scene, pass and photo, so a refresh keeps the others' order and each pass reshuffles), **oldest first** (`chronological`, continuing after the Scene's last shown photo and wrapping), **newest first**, or **On this day** (photos taken on today's date in earlier years first, newest year first, then the shuffle). A **pass** ends once every photo the line can place has been picked in it; the next pass starts over in a new order. "Today" is the house date (Settings › House's zone, `central/house_time/calculator.py` `house_date`), so On this day turns over at the house's midnight, not UTC's ([2b](roadmap.md#2b-the-week)).

The orders are declared once, as data (`ORDERS`: each order's sort keys), and interpreted twice: in Python (`order_key`, which ranks the lines the Planner holds) and in SQL (`ranked_line_in` in `central/infra/photo_library_store.py`, which ranks the whole pool in the database and returns only its top, `LineQuery.limit`). Both count On this day on the house calendar (`LineQuery.house`, Runtime's house). `tests/test_order_sql_conformance.py` holds the two equal for every order, tier and wrap, and for On this day in a house that is not on UTC. A line read in part is `complete` only when its last member is already picked, and only then may its pass end in this plan.

Ranking has three tiers: photos not picked in this pass and not shown within the Scene's **Don't repeat within** days (default 7, from 0 to 365); then those shown within them; then those already picked in this pass. Every rule here only ranks: a recently shown photo is never removed, so a repeat beats an empty Frame (owner, 2026-10-11: "this “no repeat” idea is secondary to always ensuring that frames have content"). "Shown" means a Player reported the layer presented (visible; a covered layer is never reported), recorded by coordination in `shown_photos` with its Frame, Scene, pass and planned interval on Central's clock ([execution contract](execution-contract.md#what-a-frame-shows-its-crop-and-when-a-photo-is-on-screen)). A layer planned wholly into wanted-off time (Night off or a hold, `central/infra/power_store.py` `wanted_off_in`) is never recorded shown: planning carries on through Night off so the morning reveals current state, but a photo shown to a dark room was not seen (roadmap 2a). Shown rows are kept 400 days, longer than the 365-day maximum, so a pass that lasts longer than that starts its rest over; what each offered layer shows (`photo_selections`) is kept a day after it ends. When Scenes start Frames at one instant, their photos are taken position by position: each Scene's first photo before any Scene's second.

## The wall plan

One home: [`central/wall_plan/assignment.py`](../central/wall_plan/assignment.py) `plan_wall`, called by `project`. The owner, 2026-10-11: "Frames are not running independently, and it’s up to Central to “plan” where the photos are assigned. I suggest an algorithm that computes all frame+photo assignments well in advance". Every Frame's photo showings (**slots**) over the **plan horizon** (one hour by default, coordination's `plan_seconds`) are planned together in one pure call, re-planned on every pass, with secured and offered layers and each Frame's kept still as fixed inputs:

1. Hand-placed slots take the first of their authored photos that fits and is free; Scene lines skip those photos for the hour. A hand-placed photo that is on screen on another Frame waits until it is off that Frame.
2. Slots are walked by start time. At one instant each slot offers its line's next photos it can take (the slots at that instant plus 4); the offers are kept in rank order while every kept photo can still have its own slot (Kuhn's augmenting paths: prior art for distinct picks), then placed on the slots that crop them least (a minimum-cost matching, Kuhn-Munkres).
3. **Never on two Frames at once.** A photo whose on-screen extent on another Frame overlaps a slot's is never offered to it, hand-placed photos included. The extent is one function both the Planner and the Player use ([`contracts/on_screen.py`](../contracts/on_screen.py), [execution contract](execution-contract.md#what-a-frame-shows-its-crop-and-when-a-photo-is-on-screen)): every planned layer showing the photo counts, covered or see-through, and a kept still holds its photo until something replaces it. The check reads only the extents that can overlap: each photo's extents that no later showing changes are computed once and kept sorted by start with their running latest end (`_Spans` in `central/wall_plan/assignment.py`), so a long plan on a small pool (a perpetual Default Scene on a short cycle places each photo hundreds of times an hour) stays linear rather than rechecking every earlier showing; the pass holds the coordination lock while it plans.
4. **A Frame always has content.** A slot left without a photo keeps its Frame's previous photo when it still fits and is free (it need not be in the slot's pool, so a Frame keeps its last photo across a Scene change). Failing that, it takes the line's first photo of its pool whose key content is unknown (not measured yet, or its measurement failed) that passes the fit rule's size part, is usable and is free, with the centred crop: so a pool none of whose photos is measured yet (Immich out of reach, a new analysis version) still fills the wall; inside the preparation horizon such a photo is asked to be prepared. Only a Frame that never showed anything and has nothing of this kind gets its fallback ([eligibility](#eligibility-selection-and-fallbacks)).

Slots starting inside the preparation horizon (300 s) become layers and take only prepared photos; one whose photo is not prepared in time is filled with one that is, and the unprepared photo is requested. Slots beyond it are tentative until their photos are prepared. Every pass re-plans the hour: each coordination pass (every second) plans an hour across every Frame, which costs time that grows with the pools and the history. On the reference wall (8 Frames, 30 s cycles, an hour, 10,000 measured photos) one projection took about 0.65 s on an Apple-silicon Mac, the Planner alone with no database read (measured 2026-10-11 for pull request [#82](https://github.com/mcurcio/photo-wall/pull/82)). Since the follow-up, the pass also reads from the database, the top of each line only: 50,000 photos in one pool and 8 Frames read within a placeholder budget of 0.5 s (`tests/test_planner_pass_budget.py`, to be measured on the bench). The plan holds at most `WallLimits.max_slots` (8,192) slots: a larger wall (16 Frames at 5 s cycles hold 11,520 in the hour) is planned over a shorter span, cut at one instant past the budget, with the diagnostic `plan_shortened`; the slots inside the preparation horizon are always planned. At the budget one projection took 1 to 4 s on the same Mac (16 Frames at 5 s, 1.2 s; 70 Frames at 30 s, 4.2 s; 30 Frames at 15 s with 20,000 photos, 2.9 s), and the pass holds the coordination lock meanwhile, which Player requests wait on: planning the tentative hour outside that lock, or only when its inputs change, is open (review round 1 of [#82](https://github.com/mcurcio/photo-wall/pull/82)). The fit rule's verdict for a photo on a Frame shape is memoised (`assignment.py` `fit_of`), keyed by every input, so the memo never disagrees with the rule.

What the plan does not yet do: react to a Player's "failed" report (a layer that fails to draw leaves the old photo up past its extent, and a rebooted Pi shows its local fallback; either can put one photo on two Frames for a while). Each Frame's kept still is read from the latest started layer that set what it keeps, offered or reported presented, so a photo kept beneath a covering Scene (drawn, never reported presented) is known. A "presented" report stamped with a revision offered before the latest still counts as shown; a report that never arrives leaves its photo uncounted, so it may come back sooner. A lock whose selection was never recorded (one offered before 5a) is matched to its photo by the prepared copy it draws.

## Locks and failure boundaries

Locked bytes, assignment/media identity and temporal/effect interval are carried forward only while their Runtime assignment still exists in this projection and its Player/output/Frame generation remains valid. Fresh priority/root/descendant arbitration metadata is recomputed while preserving the exact secured variant; coordination must issue a new plan revision and invalidate execution readiness as needed. Descendants use a durable per-root sequence so unrelated activation does not perturb their local order, while a future Program root can still acquire a different actual root order. Query deletion or an upstream outage cannot reroll it. A stale binding, interval, Run, or assignment key is diagnosed and excluded; authority epochs are checked by central coordination before passing locks. The caller must use the persisted adopted Runtime tree associated with the locks, which supplies fixed role and Scene-revision context; it must not pair arbitrary replacement definitions with old locks. A later central-only durable lock record may carry an adopted-definition digest. A changed display or Position (the Frame output) requires coordination to revalidate original-media suitability and invalidate incompatible execution readiness before passing locks; exact bytes remain pinned until explicit release. Locks from a cancelled or completed contribution do not extend its lifetime or pin its history.

The Planner's budgets (`PlannerLimits`) bound its work, never the wall: Runtime transitions (`max_events`, simultaneous Program admissions included), layers inside the preparation horizon (`max_assignments`) and the wall plan's slots (`WallLimits.max_slots`, 8,192) each cut the plan at one instant through one rule (`_ProjectionBuilder.cut_at`): the start of the first showing past the budget (for Runtime transitions, the last boundary the timeline processed in full), so every Frame's plan holds nothing new that starts to show at or after it, with the diagnostic `plan_shortened` and its `reason` (`runtime_events`, `assignments`, `slots`); `Projection.cut` is that instant and `valid_until` reaches no further. A lock is never cut: it is content already offered. Coordination does not replace an offer by a cut plan that would withdraw one of its layers past the cut; the offer stands until it expires or the plan reaches that far again. Diagnostics past `max_diagnostics` are counted (`Projection.diagnostics_dropped`), not kept. Acquisitions (`max_acquisitions`) and measurement requests (`max_measurements`, 64) are capped per pass. Nothing bounds a Scene's cycle, the plan horizon, or the number of Players, bindings, Sources or authored photos. It does not cut a pool before the fit test: the line is read in batches that grow while a batch is entirely refused, so a budget on a batch cannot starve a portrait Frame. Subnormal cycles past finite arithmetic shorten the timeline the same way. It deduplicates acquisitions across covered/uncovered assignments and Players. No database, network, filesystem, media worker, or physical-device access exists here.

## Coordination and the scheduler

Central's scheduler (`central/scheduler.py`) ticks once a second through steps that each run, fail and report on their own: the Node reconciler, then the coordinator's three steps (`Coordinator.advance`, each its own transaction): **runtime** (the Runtime moves to now and is saved), **planning** (the Planner over the saved Runtime, the offers to each Player, the preparation requests and the planning outcome) and **settle** (due commits, pin expiry, cleanup), then the measurement requests. Planning that fails leaves the Runtime moving on and commits settling. Within planning the Player is the unit of isolation: one whose configuration fails (its authority went stale, or anything else), whose content locks disagree or no longer read, or whose offer fails for any reason is left out alone, its writes rolled back to its own savepoint, with an `offer_unavailable` event naming the code; a stored offer that no longer reads is left out on its own. The cues coordination groups are the showings the Planner placed (`Projection.cues`), so coordination never walks the timeline a second time with its own window. A step that cannot run because an earlier one failed (measurement, without a plan) is "skipped", never left reading ok. Each step is a facet of `/healthz` ([runbook](runbook.md#tests-and-local-development)); the planning outcome (`central/planning_outcome.py`: each pass's diagnostics without their assignment ids, kept in `planning_outcome` when they change) is served in the operator snapshot, and the console's Needs attention lists planning that fails and each Scene refused.
