# Pure rolling Planner

Status: implementation contract accepted for the first MVP; its source input became the photo pools in delivery [4](roadmap.md#4-real-photo-sources) (pull request [#81](https://github.com/mcurcio/photo-wall/pull/81)); delivery [5a](roadmap.md#5a-photo-fit-and-order) (pull request [#82](https://github.com/mcurcio/photo-wall/pull/82)) made it plan the whole wall an hour ahead, one photo per Frame, never on two Frames at once; the follow-up to 5a made it read only the top of each Scene's line from the database each pass, never a whole pool (below). This is a central domain module; it does not acquire media, change Runtime, establish readiness, issue execution authority, or call devices. [The time/recovery decision](decisions/0001-mvp-time-recovery-and-module-contracts.md) and [execution contract](execution-contract.md) remain authoritative.

## Inputs, state and output

`project(runtime, now, *, bindings_by_player, lines, authored_candidates, locked_assignments, history, horizon_seconds=300, plan_seconds=PLAN_SECONDS, max_clock_uncertainty=0.1, limits=PlannerLimits()) -> Projection` is stateless; `PLAN_SECONDS` (3,600) is the one home of the plan horizon's default, which coordination's `plan_seconds` also takes. Inputs are current `Runtime`, a finite UTC instant, Player-to-`OutputBinding` sequences, a `SceneLines` reader (`central/wall_plan/order.py`; in production `PgSceneLines` over the photo library's `ScenePoolReader`) that answers, in the coordination transaction, each Source revision's pool key, readiness and emptiness (`sources`) and the top of a Scene's line (`line`, below), so the Planner never loads a pool, asset-reference-to-`Candidate` mappings for authored media, assignment-ID-to-exact-`Layer` locks already accepted by central coordination, and the wall's shown history (`WallHistory`, read by coordination; the Planner never reads it itself). Each pool candidate carries its key content (`Candidate.analysis`: measured, failed, or not measured yet), hydrated from the media worker's measurements. Shared catalog and transport models have their sole definitions in `central/catalog.py` and `contracts/models.py`.

`Projection` names `now`, `horizon_end`, and `valid_until` separately. It returns per-Player `PlayerProposal.layers` (each media layer carrying its crop, [execution contract](execution-contract.md#what-a-frame-shows-its-crop-and-when-a-photo-is-on-screen)), central-only `AcquisitionRequest(asset_id, assignment_ids, earliest_start)` entries, measurement requests (`Projection.measurements`), the whole wall plan (`Projection.plan`, every slot over the plan horizon), central-only asset/assignment selection records (each new placement naming its Scene and pass), and coded diagnostics. It does not construct a `Plan`: epoch, revision, commitment, transactionality, current Frame authority and persistent locks remain coordination responsibilities. `PlanningError` and `PlanningBudgetExceeded` fail explicitly without partial proposals or external effects.

Runtime gains `timeline(start, end, max_events=10000)`: it restores a copy, reconciles the start, and returns settled immutable views at the start and every discrete lifecycle boundary before the end. It never samples at one-second intervals. An explicit transition/event budget includes catch-up and generated descendants, so tiny cycles and excessive child work fail instead of hanging. Timeline projection cannot affect current Runs, admissions, queues or recorded Actuators. Intent retains sampled opacity for current observation and also exposes authored base opacity and fade durations for execution layers.

## Preparation horizon and execution intervals

The configured preparation horizon bounds **assignment start times**, not a Scene's total lifetime. Include a currently active assignment or a future assignment whose true start is strictly before `now + horizon_seconds`; preserve its full half-open natural cycle/outro interval and media origin. A cycle/outro must be at most `limits.max_cycle_seconds` (300 seconds by default). Longer cycles fail explicitly; long-running Scenes use an unbounded sequence of bounded cycles. The horizon itself is configurable up to the limits' explicit maximum. The **plan horizon** (`plan_seconds`, an hour from coordination, also within that maximum) is longer: [the wall plan](#the-wall-plan) chooses photos for every slot up to it, so no photo is placed on one Frame now that another Frame needs later in the hour without the plan seeing both, but only slots inside the preparation horizon become layers.

`valid_until` is the greater of the preparation-horizon end and included complete assignment ends, and can therefore extend by at most one bounded cycle. Ongoing assignments can start before `now`; Players must seek their true cycle media origin. No polling-dependent clipping changes IDs, fade timing, pinned locks, or authorization intervals. The host Plan validator permits a Layer that overlaps Plan validity and still requires its end to be inside the Plan's validity. This distinction is an MVP choice, not a numerical outage guarantee.

Assignment identity hashes Run ID, typed target, phase and original cycle interval. Selection does not participate in that identity: an unsecured assignment may change exact bytes, but a secured lock retains its exact variant/media identity and interval. Root/descendant arbitration metadata can be revised under a new Plan revision and renewed readiness; it is not a content lock. Root admission order and descendant order must both remain represented in per-Player layer stacking. A later descendant of an old background must not overtake a newer independent overlay. Unrelated and actuator-only targets never become implied display commands.

## Eligibility, selection and fallbacks

This module is the single owner of original-media eligibility, through [the photo fit rule](#the-photo-fit-rule) below: a photo goes only on a Frame it fills with its key content kept, judged by the ratio of its sides, never by orientation labels. Videos require the Frame video capability, and originals with fewer than 1080 pixels on their shorter side are excluded on Frames of at least 40 inches. A large derivative cannot rehabilitate an unsuitable original. Exact variants must have compatible media type and usable video duration; malformed prepared candidates are diagnosed rather than sent to a Player. Authored asset alternatives follow the same checks and stay on their authored Frame/role. Authored candidates are considered in authored order; source candidates are considered only for a dynamic contribution without authored alternatives.

A dynamic contribution's candidate pool is the union of the pools of the Sources it names, in the contribution's order, one candidate per asset ID (the first seen). Each Frame's contribution names its own Sources (Runtime's `source_refs` per target), so one Frame's Sources never mix into another's; the console writes the same Sources on every Frame of a Scene, so for every Scene it makes this is the Scene's pool. The Planner reaches every photo in those pools: no photo is cut by a window or a count (owner, 2026-10-09: "i dont want any limit on the count of a source"), and it reads only the top of each Scene's line each pass, fresh, with capture time and readable size read at query time (follow-up to 5a, design rule 3: only what the plan needs). `_read_lines` asks `SceneLines.line` for the first `slots x hydrate_factor` members (`PlannerLimits.hydrate_factor`, default 4) of each Scene's line, ranked in SQL by the Scene's tier and order, and doubles the batch while every member read is refused for the Frames (`useful_for`), up to the whole line; it reads the next pass's top too when this pass could end in this plan. So a photo the fit rule refuses for every slot never starves the wall, and every photo stays reachable as the line ranks it. Each Scene's line then orders its photos ([order and passes](#order-and-passes)) and [the wall plan](#the-wall-plan) places them on every Frame together. A check's newly confirmed photos enter the next unsecured cycle within the same Run. A source reference denotes an immutable authored query version; new query results remain live data. A pool whose check has not completed, or whose last check failed, still offers what it holds: the last pool keeps playing while Immich is down or the key is rejected (C7), because a pool row is a photo a check confirmed and a check removes photos only when it completes ([media module](module-media.md#live-discovery-pagination-and-metadata)). The diagnostics are `source_missing` (no pool for the reference), `source_not_ready` (no complete check yet and nothing found so far), `source_empty` (a complete check found nothing: truly empty), `no_eligible_candidates` (no photo of the pool fits the Frame), `no_photo_free` (every photo that fits is on another Frame at that time; the Frame keeps its previous photo when it still fits) and `authored_no_eligible_alternative`; `preparation_pending` and `variant_incompatible` are retired, since a slot that cannot use a photo's prepared copy takes another photo. The connection's own health says why a check failed.

`candidate_standing(candidate, profile)` is the planner's one per-candidate verdict for an eligible candidate, in its exclusion order: `failed_to_prepare` (a recorded preparation failure; the media repository's candidate hydration also records one for a failed job whose retry is not yet due), `preparing` (no variant yet), `no_compatible_variant` (a variant the profile cannot use), or `usable`. The line drops `failed_to_prepare`; inside the preparation horizon a slot takes only `usable` candidates, and the wall plan requests acquisition for the `preparing` ones its lines rank first. The operator candidates route serves the same verdict ([authored media](module-authored-media.md)), so no caller restates the variant rule.

A selected eligible candidate without exact prepared bytes creates a bounded central acquisition request and no playback-ready Layer. A missing/empty/error contribution emits no replacement display command and a fallback diagnostic; the executor retains its authorized compatible still or configured local fallback under the recovery policy. The Planner never substitutes a different target or relaxes eligibility. Explicit authored opaque black produces an exact black Layer independently of media availability. Covered contributions remain in proposals for current-state reveal and transparency; only Runtime's target union is not sufficient to create a Layer.

## The photo fit rule

One home: [`central/wall_plan/fit.py`](../central/wall_plan/fit.py) (`judge`, and `shape_fit` for the checks that need only the photo's size). The Planner, the hand-placed authoring check, the operator candidates route and [the fit analysis](#the-fit-analysis) all ask it; the media worker only measures and the Player only draws. The requirement is [requirements › compatibility](requirements.md#live-media-compatibility-and-preparation). The rule judges a Frame as a `FitTarget`: its display profile (the shape, `width_px / height_px`, video and size) and its **Frame output**, the Frame's picture on its Display in output pixels (owner, 2026-10-11: compatibility "measuring against the Frame output and not the Display"; `contracts.models.frame_output`, read by `central.infra.display_store.frame_outputs_in`). A photo fits a Frame when some **crop window** (the part of the photo the Frame shows: the profile's aspect, slid along the photo's one free axis) passes four tests:

1. It removes no more than the Scene's **crop limit** of the photo's area (a backstop whatever the content). A Scene without its own crop limit follows the house crop limit (default 35 %, from 5 % to 60 %). At 35 %, 3:2, 4:3 and 5:4 photos on a 16:9 Frame (16, 25 and 30 % cut away) go on to the content tests; a portrait photo on a landscape Frame (the nearest pair, 4:5 on 5:4, cuts 36 %) and a square photo on 16:9 (44 %) do not fit. `fit.band` is the ratios a Frame accepts at a crop limit.
2. It holds at least the Frame output in the pixels of the largest copy Photo Wall can read (`contracts.frame_fit.window_holds`, the one test the rendition choice also asks; the readable size of [the copy ladder](module-media.md#original-validation-and-preparation-recipe), which for an unedited RAW photo with full-size copies off is its preview, never its original; a photo whose readable size is not measured yet is judged by shape only and its preview is measured), and the copy that Frame needs is no longer than the Player shows (`FitSettings.max_still_edge`, default 4,096): longer is `above_player_limit`, "needs more detail than this Pi can draw". A Frame through a mat opening of 40 % × 40 % on a 3,840 × 2,160 Display has a Frame output of 1,536 × 864, so a 1,600 × 900 photo fills it; the same Frame turned 10° needs more than the Display, so a photo of exactly the Display's size does not. A Frame whose Output never reported a size has no Frame output and is judged by shape only.
3. It keeps every face whole: each face Immich found of at least the smallest face that counts (0.2 % of the photo's area), with room kept around it (20 % of the face's own width and height on each side).
4. It cuts no key content: the share of the photo's interest it removes is at most 1.25 times the share of the area it removes. A plain side may go; a side holding a face or the subject may not; an even spread of interest passes, and so does a photo whose saliency map spans less than 0.05 (nothing stands out).

Every number above is a **photo fit setting** (owner, 2026-10-11: "Agreed that these should be configurable, and not hardcoded."): `central/wall_plan/fit_settings.py` `FitSettings` is their one home, with each value's range (`FIT_SETTING_RANGES`); the house's are one row (migration 086, `central/infra/fit_settings_store.py`), served by `GET` and `PUT /v1/operator/settings/photo-fit` (`central/photo_fit_routes.py`) and read once per planning pass and authoring check. The defaults are the values above, with the still limit (`max_still_edge`) and the coarse steps of a photo's one copy (`copy_ladder_px`, 1,920, 2,560 and 3,840 by default, [the copy ladder](module-media.md#original-validation-and-preparation-recipe)); the rest are the crop positions tried (64 steps) and the large-Frame video floor (40 inches, 1,080 rows).

Among the windows that pass, the one keeping the most interest wins (ties: nearest the centre). Its **crop** (`PhotoCrop.offset`, 0 keeps the left or top edge, 1 the right or bottom) goes on the layer. A refused photo has one reason (`FitRefusal`), which the Frame page counts in plain words: `beyond_crop_limit` "doesn't fit this Frame's shape", `below_frame_pixels` "too small for this Frame", `above_player_limit` "needs more detail than this Pi can draw", `face_cut` "a face would be cut", `interest_cut` "the interesting part would be cut", `no_video_here` "this Frame shows no videos". Videos take a centred window, test 1 and the 40-inch floor above; their key content is not measured. A photo whose key content is not measured yet, or whose measurement failed until its retry, is placed only as a last resort (content first: see [the wall plan](#the-wall-plan), step 4); measurement is the [media worker's](module-media-worker.md#key-content) and is requested by the Planner (`Projection.measurements`, at most 64 per pass, highest-ranked first). Without Immich's face detection there are no faces, so crops ignore faces (owner, 2026-10-11: "If immich face detection is unavailable, then smart crop doesn’t take into account faces").

Fit is judged at read time against the stored key content, which holds Immich's face boxes as found and the saliency map's spread (`ANALYSIS_VERSION` "2"): face room, the smallest face and the flat-map threshold are applied when judging, so changing a setting or a Scene's crop limit takes effect at the next pass with no re-measurement. A ratio near square can fit either way: a 1.05 : 1 photo fits a 0.95 : 1 Frame (about 9.5 % cut).

### The fit analysis

One read answers how a selection of photos fits the Frames, at every moment the console asks it (owner, 2026-10-11: "this preview idea could apply at a few different moments"): `POST /v1/operator/photo-fit/analysis`, `central/wall_plan/fit_analysis.py` `analyse` over `central/infra/fit_analysis_store.py` `PgFitAnalysisReader`. Every input may be saved or a draft: the selection (saved Sources and unsaved Photo source drafts, each photo once), the Frames (saved, or one Frame's draft profile and Position, judged against its Display's last reported size), the crop limit and the settings. Two tiers, both through the fit rule above: **shape and size**, complete, judged once per (kind, width, height) group with each Frame's band, the ratio bins (the Shape map) and, for a Frame nothing fits, the nearest crop limit at which something would; **faces and subject**, sampled, up to 64 measured photos per Frame in a seeded order ("checked N of M"), with up to six samples that fit (their crops) and up to six per refusal, and one lead photo per Frame, never the same photo for two Frames. Tier "shape" answers only the first (the console's slider drags). Budget: 50,000 photos and 8 Frames, the full tier in about 1 s on the lane's machine, a bench measurement (`tests/test_fit_analysis_budget.py` prints the time and gates the work done, never the time).

## Order and passes

One home: [`central/wall_plan/order.py`](../central/wall_plan/order.py). Each Scene with photo slots has one **line**: its photos in the Scene's **order** (`SceneSelection.order`): **shuffle** (the default; a keyed hash of Scene, pass and photo, so a refresh keeps the others' order and each pass reshuffles), **oldest first** (`chronological`, continuing after the Scene's last shown photo and wrapping), **newest first**, or **On this day** (photos taken on today's date in earlier years first, newest year first, then the shuffle). A **pass** ends once every photo the line can place has been picked in it; the next pass starts over in a new order. Dates are UTC until [2b](roadmap.md#2b-the-week) gives the house a timezone.

The orders are declared once, as data (`ORDERS`: each order's sort keys), and interpreted twice: in Python (`order_key`, which ranks the lines the Planner holds) and in SQL (`ranked_line_in` in `central/infra/photo_library_store.py`, which ranks the whole pool in the database and returns only its top, `LineQuery.limit`). `tests/test_order_sql_conformance.py` holds the two equal for every order, tier and wrap. A line read in part is `complete` only when its last member is already picked, and only then may its pass end in this plan.

Ranking has three tiers: photos not picked in this pass and not shown within the Scene's **Don't repeat within** days (default 7, from 0 to 365); then those shown within them; then those already picked in this pass. Every rule here only ranks: a recently shown photo is never removed, so a repeat beats an empty Frame (owner, 2026-10-11: "this “no repeat” idea is secondary to always ensuring that frames have content"). "Shown" means a Player reported the layer presented (visible; a covered layer is never reported), recorded by coordination in `shown_photos` with its Frame, Scene, pass and planned interval on Central's clock ([execution contract](execution-contract.md#what-a-frame-shows-its-crop-and-when-a-photo-is-on-screen)). Shown rows are kept 400 days, longer than the 365-day maximum, so a pass that lasts longer than that starts its rest over; what each offered layer shows (`photo_selections`) is kept a day after it ends. When Scenes start Frames at one instant, their photos are taken position by position: each Scene's first photo before any Scene's second.

## The wall plan

One home: [`central/wall_plan/assignment.py`](../central/wall_plan/assignment.py) `plan_wall`, called by `project`. The owner, 2026-10-11: "Frames are not running independently, and it’s up to Central to “plan” where the photos are assigned. I suggest an algorithm that computes all frame+photo assignments well in advance". Every Frame's photo showings (**slots**) over the **plan horizon** (one hour by default, coordination's `plan_seconds`) are planned together in one pure call, re-planned on every pass, with secured and offered layers and each Frame's kept still as fixed inputs:

1. Hand-placed slots take the first of their authored photos that fits and is free; Scene lines skip those photos for the hour. A hand-placed photo that is on screen on another Frame waits until it is off that Frame.
2. Slots are walked by start time. At one instant each slot offers its line's next photos it can take (the slots at that instant plus 4); the offers are kept in rank order while every kept photo can still have its own slot (Kuhn's augmenting paths: prior art for distinct picks), then placed on the slots that crop them least (a minimum-cost matching, Kuhn-Munkres).
3. **Never on two Frames at once.** A photo whose on-screen extent on another Frame overlaps a slot's is never offered to it, hand-placed photos included. The extent is one function both the Planner and the Player use ([`contracts/on_screen.py`](../contracts/on_screen.py), [execution contract](execution-contract.md#what-a-frame-shows-its-crop-and-when-a-photo-is-on-screen)): every planned layer showing the photo counts, covered or see-through, and a kept still holds its photo until something replaces it.
4. **A Frame always has content.** A slot left without a photo keeps its Frame's previous photo when it still fits and is free (it need not be in the slot's pool, so a Frame keeps its last photo across a Scene change). Failing that, it takes the line's first photo of its pool whose key content is unknown (not measured yet, or its measurement failed) that passes the fit rule's size part, is usable and is free, with the centred crop: so a pool none of whose photos is measured yet (Immich out of reach, a new analysis version) still fills the wall; inside the preparation horizon such a photo is asked to be prepared. Only a Frame that never showed anything and has nothing of this kind gets its fallback ([eligibility](#eligibility-selection-and-fallbacks)).

Slots starting inside the preparation horizon (300 s) become layers and take only prepared photos; one whose photo is not prepared in time is filled with one that is, and the unprepared photo is requested. Slots beyond it are tentative until their photos are prepared. Every pass re-plans the hour: each coordination pass (every second) plans an hour across every Frame, which costs time that grows with the pools and the history. On the reference wall (8 Frames, 30 s cycles, an hour, 10,000 measured photos) one projection took about 0.65 s on an Apple-silicon Mac, the Planner alone with no database read (measured 2026-10-11 for pull request [#82](https://github.com/mcurcio/photo-wall/pull/82)). Since the follow-up, the pass also reads from the database, the top of each line only: 50,000 photos in one pool and 8 Frames read within a placeholder budget of 0.5 s (`tests/test_planner_pass_budget.py`, to be measured on the bench). The plan holds at most `WallLimits.max_slots` (8,192) slots: a larger wall (16 Frames at 5 s cycles hold 11,520 in the hour) is planned over a shorter span, cut at one instant past the budget, with the diagnostic `plan_shortened`; the slots inside the preparation horizon are always planned. At the budget one projection took 1 to 4 s on the same Mac (16 Frames at 5 s, 1.2 s; 70 Frames at 30 s, 4.2 s; 30 Frames at 15 s with 20,000 photos, 2.9 s), and the pass holds the coordination lock meanwhile, which Player requests wait on: planning the tentative hour outside that lock, or only when its inputs change, is open (review round 1 of [#82](https://github.com/mcurcio/photo-wall/pull/82)). The fit rule's verdict for a photo on a Frame shape is memoised (`assignment.py` `fit_of`), keyed by every input, so the memo never disagrees with the rule.

What the plan does not yet do: react to a Player's "failed" report (a layer that fails to draw leaves the old photo up past its extent, and a rebooted Pi shows its local fallback; either can put one photo on two Frames for a while). Each Frame's kept still is read from the latest started layer that set what it keeps, offered or reported presented, so a photo kept beneath a covering Scene (drawn, never reported presented) is known. A "presented" report stamped with a revision offered before the latest still counts as shown; a report that never arrives leaves its photo uncounted, so it may come back sooner. A lock whose selection was never recorded (one offered before 5a) is matched to its photo by the prepared copy it draws.

## Locks and failure boundaries

Locked bytes, assignment/media identity and temporal/effect interval are carried forward only while their Runtime assignment still exists in this projection and its Player/output/Frame generation remains valid. Fresh priority/root/descendant arbitration metadata is recomputed while preserving the exact secured variant; coordination must issue a new plan revision and invalidate execution readiness as needed. Descendants use a durable per-root sequence so unrelated activation does not perturb their local order, while a future Program root can still acquire a different actual root order. Query deletion or an upstream outage cannot reroll it. A stale binding, interval, Run, or assignment key is diagnosed and excluded; authority epochs are checked by central coordination before passing locks. The caller must use the persisted adopted Runtime tree associated with the locks, which supplies fixed role and Scene-revision context; it must not pair arbitrary replacement definitions with old locks. A later central-only durable lock record may carry an adopted-definition digest. Changed equipment profiles/calibration require coordination to revalidate original-media suitability and invalidate incompatible execution readiness before passing locks; exact bytes remain pinned until explicit release. Locks from a cancelled or completed contribution do not extend its lifetime or pin its history.

The Planner explicitly bounds horizon length, cycle length, Runtime transitions (including simultaneous Program admissions), assignments, sources, authored reference counts (`max_authored_refs`, 10,000), acquisition count, measurement requests (`max_measurements`, 64) and the wall plan's slots (`WallLimits.max_slots`, 8,192: past it the tentative tail is cut, `plan_shortened`, and only more slots inside the preparation horizon than that fail). It does not cut a pool before the fit test: the line is read in batches that grow while a batch is entirely refused, so a budget on a batch cannot starve a portrait Frame. Subnormal cycles that exceed finite arithmetic fail with the same explicit Runtime budget error. It validates budgets before broad selection work and deduplicates acquisitions across covered/uncovered assignments and Players. Budget exhaustion returns no partial plan. No database, network, filesystem, media worker, or physical-device access exists here.
