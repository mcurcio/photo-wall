# Single-process Player control service

Implementation contract, revised for stateless Players. The service composes neutral enrollment, the [Executor](module-player-execution.md), the [disposable cache](module-cache.md), and [the plane renderer](module-plane-renderer.md). It owns networking, fresh session authority, current preparation, and worker scheduling. It never imports central or media packages, selects media, or owns durable state.

## Startup and enrollment

The common public configuration names an optional saved central root, an optional public CA file, an optional cache directory, a cache quota, and native resource limits. The Player reads `photowall.central` from the kernel command line; that root takes precedence. `central_origin` in public.json is the saved root, written by the Node's handoff stage (`appliance/boot/node_bootstrap.py`), and used only when the command line names no Central. There is no mDNS discovery: with neither, the Player reports `not_discovered`. Before the first request the Player locates Central with `GET /v1/locate` (the only request that follows redirects) and sends every subsequent request, including the WebSocket, to the located origin. It locates again after every failed cycle. Its registration is bound to the origin that issued it, via a `Session(central)` value in `player/central_link.py` that is the only source of authenticated headers: a registration joins a session only through `.enrolled()`, and `.relocated(new)` keeps it only when the new origin's scheme, host and port match the one that issued it. A newly located origin means silent re-enrollment by serial, which keeps the Frame binding ([decision 0014, U8](decisions/0014-reaching-central-from-every-boot-stage.md#requirements-hard-rules)). `CentralLink` also owns the httpx clients (a response hook refuses any 3xx before it can be followed; built as each session cycle starts and closed once its tasks are cancelled, so no pooled connection outlives a failed cycle), the websocket factory, and failure naming, so `service.py` never passes `follow_redirects`, `ssl`, headers or URLs itself. Strict bounded JSON rejects unknown fields, credentials in URLs, query fragments, and non-origin base paths. Output observations come from Linux DRM connectors, with at most two HDMI connectors.

Every process start generates a new Ed25519 key in memory. The key, bearer token, authority epoch, plans, commitments, observations, pins, and cache metadata never reach persistent storage. Enrollment proves the fresh key together with the equipment observation ID, the boot ID, and current Output observations. The central registry recognizes returning equipment from the trusted provisioning observation, issues a new authority epoch, and returns current configuration and assignments. Unknown equipment remains unbound. An earlier process key, bearer token, epoch, plan, or commitment is rejected after the new session becomes current.

Cold boot requires reachable provisioning, release, enrollment, control, and media services. A running Player keeps playing its held plan while Central is slow or unreachable, its layers and then its continuations ([0032](decisions/0032-the-player-continues-centrals-plan.md), [execution contract](execution-contract.md#failure-behavior)). The Player makes no promise to reconstruct playback after a cold reboot without central connectivity.

**No watchdog.** The node Player is started by the broker as a transient `Type=exec` unit with no `WatchdogSec` ([Player architecture](player-architecture.md#processes-and-supervision)) and sends no `sd_notify` messages: the V1 unit's `READY=1` and watchdog pets (0014 M5) were deleted with it in PR 45. A Player whose GLib loop stops is ended by the broker's probe kill.

The boot context is the Pi's serial-derived `device_id` (`contracts.equipment.equipment_device_id`, kind `pi`, the scheme Central's `device_id_for_serial` uses) and a fresh `boot_id` for this run (`hardware_boot_context`). There is no boot-context file and no boot ticket: the Player's unit mounts an empty `/run`, and every enrollment is ticketless, so Central enrolls an unknown Player unbound by serial. After enrollment the Player says hello on its control session (`/v1/player/hello`, control schema 2) before Central answers any state; a state request before hello is refused with 409 `control_negotiation_required` (the WebSocket closes 1008).

## Control, media, and authority

The GLib main thread owns the Renderer and control-state application (the Player has no GTK since the render redesign, [0029](decisions/0029-render-planes.md)). An asyncio network thread owns authenticated bounded HTTP/WebSocket work, and one media thread serializes cache operations. Queues are bounded. Configuration/epoch changes and revocations cannot be lost through state coalescing. Apply configuration, the optional Plan, revocations, compatible commits, and the immediate prepare/tick in one GLib callback.

Every GLib source the Player adds goes through `player/mainloop.py` (G8 in [observed gaps](player-architecture.md#observed-gaps)): thread-to-main handoffs run at `PRIORITY_HIGH`, above the screens' frame turns and the planning tick, so a saturated loop cannot starve control; the tick re-arms after its work with a gap; a screen is committed only when what it shows changes (a still photo once), and every change over time (a fade, a video's new frame, a finished picture, a Live slider edit) reaches the screen through a frame turn (`FrameLoop`, run on a read of the screens' connection, a wake or the time the last turn asked for), not at the tick's pace ([plane renderer](module-plane-renderer.md#the-frame-loop-and-pacing)). A handoff that has not started within `DISPATCH_DEADLINE` (2 x `REPORT_INTERVAL`) is abandoned (it never runs) and the Player raises the health fault and reason `main_loop_late` in `service-health.json` and its log. It posts nothing on readiness then: Central keeps the readiness it last accepted, prepared playback included, so groups already committed stand; Central refuses no grant on a report's age ([0032](decisions/0032-the-player-continues-centrals-plan.md): freshness is the readiness sequence a Commit echoes), and past 31.5 s the Player reads as `player-silent`, as before. A late loop never withdraws prepared playback, because Central treats a current layer missing from `prepared` as lost and skips the wall's coordinated groups. Nothing on a V2 node restarts a Player whose loop is only saturated: the probe-kill path acts on unanswered probes, and the probes are answered at handoff priority, so it ends only a blocked main thread. A started handoff is always awaited, never reported late. First enrollment waits for a late loop instead of discarding its registration.

HTTP does not follow redirects or use ambient proxy settings. Metadata responses and WebSocket messages are limited to 1 MiB with bounded deadlines. Media requests use only `/v1/media/{exact SHA256}` on the located central origin. The service verifies status, media type, content length, and current authority at every awaited boundary, then streams bounded chunks into Executor/Cache. Cache verifies the complete digest and quota admission. No redirect is ever followed by httpx or the WebSocket, so the bearer token never leaves the located origin.

Before requesting media, the service asks Cache to validate a reusable content-addressed file. A valid candidate is pinned for the current assignment without a download. A missing or corrupt candidate is reacquired. Download and cache loss invalidate readiness but never change the exact centrally secured selection. A download the Player stops itself (its session ends, or a newer plan revision or a revocation takes the job's authority) is neither a `download` readiness failure nor a `media_download` fault: the assignment is only not secured, and the next job fetches it again (`AcquisitionStopped`, `player/executor.py`). A download that breaks on the network side (a reset, a body short of or past its length) is still both: the network side ends the chunk bridge with its error, and only a stop without one is the Player's own. Acquisition retries use bounded 1/5/15/60-second delays. Cache ownership is reconciled every two seconds and secured bytes are reverified at least every ten seconds.

The service sends readiness at least twice per second while a Plan is active. Observations retain their actual sample/draw times; download or preroll is never reported as presentation. A current-state response carries configuration, an optional Plan, Commit records, Revocations, and optional `identify_output` operational state. Central still sends the identify cue (a request ID, Output ID, authority epoch and server-computed remaining seconds) on both `/v1/player/state` and the authenticated WebSocket, but the Player reads and ignores it and no longer offers the `identify_output` capability, so Central refuses the console's Identify with `identify_unsupported`: the banner could never be seen on a node (Display Host's page covers every Output not granted, and only a bound Output is granted), and it was deleted with the old renderer ([0029](decisions/0029-render-planes.md)). Every state answer carries Central's clock (`State.server_time`, outside the delivery digest) and is a show-clock sample ([below](#independent-clock-probe)). Invalid or stale messages cause a coded reconnect and cannot restore old authority.

**A failed request never ends the session** ([0032](decisions/0032-the-player-continues-centrals-plan.md)). In `_control_loop`, `_media_loop` and `_observation_loop` a failed request (any `UplinkError` but a redirect and `local_pool`, an `httpx.HTTPError`, a `ServiceError` from a reply, a `ValidationError`) is named as a fault and the loop tries again at its next turn; only a refused registration (`Unauthorized`), a redirect, a request that never left its pool, and a cycle that already lost its Central end the cycle (`ends_cycle`). The control loop builds the held plan's feedback whether or not its poll was answered, so downloads of the held plan's photos continue while Central answers any request, and a session's end never empties them: the next `_feedback` rebuilds the jobs from the held plan. An observation is sent while it names the held plan's epoch and plan at its revision or an earlier one (a Frame playing its continuation through an outage observes under the revision it held; Central judges the rest), and a failed send is tried again at the next turn, unless Central refused it (4xx). The `frames` key of the Player line carries each Frame's `continuing_since` (`Executor.continuing_since`: the show time it began drawing only continuation slots of the held plan; worded for people as "playing Central's continuation since 14:02"). Run's first poll of a new cycle still ends that cycle when it fails: authority is reconciled before any download work.

## Independent clock probe

Show time is Central's time, carried on the Player's own monotonic clock ([`player/show_clock.py`](../player/show_clock.py) `ShowClock`; [execution contract](execution-contract.md#time-and-current-state-reveal), [0031](decisions/0031-show-clock-and-late-join.md), amended by [0032](decisions/0032-the-player-continues-centrals-plan.md)). Every Central answer that names this registration is a sample: each state answer (`State.server_time`) and an authenticated `GET /v1/player/time` probe, asked once a second on its own one-connection HTTP client, apart from the plan, so a failing time route never holds a plan back. A sample for another Player or epoch is refused and leaves the clock untouched. The Player measures transport RTT through complete bounded-body receipt (monotonic send and receive readings) and takes Central's reading at the interval's midpoint. It never reads the Pi's wall clock for the show.

**Any answer anchors; the bound is a quality, never a gate.** A sample's bound is half its round trip, however slow: a 6 s answer anchors at ±3 s. Between samples the bound grows by `DRIFT_RATE` (100 ppm). A later sample consistent with the estimate never loosens it, one that overlaps narrows it to the intersection, and one that disagrees beyond it re-anchors at its midpoint; an impossible one (non-finite or negative RTT) is counted and changes nothing. There is no healthy threshold and no forget. Until the first sample the clock is not anchored, the Player reports no readiness, and nothing is due or expired. The bound travels in every readiness report (`clock_uncertainty`), where Central widens that Frame's hand-over guard by it. Diagnostics (`ShowClockDiagnostics`) are bounded: status (`no_sample`, `anchored`), RTT, uncertainty, sample age, and sample, accepted and rejected counters. A failed time request is named like any other request (`_fault_for`; there is no `clock_probe` fault). The endpoint samples time; it never sets the system clock. systemd-timesyncd, in the base image, disciplines the Pi's wall clock for what still reads it (the display power timetable, the card's "since"), and the kernel's verdict on it is the host fact `wall_clock` ([runbook](runbook.md#the-pis-clock-and-its-time-client)).

## Health and release trial

The Player writes no health file: the V1 `service-health.json` sample, which nothing on a Node read, was deleted in PR 45. A missed dispatch deadline is the `main_loop_late` fault.

The service sends connected, unbound Output IDs and its local Central-link
diagnostic state to the Renderer on the Player's owning thread. The state is
`connecting` before configuration has been applied, `reachable` after a
successful state exchange, or `retrying` following a failed control exchange.
The retrying wording records whether this process has received configuration
before. It describes the last observed control exchange; it is not boot health,
current readiness, or evidence that the panel displays content. Only connected
unbound Outputs show the diagnostic, so bound content is unaffected. The
Renderer owns the local status page's presentation but not link-state decisions.

The journal line for faults is `player fault: <code> <detail>`, logged once per change of code. Network failures use `<cause>_<reason>` codes (e.g. `tls_untrusted`, `time_not_yet_valid`, `redirect_unexpected`, `connect_refused`, `dns_failed`, `central_error`, `http_status`, `transfer_short`; `local_pool` when a request never got a slot in the Player's own connection pool, with no host, since nothing about Central was learned), and the detail is `cause=... reason=... host=... detail=...` plus the stage-1 clock record for time and untrusted-TLS failures. Service codes (e.g. `registration_required`, `media_download`) are unchanged; `clock_probe` is gone ([0032](decisions/0032-the-player-continues-centrals-plan.md)).

The earlier signed-release boot-health trial has been retired: every boot is ticketless, so there is no per-boot signed release trial or trial watchdog to disarm. The Player also writes current process health locally to the health file. The hardware watchdog that stage 1 arms and hands to systemd ([0014](decisions/0014-reaching-central-from-every-boot-stage.md)) is systemd's to pet; the Player never touches it.

On a Node the Player runs from its sealed app root as `python3 -I -B /usr/lib/photo-wall/player --config /etc/photo-wall/public.json` ([Player package](module-player-package.md)); the Node binds `/etc/photo-wall/public.json` over the root. The public configuration shape is:

```json
{
  "schema": 1,
  "central_origin": "https://photo-wall.example",
  "ca_file": "/etc/photo-wall/ca.pem",
  "cache_dir": null,
  "cache_bytes": 536870912,
  "decoder_limit": 4,
  "texture_budget": 536870912
}
```

`cache_dir=null` uses a process-owned temporary directory. A deployment may point it at a writable cache path to reuse surviving bytes, but availability and correctness never depend on that path. Bootstrap/release configuration is separate.

`ca_file` is an absolute path to a PEM bundle used **instead of** the Debian bundle (`/etc/ssl/certs/ca-certificates.crt`) for every Central request (locate, httpx, and WebSocket). One trust store per process.

The schema forbids unknown keys; the retired `boot_context_file` and `allow_http` keys are refused.

The systemd sandbox keeps the Wayland runtime visible and grants the Player write access only to its runtime health directory and any explicitly configured cache directory. Native namespace boot and exact-image testing remain required to qualify the built unit.

`player.service` and every module it loads also load inside Central's image, whose qualification runs Player-side tests there. A package only the Pi has (GStreamer's `gi`, `segno`, EGL and gbm through ctypes) is therefore imported or opened inside the function that uses it, never at module load. `tests/test_node_rollout_image_check.py` holds this on every pull request: it loads the image qualification's modules and suites with only the image's runtime and pytest distributions importable.

## Acceptance boundary

Service tests cover fresh enrollment/session rotation, a session that survives a failed request and keeps its downloads, earlier-revision observations, stale grants and revocations, current-state reconciliation, independent time-probe diagnostics, bounded bodies and redirects, cancellation during media transfer, valid surviving-cache reuse, corrupt-cache reacquisition, and real central HTTP integration. The complete exact-image native path, process restart/reboot on built artifacts, failed-candidate reboot, and physical Pi/PXE/dual-HDMI behavior remain acceptance work in [validation](validation.md).
