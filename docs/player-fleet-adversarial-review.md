# Adversarial review: Player control and fleet architecture

**Status:** proposed design corrections for review; no implementation or deployed qualification. **Scope:** F0–F4/F6 in the [v0.13 readiness intake](production-readiness-v0.13.md). This review challenges the [control-protocol](player-protocol-compatibility-design.md) and [fleet-control](player-fleet-control-design.md) proposals against current source and failure traces. It records the first cross-boundary invariants and module contracts; the subsequent [red/blue refinement](player-fleet-red-blue-refinement.md) tightens trust, transactions, maintenance and qualification. The linked proposals own their feature-specific wire and rollout choices.

## Counterexamples the design must survive

| Trace | Unsafe conclusion | Required result |
|---|---|---|
| Unbound Player enrolls, parses state, has no live offer. | No accepted readiness means disconnected or incompatible. | Authenticated **control accepted** can be fresh while plan readiness is inapplicable. Current code emits readiness only with a plan ([Player service](../player/service.py)); Central rejects it without an offer ([coordination](../central/coordination.py)). The F0 regression fixture needs a bound active plan to assert readiness. |
| Repaired Central serves v0.12 Player, then traffic reaches an old v0.13 pod or that binary is restored. | A successful repair remains compatible during rolling deploy or rollback. | Every routable Central binary must emit the exact four-field legacy state. Drain or isolate incompatible pods; keep a repaired rollback artifact. Test the mixed-replica interval, not only endpoints. |
| Stage one receives HTTP headers/part of an image, then disconnects. | Serve record proves the image was consumed or failed. | Record an immutable **offer**; distinguish stage-one reported digest verification, OS-agent reachability, and base self-check. A missing receipt is unknown. The current route records a serve before streaming completes ([content route](../central/content_routes.py)). |
| Boot A requests, boot B requests, then A retries late; or two hosts claim one serial. | Greatest Central serve sequence identifies the physically current boot. | A serve sequence orders issuance only. Keep one immutable selection per boot nonce; overlapping claimants become ambiguous and cannot receive an automatic command or supersede accepted evidence. Serial/serve ID correlation is not device attestation. |
| Two phase changes occur in one uptime millisecond, or agent restarts. | Uptime uniquely orders observations. | Use a per-boot monotonic observation sequence retained in `/run` across agent restarts and a distinct agent incarnation; uptime is a sanity check. Replayed or reordered observations cannot erase a later fault. |
| Target package installs while the old process remains running and reporting readiness. | Fresh readiness after `dpkg` proves target digest runs. | Join an exact install attempt to an OS-observed new service invocation/process incarnation and a new authenticated app control session before accepting target. The present `.deb` post-install and installer do not themselves prove a restart ([package builder](../scripts/build_player_deb.py), [provisioner](../appliance/provision.py)). |
| Target installs; Central partitions before acceptance; Pi reboots and RAM staging disappears. | Silence proves target failure, or target may be retried forever. | Durable `unconfirmed`/`expired_unknown` outcome, bounded retry, then only an exact obtainable compatible previously accepted fallback; otherwise `recovery_required`. Do not promote either frontier. |
| App override is preflighted against one base; a newer fleet base is selected at next boot. | Independent app and OS policies imply the pair is compatible. | Resolve one exact compatible base/app pair per boot, binding digests and policy revisions. Keep each policy's owner separate. An invalid override is an explicit block, not silent fallback to fleet policy. |
| Online update stops a Pi with two Outputs in a multi-Frame Run. | Operator disclosure alone makes the stop safe. | Runtime/coordination must issue a fenced maintenance permit for all affected bindings, participants and leases before stop. A typed equipment-withdrawal outcome drives the declared Run policy; installation cannot implicitly finish or cancel authored work. |

## Proposed state and evidence types

Use stable typed identities across ports, with immutable values and compare-and-swap transitions. These names are conceptual, not a wire schema or a claim that current code implements them.

- `BootOffer(device_claim, boot_nonce, serve_id, base_digest, base_policy_revision, selected_app_digest, app_policy_revision)`: Central's immutable selection. Duplicate requests for the same boot nonce return the same pair or a named conflict, even if fleet policy changed. A response started is `offered`, never `delivered`.
- `BootObservation(offer_ref, kernel_boot_id, agent_incarnation, observation_sequence, phase, receipt_time)`: a claimed event from the base agent. Distinguish `stage1_verified_claim`, `agent_reached_claim`, `self_check_claim`, `observed_fault`, and `unconfirmed`; no observation implies rendered pixels. Receipt time determines freshness. A new claim cannot overwrite another boot merely by having a larger serve sequence.
- `AppAttempt(device_claim, boot_ref, desired_revision, attempt_id, target_digest, fallback_digest)`: durable Central transaction identity. The base agent retains a bounded crash-recoverable `/run` journal and verified package files for process restart within one boot. Central retains the accepted fallback digest and exact bytes as a cache/garbage-collection root for cold boot until the attempt resolves.
- `AppIncarnation(boot_ref, attempt_id, installed_digest, systemd_invocation, process_start_identity)`: OS-agent evidence that a specific package transaction launched a new service process. Pair it with a fresh app enrollment epoch and an app control handshake scoped to the same attempt. A self-reported package version is diagnostic, not binary proof. On a trusted host this is operational evidence, not cryptographic attestation against a compromised OS.
- `ControlSession(player_id, authority_epoch, schema_selection, control_accepted_at, app_incarnation_ref)`: app-level protocol fact. `control_accepted` means that a current authenticated process acknowledged successful parse/apply of a state delivery identified for that epoch, independent of a plan; replayed acknowledgments do not refresh it. `PlanReadiness` remains a separate fact valid only for the current offer, assignment, epoch and plan. `OutputObservation` remains separate from both.
- `MaintenancePermit(boot_ref, attempt_id, binding_generations, affected_run_ids, lease_fences, expiry, interruption_policy)`: a Runtime/coordination decision required before stopping a healthy Player. The installer validates it immediately before stop; changed bindings or Runs invalidate it.

An attempt reducer accepts only events that match its immutable boot, policy revision, attempt and digest. It distinguishes `queued`, `preflight`, `verified`, `installing`, `installed_local`, `acceptance_pending`, `accepted`, `observed_failed`, `expired_unknown`, `recovering`, and `recovery_required`. Transport timeouts enter unknown, never observed failure. Accepting an app requires the matching new incarnation, control acceptance, and whatever sustained plan readiness applies when a plan is active. An unbound healthy app can pass control acceptance while readiness is inapplicable. Base acceptance and output observation have their own gates. A safety fence may follow unknown without relabelling it failed.

## Layered ownership and narrow ports

| Module | Single owner and useful ports | Dependency direction |
|---|---|---|
| Installation registry | Device inventory/retirement, Player authority epochs and Frame binding generations; `resolve_device`, `validate_epoch`, `bindings_for_device`. | Other domains query it; OS observations never create Player authority. |
| Release catalog | Immutable artifacts, digest, size, compatibility metadata and verified byte availability/reservations; `resolve_exact`, `reserve`, `retain_fallback`. | Policy consumes catalog facts; catalog does not decide health or desired release. |
| Fleet policy and boot selector | Fleet/per-device desired app and OS base pin/frontier, independent revisions, exact compatible pair resolution; `select_pair`, `record_offer`. Legacy manifest routes are adapters with explicit capability tables. | Pure selection rules consume registry and catalog ports; HTTP routes do not reimplement precedence. |
| Boot ledger and OS observation intake | Immutable offers, claimed receipts, ordering, ambiguity and provenance; `record_observation`, `current_boot_evidence`. | Intake cannot grant command, accepted health or app authority from serial alone. |
| Agent command authority and app-attempt reducer | Boot-scoped command issuance, current attempt, transitions, fences and rollback eligibility; `get_desired_action`, `advance_attempt`. | Commands require a separately justified boot identity/authorization boundary; observations alone cannot authorize them. |
| App protocol compatibility | Per-epoch envelope selection and one pure `project_state` shared by HTTP and WebSocket; `pin_schema`, `control_accepted`. | No package-tag inference; coordinator receives immutable schema snapshots and fences stale epochs. |
| Coordination and Runtime | Offers, plan readiness, execution leases and maintenance impact/permits; `record_plan_readiness`, `admit_maintenance`, `record_equipment_withdrawal`. | Fleet cannot directly mutate Run completion/cancellation. |
| OS agent and package executor | Current-boot local facts, one installer for cold/online paths, verified files, `/run` journal, service process identity and error-display handoff. | Base owns management continuity; Player app owns execution; neither owns Central release policy. |
| Status projector | Read-only join of independently timestamped facts and their provenance; one classifier for console/API. | Projection does not grant authority or turn missing evidence into a failure fact. |

The dependency direction is domain policy → small ports → storage, HTTP, systemd, PXE, and renderer adapters. Reuse one package transaction and one status classifier. Durable records must survive Central restart; current-boot files need only survive agent restart, while exact fallback artifacts must remain obtainable after reboot.

## Trust and visible-output boundary

The current serial selector is supplied by the requester, so an opaque serve ID proves only correlation with an issued response. A LAN claimant can request a serve for another serial and echo its ID. **Under the current trust boundary, automated fleet-frontier promotion, failure attribution to a physical Pi, and update/reboot commands must not derive authority from check-ins.** The design needs a separately reviewed device-identity mechanism that remains compatible with plug-and-play PXE (for example, authenticated access-layer identity or a commissioned credential), or must keep those actions operator-confirmed and telemetry explicitly labelled as claims. A boot-scoped token delivered over a serial-only request does not solve spoofing. Duplicate claimants, overlapping boots and stale sessions fail closed for commands.

The base error surface needs a real owner and display handoff: define which base-owned compositor/DRM process can show diagnostics on **each** Output before `.deb` installation, while the app fails, and after an app crash; how it yields atomically to the Player; and how it returns without stealing active Scene pixels. Stage-one text is only a pre-OS path. A started unit is not proof of a visible diagnostic. Physical failure injection must qualify this boundary.

## Migration and qualification gates

1. Central's legacy projection must be on every serving replica and in the rollback artifact before claiming F0 recovery. Test the exact v0.12 package against mixed pods, both state transports, a bound active plan, unbound control acceptance, stale WebSocket sessions and rollback. A selected-schema database migration must remain readable by every binary allowed in the rollout.
2. Introduce additive observations first; preserve old boot-tree manifest semantics by an explicit capability matrix. Show a per-device app override as `queued, unenforceable by current base` until that base can execute it. New base against old Central must continue safe legacy provisioning on a known 404, without claiming the override applied.
3. Model-check the traces above with controllable event order, Central/agent crash at every attempt phase, cache loss, report replay, boot overlap and network partition. Assert that no source of weaker evidence can advance a stronger state. Exact packages and physical Pi/panel tests remain required for compatibility and visible output.
4. Before an implementation is accepted, reconcile the existing signed-root/ticket/Ubuntu descriptions in [requirements](requirements.md), [architecture](architecture.md) and [execution contract](execution-contract.md) with the current Debian, unsigned and ticketless path and the reviewed trust decision. The current documents describe incompatible deployment contracts; this review does not silently alter product requirements.

These contracts can prevent false state transitions and unsafe automatic actions. They cannot make network loss, hardware failure or a compromised LAN impossible; those cases remain explicit `unknown`, `ambiguous` or `recovery_required` outcomes.
