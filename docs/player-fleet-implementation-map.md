# Player fleet implementation map

**Status:** source-grounded implementation map with code staged in the current PR, not a deployment or physical qualification record. **Scope:** F0–F4/F6 in the [production-readiness intake](production-readiness-v0.13.md). The [control-protocol design](player-protocol-compatibility-design.md), [fleet-control design](player-fleet-control-design.md), [red/blue safety contract](player-fleet-red-blue-refinement.md) and later [node domain model](player-node-domain-model.md) own behavior in their stated stages. The node model is the selected target; this map primarily describes code already staged in the PR. This page distinguishes implemented foundations from activation and qualification gates.

## Dependency order and claimable slices

| Slice | Module boundary and deliverable | Gate before a stronger claim |
|---|---|---|
| F0a: published-app recovery | One pure Central state projector feeds REST and WebSocket; Registry refuses Identify for unnegotiated sessions. Legacy wire state has exactly four fields. | Exact published v0.12/v0.13 package fixtures against warm/cold sessions, bound readiness and both transports; a compatibility-safe serving and rollback binary. |
| F0b: negotiated application control | Registry owns epoch-scoped schema selection and applied-control evidence; a shared protocol contract owns hello, delivery challenge and acknowledgment; Player service negotiates before its first state read. | Expand DB and deploy every routable Central pod before requiring hello. Test concurrent hello/read, re-enrollment, duplicate/replayed acknowledgments and a later rejection with an older `applied_at`; report the latest result separately from historical application. |
| F1/F2: observational base | Additive Central boot-offer/check-in records and one read-only status projector; initramfs hands an exact offer reference into the new root; a base-owned agent reports independently of app install. | Mount production routes and boot-tree service only after old Central/base compatibility, stage-one restart and real switch-root readback, quota/TTL and report ordering tests. Show a delayed old-boot report as a T0 claim, not current physical boot. No remote action follows a check-in. |
| F3: desired app and operator view | Fleet policy owns fleet target and per-device app override separately from base pin; catalog resolves immutable compatible artifacts; Equipment UI shows desired, offered, installed, running and assurance/age. | Legacy aliases explicitly unverified; surface policy source/revision, local byte availability and ABI provenance. An override on an incapable base is `queued, unenforceable`; no claim that promotion updates a running process. |
| F4/F6: managed activation/recovery | Staged base executor, data-only artifact contract, durable Central attempt and Runtime drain; target HostCore/broker split, release-built Debian closure, base Display Host, exact fallback and cohort acceptance. | D15 target is amended and D14 selects LAN-serial command trust, but neither new schema nor production verifier/route exists. D16 planned withdrawal and D17 mixed-version rollout remain open. Exact fallback/capacity, physical two-Output qualification and compatible rollback are required. |

The F0a and F1 observational slices can proceed independently. F0b and F3 can expand records and UI before F4 is activated. A T0 serial-only base never earns command or automatic frontier authority from a fresh check-in alone. The selected `lan_serial` command path requires a separate boot-scoped session, scoped route and exact command/permit, with weaker claimed-device assurance; it is not staged in this PR.

### F3 app observation slice: module contract

The base-owned OS agent samples the data-only executor's selected root and current systemd process through the existing read-only `AppEvidenceCollector`. It sends schema-2 observations to `/v2/appliance/check-ins`: all schema-1 fields plus one bounded `app_evidence` value containing `kernel_boot_id`, `installed_sha256`, `running` (`sha256`, `pid`, `start_ticks`, `invocation_id`), and named installed/running unknown reasons. The collector's boot ID must equal the report's boot ID. A sampling failure still produces a base check-in with unknown app evidence; it cannot silence OS liveness. The observer owns transport and sequence; the executor owns installed-root verification; neither owns acceptance or commands.

Central admits schema 1 and 2 through one quota, offer-correlation, and sequence boundary. Schema 1 stays byte-for-byte valid. An additive observation migration stores optional app fields; old rows project unknown. An agent retries the same sample on schema 1 only when a located Central returns the canonical unsupported-route response for v2. Other errors never cause downgrade. Both versions return the same receipt vocabulary and share the per-boot sequence high-water mark, so a mixed pod cannot count two accepted reports for one sample.

The fleet projector chooses the same most recently received boot claim for base, installed, and running facts, and exposes digest, process identity where present, age, boot ID, source `serial_claim`, assurance `t0_unverified`, and `boot_linkage: claim_only`. Unknown collector reasons are diagnostic, not proof of absence. A later old-boot report remains visibly ambiguous with the latest offer. Equipment labels these as **reported** installed/running facts and never offers an action or marks an artifact accepted from them. This slice is complete in software when v1/v2 mixed Central behavior, absent/invalid collector evidence, stale sequence, delayed old-boot claims, and strict no-command receipts pass ingress/database/agent checks. Physical Pi output and command trust remain separate gates.

App evidence sampling has a short independent deadline and at most one in-flight collector. The OS agent reports `evidence_unavailable` if the collector is slow, while still sending its base check-in; it never reuses an old app sample as if it were current. A completed late sample is discarded. The collector takes short read-locked snapshots of the terminal journal, selected digest and attempt identity before and after root verification and PID1 sampling. Digest-named published roots are immutable to the executor; verification and systemd calls run outside the mutation lock. If the snapshots or process identity differ, the result is unknown. An exclusive activation/recovery lock refusal named `executor_busy` is transient: the provisioner retries the same exact local operation with bounded waits and watchdog renewal rather than treating contention as an app failure. All other executor errors keep their existing recovery-required behavior. Tests must simulate slow collection and concurrent activation to prove OS telemetry cadence, coherent snapshots and the one-writer mutation invariant.

## Staged implementation and remaining proof

- **F0:** Central and Player stage schema negotiation, an exact four-field legacy state projection, delivery sequence/digest acknowledgment and separate latest-result versus historical-applied facts. CI now runs the published v0.12/v0.13 Player enrollment method against Central challenge/register HTTP routes, then feeds Central REST/WebSocket bytes and bound readiness through those digest-pinned packages. A full packaged process with real network/rendering, every routable Central replica and a behavior-compatible rollback binary still need the ingress compatibility matrix.
- **F1/F2:** Central stages immutable boot offers, exact byte routes, bounded T0 check-ins and a status projector; the production boot tree stages offer verification, switch-root handoff and a resident base OS observer. Stage two rejects a present stale or invalid handoff, and a corrupt same-boot nonce cannot mint a second offer identity. These are distinct from Player enrollment and readiness. A serial, offer ID or latest received check-in is a **claim**, not physical boot identity, command authority or automatic frontier evidence. Old bases show OS telemetry unavailable; mixed boot trees and physical switch-root remain to be qualified.
- **F3 and D15:** Separate fleet app policy, per-device app override and base baseline records stage exact digest/size and source/revision provenance. The base ABI is independently sealed from the base build and final squashfs; the payload declares its required ABI. An ABI match is distinct from a same-tag, unverified co-release. `manifest.json` and the `.deb` remain the schema-1 legacy contract; optional `manifest.v2.json` carries the inert `pw-player-data-v1` archive. The base-owned launcher/executor repairs interrupted local attempts before Central discovery, and a release probe now starts the built data payload through the base unit. A local collector verifies the selected installed root and a stable systemd process sample, and the agent sends them as bounded schema-2 T0 claims to Central. They are not acceptance evidence. Online update, cross-boot fallback, package-failure continuity and physical handoff remain unqualified.
- **F4/F6:** A durable Runtime drain foundation fences offers, readiness, media grants and equipment writes. Public preparation is limited to the unbound canary until D16 defines due Program behavior; bound preparation now refuses before changing durable state. Stop admission rechecks due active Runs under the Coordination and Runtime locks; a refusal leaves an existing prepared drain fenced. Unbound preparation/commit freezes every Output's inventory and observation and rechecks them before commitment; it is not a stop permit. The base executor refuses a healthy-app stop when measured RAM or writable-space headroom is insufficient, using provisional reserves that still need physical qualification. A Central fallback reservation retains a same-device schema-2 exact payload locator only for a separately accepted T1/T2 artifact and hashes bytes available on one serving pod; T0 reports cannot create acceptance. Reservations rotate to one current digest; the exact attempt-byte retention view releases only by an explicit lifecycle decision after any issued stop. A queued AppAttempt now freezes target/fallback locator, size, ABI and provenance with two attempt-owned roots in one transaction; canceled queued roots require explicit lifecycle release. The current accepted reservation can source a first locator only from a boot offer, so an accepted online target still needs a separate promotion writer before it can become the next fallback. A device lifecycle generation, revocable OS-session schema, strict command envelope and root-only inert OS command inbox are staged separately from the T0 observation and app channels. There is no acceptance writer, authenticated command verifier or command route, and no automatic stop. Historical bound drains can still be reconciled, but due Program handling, `stop_committed` reconciliation and per-Output diagnostics remain D16 work. Current command routes remain unmounted; the selected `lan_serial` verifier, versioned schema and D17 deployment gate are absent. D16 gates planned healthy-app stops, not immediate operator reboot. Automatic base-frontier qualification remains separate and requires the declared assurance/evidence tier.
- **F3 maintenance intent seam:** The operator console can queue a bounded request against the current device generation, explicit or override policy revision and exact payload artifact, and cancel it by revision. The database freezes the selected tag, digest, size, base ABI and manifest provenance; queued intent expires, closes on device retirement, and never creates an attempt, drain, OS session or stop. The `dispatched` status is reserved for a future handoff, not evidence of execution. This is an honest operator workflow while F4 authority and Runtime policy remain gated.
- **F4 pre-effect seams:** Internal attempt-byte access resolves only the frozen target/fallback refs under a current T1/T2 principal, hashes bytes on the serving pod, and rechecks authority after byte I/O. A separate data-only HTTP module exposes exact attempt bytes and bounded report intake only when a caller injects a T1/T2 request verifier; no production composition root mounts it. The cache can rehydrate a retained attempt after a release recut or offer expiry. The base executor's online preparation accepts a neutral attempt value, requires the running exact root to equal the fallback, checks the sealed base ABI and stable process identity, and stages fallback then target under a provisional capacity bound without stopping the app. The Player now has a separate, nonblocking local key-proof client; a base-owned socket service checks per-packet Linux credentials and one-use challenge context before an injected compare-and-store sink may record volatile proof. The base package carries that service and seals the proof contract into its ABI, but does not install or enable a socket unit because no protected T1/T2 context provider/sink exists. A future acceptance writer must bind the signed key to the claimed Player and authority epoch in the authenticated Registry session. No Output evidence or acceptance writer is composed. These facts are prerequisites, not a remotely executable update.
- **F4 evidence storage seams:** The Linux proof adapter brackets PID1's Player invocation against `/proc` process and cgroup facts; the local service additionally checks kernel credentials on both `SOCK_SEQPACKET` packets, rejecting a different later writer on a passed socket. The proof socket remains unmounted in production. A PostgreSQL append-only store accepts bounded OS attempt reports only under a current T1/T2 principal and a matching post-stop attempt, with monotonic sequence and exact replay. A new attempt freezes its issuing OS command session, and byte/report access rejects a different or historically unbound session. Future accepted artifacts live in a generation-scoped table; legacy accepted rows remain historical and cannot qualify a new fallback after recommissioning. A nested proof must match the report's command session, and its trust mode must match the carrier principal. These rows do not certify the reported app process, control adoption, Output buffers or rollback eligibility. The read-only acceptance projector therefore returns refusal reasons and cannot authorize promotion.
- **F4 causal control proof seam:** Registry now mints a random receipt only in the transaction that accepts an applied v2 control ACK, returns it on exact current-delivery retry, and invalidates it on supersession or later rejection even when an older Central pod writes the control row. The Player sends that receipt asynchronously through a separate V2 local proof exchange. The base-owned socket signs a new domain bound to the protected active app root and current process/session context, while V1 bytes remain unchanged. Player invalidates its worker on a newer delivery, rejection, re-enrollment or shutdown. This volatile local proof is not submitted as accepted health: a future authenticated writer must join the receipt to the current Registry row, match the same process and each Output handoff, and then decide whether an immutable acceptance is justified.
- **D16/D17 pre-effect seams:** Runtime reads and direct commands now take the shared Coordination→Runtime advisory-lock order, and `Coordinator.advance()` samples time after both locks. Runtime hydrates an immutable admission policy from active drain snapshots in the same read cut, carries it through projections, rejects new manual/force/restart/queue activation of affected Scenes, and lets preexisting queued items wait only until their expiry. Drain prepare and abort persist Runtime at their post-lock barrier cuts. The unbound drain can prepare and commit through a caller-owned transaction after that lock cut, and the unmounted internal issuer now commits it with an attempt and permit; these helpers still issue no command. A durable fleet effect gate starts closed and accepts a new generation only through an injected deployment verifier that certifies every serving image, rollback cohort, route/EndpointSlice inventory and compatibility/fence/readiness evidence. Future effect writers must hold its shared row lock through commitment, match a trusted local serving-image measurement, and recheck lease expiry after downstream lock waits. No production verifier or command route is installed. Due Programs and bound Run/Actuator interruption still need D16 decisions; the separate IaC deployment must enforce close-before-endpoint-mutation and certify the actual serving path before D17 can open.

The immutable generation-scoped acceptance table is historical evidence, not by itself a bounded cache root. The current base-GC query conservatively retains every accepted base in a live generation. It must not be narrowed until a trusted acceptance writer can atomically select one current base frontier and keep the previous base under an explicit rollback lease through reconciliation; neither writer nor lease exists yet. Narrowing GC early could evict bytes still needed for rollback. Existing pre-session attempts also retain a null issuing session after the additive migration; an attempt at the same offer and policy revision cannot be rebound to a new session. Command activation must first quiesce those legacy rows or add an explicit unstarted-attempt supersession transaction without rewriting history.

The original exact-byte and outcome-report paths still require the issuing OS session. A separate **unmounted recovery data adapter** now accepts only an injected current T1/T2 carrier principal and a short-lived CAS lease over the original immutable attempt. Historical drains have no `fleet_drain_id` and are ineligible. Admission requires the matching `stop_committed` drain, its exact UUID link, the immutable stop permit, the current device generation, unreleased exact target/fallback roots and no explicit terminal lease revocation. The lease exposes only those two retained payloads and append-only claims; per-carrier report sequence continues across lease renewal and resets for a newly verified boot. The original issuer identity remains frozen, and neither claims nor a lease certify accepted bytes, permit another stop or select another target. The unmounted internal issuer now populates `fleet_drain_id` atomically with the ready-to-stop permit. No production verifier mounts these routes, and closing new-command admission must leave this narrow repair path available on a certified binary. A healthy fallback process still requires a fresh command before it can be stopped again.

The 2026-09-29 [netboot tracer](../scripts/test_netboot_e2e.py) invokes the exact installed bootstrapper closure for one schema-2 OS check-in before Player installation and another after a packaged, one-attempt corrupt-package refusal. It checks Central's HTTP projection and committed PostgreSQL rows for continuing T0 base claims, unknown app state and no acceptance. These are separate one-shot `docker exec` calls: the gate does not start the installed `photo-wall-os-agent.service`, keep a resident agent running across the refusal, or qualify its systemd cadence, a Pi boot or mixed Central pods.

A separate 2026-09-29 [built-base service probe](../scripts/os_agent_service_probe.py) is staged for CI. One container boots the final squashfs to `multi-user.target` with the provisioner masked, checks the agent's enablement link, and requires a schema-2 report without manually starting the agent. A second container starts the installed OS-agent unit under container systemd, records its process identity and first schema-2 report, starts the provisioner against a deliberately corrupt Player package, and requires a later `app_integrity` report from the same agent process and incarnation. Its local HTTP recorder isolates service continuity; it does not qualify Central persistence, a Pi boot, display output or mixed pods.

The unmounted internal `FleetCommandLifecycle` now creates one immutable command from a current explicit/override maintenance request, a rooted exact AppAttempt, and a prepared unbound drain under the default-closed deployment gate. A separate ready-to-stop transaction records an immutable permit and the drain/attempt stop commitment together. Exact replay checks the current carrier, gate and deadlines after waits; an already issued permit can replay despite a later desired-policy change, while a pre-stop command cannot proceed under that change. Migration 052 rejects a new unbound stop commitment without the matching permit in the same transaction, and migration 050 freezes prepared unbound identity/snapshot and the entire committed drain. These are internal transaction seams, not a production command route or proof that the OS stopped. A prepared command that never reaches stop still needs authenticated base-journal no-stop reconciliation before its drain and roots can be released; timeout alone is insufficient. The operator status view separates these durable records from OS claims and unknown physical output.

## Current seams and proposed owners

- `central/coordination.py` owns plan delivery, readiness, offers and commits. Its rich internal delivery should pass through one app-protocol projector before `central/app.py` REST or WebSocket serialization. `central/registry.py` owns bearer/epoch validation, per-epoch schema selection and Identify; it must recheck identity under its player-row lock, then release that lock before coordination delivery. A negotiated challenge binds an epoch and projected state digest; only a matching, once-consumed applied acknowledgment refreshes control acceptance.
- Central fleet policy and status need a narrow module boundary separate from registry and catalog. Catalog owns release discovery, exact byte availability and the legacy manifests; fleet policy owns desired revision, immutable BootOffer/AppAttempt, assurance and observation reducers. SQL records need transaction ports rather than direct catalog-to-Runtime writes. Existing `known_good_tag`, `last_good_tag`, `boot_outcome` and automatic promotion are legacy tag-based evidence, not accepted exact-digest fallback. Additive migration must keep old routes and record their weaker provenance. An offer lookup that returns metadata without opening and leasing exact bytes, or a T0 projection that treats latest receipt as current physical boot, cannot satisfy the activation gate.
- `appliance/netboot_init.py` stages a validated exact offer handoff through switch-root, and `appliance/os_agent.py` stages an independent observer. The data-only archive, base-owned launcher and executor are separate from the old root-running `.deb` path. The actual built boot tree, single executor/cgroup ownership and display host need integrated and physical qualification; observation sequence state stays separate from package mutation state. Old boot trees keep their legacy cold path.
- Runtime owns equipment withdrawal and maintenance fencing. The staged idle-only drain uses coordination→Runtime→registry serialization, cancels old groups and rejects new offers/grants; `stop_committed` never time-releases. Active multi-Frame Run/Actuator policy, production permit delivery, post-stop reconciliation and per-Output handoff remain unimplemented gates; an internal unbound-only permit record is staged. The lifecycle owner, not the installer, decides multi-participant Run effects.
- The staged OS command contract binds audience, device generation, boot, offer, session, attempt, desired revision, drain, exact target/fallback and deadline. Parsing a command grants no authority. The staged internal verifier type accepts only T1/T2 and is not mounted. The selected target instead needs a new `lan_serial` command-capable offer/audience/session schema and separate root-only HostCore reboot and broker effect scopes; current T0 BootOffers cannot be silently relabeled. Central must match the boot-scoped claimed-device session and immutable attempt under lock, while reporting that the session does not authenticate a physical Pi. The command gate remains closed until the new verifier, route and D17 rollout certification exist. The base must stage and verify both exact roots before stop, then check the current permit and session. Fallback reservation supports prefetch, but there is no scheduled in-process asset-cache GC today; external cache loss remains possible, so a database root alone is not stop-safety evidence.
- The console currently reads inventory/Runtime in one operator snapshot and boot facts separately. Fleet status either joins them in one read transaction or shows distinct read times. `OS telemetry unavailable`, `boot linkage unknown`, and `fallback unverified` remain visible during migration.

## Integration order and activation boundary

1. Apply additive F0/F1 tables while old Central binaries still serve; prove every allowed old binary tolerates them. Route legacy four-field state from **every** pod before any Player depends on hello, and deploy only a rollback binary with the same compatibility behavior. Persist an acknowledgment's latest result/time independently of its earlier applied time.
2. Wire the bounded base observation path into the actual Central composition root and production boot tree. The boot-offer POST, exact base/app GET and check-in POST need explicit route tests through ingress and mixed pods; a helper module or isolated client test is not a deployed feature. Preserve an immutable nonce-to-pair record or refusal tombstone across payload GC; verify or rehydrate exact bytes on each serving pod and lease the stream. If an artifact is absent, return named unavailable for the same offer. A T0 rate-limit response must preserve base provisioning.
3. Project fleet status from separately timestamped OS, app and Output facts. The latest receipt from boot A after boot B's offer does not prove A is current; show its boot and uncertainty. Join current F0 `ControlApplied` only for the matching app authority epoch, and show a later rejection as the current diagnostic while retaining the earlier applied acknowledgment as history. Do not infer app liveness from missing plan readiness on an unbound Player.
4. Activate F3 desired policy only after exact digest/size, release-source and base/app ABI provenance are available. Preserve separate fleet and per-device compare-and-set revisions (including override deletion tombstones), distinguish explicit empty policy from legacy promotion fallback, and snapshot that source plus compatibility basis in each offer. Revision-zero legacy promotion must not be projected as an explicit fleet choice. Mark mirror metadata separately from per-pod file availability. Keep F4 commands, automated F6 acceptance/frontier and maintenance effects gated by the [red/blue contract](player-fleet-red-blue-refinement.md#rollout-and-decision-gates) and owner decisions.
5. Before an online target can become a future fallback, create an immutable AppAttempt snapshot with exact target and fallback digest, size, ABI and source locator, plus attempt-owned artifact references, in one fleet-locked transaction. Keep roots until an explicit `root_released_at` lifecycle decision; phase and command revocation alone cannot release bytes after an issued stop. On separately qualified acceptance, copy the target's frozen locator into the bounded fallback reservation before releasing attempt roots. Rehydrate and preflight from these frozen facts after release-tag recuts and offer expiry. A T0 report or a quiet unbound app does not qualify acceptance.

## Verification and decisions

Use controllable-clock tests for lock ordering, replay, acceptance, expiry and crash reconciliation. Add database/ingress races for two pods issuing the same boot offer, quota exhaustion and cleanup, delayed old-boot reports, an expired nonce that cannot select different bytes, one pod missing offer bytes, mixed F0 protocol pods and an old applied acknowledgment followed by rejection. Use exact release packages for the F0 compatibility matrix, staged old/new boot trees for rollout, and physical Pi/panels for switch-root, package continuity, first-buffer handoff and visible diagnostics. Exercise an agent that stays healthy while its executor hangs, a cache loss after stop, a tag alias moved to new bytes, and one Output ready while another stalls. Record test artifacts and limits in [evidence](evidence/README.md); green Central endpoints or simulated Players do not establish pixels.

The PR stages the former [D15 data-only direction](design-decisions.md); the [Player node domain model](player-node-domain-model.md) now owns the target Debian-closure and HostCore/broker split. Existing V1 rows and code remain transitional. [D14](design-decisions.md) now selects trusted-LAN/serial command trust, but the PR still has no production verifier or command route. [D16 and D17](design-decisions.md) remain open for planned app-update withdrawal and mixed-version rollback. Operator reboot remains disabled until its selected `lan_serial` verifier/route and D17 rollout gate are implemented; it does not require D16 planned withdrawal. Healthy-app upgrade stop and automatic health frontier remain disabled until their respective D16, exact fallback/capacity and physical qualification gates are satisfied.

The first proposed executable canary is an **unbound** Player. Its drain can prove that the whole observed Output inventory remains unbound at both preparation and command commitment. A bound Player needs an immutable Runtime admission policy derived from the active drain table under the Runtime lock and consumed by due Programs, manual/queued activation, `force`, `restart` and nested Scene participants; the current Coordinator can advance a Program logically while its display delivery is fenced. The D16 review recommends one recorded skip for a due Program, whole-root interruption with Actuator safe-state acknowledgment, and time cuts before barrier insertion/removal; these are not selected product behavior. Any future command route also needs a deployment-supplied, digest-bound check that every routable and rollback Central image enforces active drain and attempt fences on the legacy app, netboot, control and media paths. The [2026-09-30 live audit](evidence/2026-09-30-command-rollout-audit.md) shows a direct Service LoadBalancer/NodePort path and no Kubernetes rollout controller in this repository, so a local environment flag cannot establish that condition. These are D16/D17 proposals, not claims of activated commands.
