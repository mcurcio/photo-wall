# Player fleet implementation map

**Status:** source-grounded implementation map with code staged in the current PR, not a deployment or physical qualification record. **Scope:** F0–F4/F6 in the [production-readiness intake](production-readiness-v0.13.md). The [control-protocol design](player-protocol-compatibility-design.md), [fleet-control design](player-fleet-control-design.md) and [red/blue safety contract](player-fleet-red-blue-refinement.md) own behavior. This page distinguishes implemented foundations from activation and qualification gates.

## Dependency order and claimable slices

| Slice | Module boundary and deliverable | Gate before a stronger claim |
|---|---|---|
| F0a: published-app recovery | One pure Central state projector feeds REST and WebSocket; Registry refuses Identify for unnegotiated sessions. Legacy wire state has exactly four fields. | Exact published v0.12/v0.13 package fixtures against warm/cold sessions, bound readiness and both transports; a compatibility-safe serving and rollback binary. |
| F0b: negotiated application control | Registry owns epoch-scoped schema selection and applied-control evidence; a shared protocol contract owns hello, delivery challenge and acknowledgment; Player service negotiates before its first state read. | Expand DB and deploy every routable Central pod before requiring hello. Test concurrent hello/read, re-enrollment, duplicate/replayed acknowledgments and a later rejection with an older `applied_at`; report the latest result separately from historical application. |
| F1/F2: observational base | Additive Central boot-offer/check-in records and one read-only status projector; initramfs hands an exact offer reference into the new root; a base-owned agent reports independently of app install. | Mount production routes and boot-tree service only after old Central/base compatibility, stage-one restart and real switch-root readback, quota/TTL and report ordering tests. Show a delayed old-boot report as a T0 claim, not current physical boot. No remote action follows a check-in. |
| F3: desired app and operator view | Fleet policy owns fleet target and per-device app override separately from base pin; catalog resolves immutable compatible artifacts; Equipment UI shows desired, offered, installed, running and assurance/age. | Legacy aliases explicitly unverified; surface policy source/revision, local byte availability and ABI provenance. An override on an incapable base is `queued, unenforceable`; no claim that promotion updates a running process. |
| F4/F6: managed activation/recovery | One base executor, data-only artifact contract, durable Central attempt and Runtime drain, base display host, exact digest fallback and cohort acceptance. | D15 selects the data-only direction; D14, D16 and D17 remain open. An approved command path, exact fallback retention/capacity, physical two-Output qualification and behavior-compatible rollback are still required. |

The F0a and F1 observational slices can proceed independently. F0b and F3 can expand records and UI before F4 is activated. A T0 serial-only base never earns command or automatic frontier authority from a fresh check-in.

### F3 app observation slice: module contract

The base-owned OS agent samples the data-only executor's selected root and current systemd process through the existing read-only `AppEvidenceCollector`. It sends schema-2 observations to `/v2/appliance/check-ins`: all schema-1 fields plus one bounded `app_evidence` value containing `kernel_boot_id`, `installed_sha256`, `running` (`sha256`, `pid`, `start_ticks`, `invocation_id`), and named installed/running unknown reasons. The collector's boot ID must equal the report's boot ID. A sampling failure still produces a base check-in with unknown app evidence; it cannot silence OS liveness. The observer owns transport and sequence; the executor owns installed-root verification; neither owns acceptance or commands.

Central admits schema 1 and 2 through one quota, offer-correlation, and sequence boundary. Schema 1 stays byte-for-byte valid. An additive observation migration stores optional app fields; old rows project unknown. An agent retries the same sample on schema 1 only when a located Central returns the canonical unsupported-route response for v2. Other errors never cause downgrade. Both versions return the same receipt vocabulary and share the per-boot sequence high-water mark, so a mixed pod cannot count two accepted reports for one sample.

The fleet projector chooses the same most recently received boot claim for base, installed, and running facts, and exposes digest, process identity where present, age, boot ID, source `serial_claim`, assurance `t0_unverified`, and `boot_linkage: claim_only`. Unknown collector reasons are diagnostic, not proof of absence. A later old-boot report remains visibly ambiguous with the latest offer. Equipment labels these as **reported** installed/running facts and never offers an action or marks an artifact accepted from them. This slice is complete in software when v1/v2 mixed Central behavior, absent/invalid collector evidence, stale sequence, delayed old-boot claims, and strict no-command receipts pass ingress/database/agent checks. Physical Pi output and command trust remain separate gates.

App evidence sampling has a short independent deadline and at most one in-flight collector. The OS agent reports `evidence_unavailable` if the collector is slow, while still sending its base check-in; it never reuses an old app sample as if it were current. A completed late sample is discarded. The collector takes short read-locked snapshots of the terminal journal, selected digest and attempt identity before and after root verification and PID1 sampling. Digest-named published roots are immutable to the executor; verification and systemd calls run outside the mutation lock. If the snapshots or process identity differ, the result is unknown. An exclusive activation/recovery lock refusal named `executor_busy` is transient: the provisioner retries the same exact local operation with bounded waits and watchdog renewal rather than treating contention as an app failure. All other executor errors keep their existing recovery-required behavior. Tests must simulate slow collection and concurrent activation to prove OS telemetry cadence, coherent snapshots and the one-writer mutation invariant.

## Staged implementation and remaining proof

- **F0:** Central and Player stage schema negotiation, an exact four-field legacy state projection, delivery sequence/digest acknowledgment and separate latest-result versus historical-applied facts. CI now runs the published v0.12/v0.13 Player enrollment method against Central challenge/register HTTP routes, then feeds Central REST/WebSocket bytes and bound readiness through those digest-pinned packages. A full packaged process with real network/rendering, every routable Central replica and a behavior-compatible rollback binary still need the ingress compatibility matrix.
- **F1/F2:** Central stages immutable boot offers, exact byte routes, bounded T0 check-ins and a status projector; the production boot tree stages offer verification, switch-root handoff and a resident base OS observer. Stage two rejects a present stale or invalid handoff, and a corrupt same-boot nonce cannot mint a second offer identity. These are distinct from Player enrollment and readiness. A serial, offer ID or latest received check-in is a **claim**, not physical boot identity, command authority or automatic frontier evidence. Old bases show OS telemetry unavailable; mixed boot trees and physical switch-root remain to be qualified.
- **F3 and D15:** Separate fleet app policy, per-device app override and base baseline records stage exact digest/size and source/revision provenance. The base ABI is independently sealed from the base build and final squashfs; the payload declares its required ABI. An ABI match is distinct from a same-tag, unverified co-release. `manifest.json` and the `.deb` remain the schema-1 legacy contract; optional `manifest.v2.json` carries the inert `pw-player-data-v1` archive. The base-owned launcher/executor repairs interrupted local attempts before Central discovery, and a release probe now starts the built data payload through the base unit. A local collector verifies the selected installed root and a stable systemd process sample, and the agent sends them as bounded schema-2 T0 claims to Central. They are not acceptance evidence. Online update, cross-boot fallback, package-failure continuity and physical handoff remain unqualified.
- **F4/F6:** An idle-only durable Runtime drain foundation fences offers, readiness, media grants and equipment writes. It does not authorize a stop, interrupt an active Run, reconcile `stop_committed` or lift a per-Output diagnostic. T0 commands and automatic base-frontier promotion remain disabled while D14, D16 and D17 are open.

## Current seams and proposed owners

- `central/coordination.py` owns plan delivery, readiness, offers and commits. Its rich internal delivery should pass through one app-protocol projector before `central/app.py` REST or WebSocket serialization. `central/registry.py` owns bearer/epoch validation, per-epoch schema selection and Identify; it must recheck identity under its player-row lock, then release that lock before coordination delivery. A negotiated challenge binds an epoch and projected state digest; only a matching, once-consumed applied acknowledgment refreshes control acceptance.
- Central fleet policy and status need a narrow module boundary separate from registry and catalog. Catalog owns release discovery, exact byte availability and the legacy manifests; fleet policy owns desired revision, immutable BootOffer/AppAttempt, assurance and observation reducers. SQL records need transaction ports rather than direct catalog-to-Runtime writes. Existing `known_good_tag`, `last_good_tag`, `boot_outcome` and automatic promotion are legacy tag-based evidence, not accepted exact-digest fallback. Additive migration must keep old routes and record their weaker provenance. An offer lookup that returns metadata without opening and leasing exact bytes, or a T0 projection that treats latest receipt as current physical boot, cannot satisfy the activation gate.
- `appliance/netboot_init.py` stages a validated exact offer handoff through switch-root, and `appliance/os_agent.py` stages an independent observer. The data-only archive, base-owned launcher and executor are separate from the old root-running `.deb` path. The actual built boot tree, single executor/cgroup ownership and display host need integrated and physical qualification; observation sequence state stays separate from package mutation state. Old boot trees keep their legacy cold path.
- Runtime owns equipment withdrawal and maintenance fencing. The staged idle-only drain uses coordination→Runtime→registry serialization, cancels old groups and rejects new offers/grants; `stop_committed` never time-releases. Active multi-Frame Run/Actuator policy, stop permit, post-stop reconciliation and per-Output handoff remain unimplemented gates. The lifecycle owner, not the installer, decides multi-participant Run effects.
- The console currently reads inventory/Runtime in one operator snapshot and boot facts separately. Fleet status either joins them in one read transaction or shows distinct read times. `OS telemetry unavailable`, `boot linkage unknown`, and `fallback unverified` remain visible during migration.

## Integration order and activation boundary

1. Apply additive F0/F1 tables while old Central binaries still serve; prove every allowed old binary tolerates them. Route legacy four-field state from **every** pod before any Player depends on hello, and deploy only a rollback binary with the same compatibility behavior. Persist an acknowledgment's latest result/time independently of its earlier applied time.
2. Wire the bounded base observation path into the actual Central composition root and production boot tree. The boot-offer POST, exact base/app GET and check-in POST need explicit route tests through ingress and mixed pods; a helper module or isolated client test is not a deployed feature. Preserve an immutable nonce-to-pair record or refusal tombstone across payload GC; verify or rehydrate exact bytes on each serving pod and lease the stream. If an artifact is absent, return named unavailable for the same offer. A T0 rate-limit response must preserve base provisioning.
3. Project fleet status from separately timestamped OS, app and Output facts. The latest receipt from boot A after boot B's offer does not prove A is current; show its boot and uncertainty. Join current F0 `ControlApplied` only for the matching app authority epoch, and show a later rejection as the current diagnostic while retaining the earlier applied acknowledgment as history. Do not infer app liveness from missing plan readiness on an unbound Player.
4. Activate F3 desired policy only after exact digest/size, release-source and base/app ABI provenance are available. Preserve separate fleet and per-device compare-and-set revisions (including override deletion tombstones), distinguish explicit empty policy from legacy promotion fallback, and snapshot that source plus compatibility basis in each offer. Revision-zero legacy promotion must not be projected as an explicit fleet choice. Mark mirror metadata separately from per-pod file availability. Keep F4 commands, automated F6 acceptance/frontier and maintenance effects gated by the [red/blue contract](player-fleet-red-blue-refinement.md#rollout-and-decision-gates) and owner decisions.

## Verification and decisions

Use controllable-clock tests for lock ordering, replay, acceptance, expiry and crash reconciliation. Add database/ingress races for two pods issuing the same boot offer, quota exhaustion and cleanup, delayed old-boot reports, an expired nonce that cannot select different bytes, one pod missing offer bytes, mixed F0 protocol pods and an old applied acknowledgment followed by rejection. Use exact release packages for the F0 compatibility matrix, staged old/new boot trees for rollout, and physical Pi/panels for switch-root, package continuity, first-buffer handoff and visible diagnostics. Exercise an agent that stays healthy while its executor hangs, a cache loss after stop, a tag alias moved to new bytes, and one Output ready while another stalls. Record test artifacts and limits in [evidence](evidence/README.md); green Central endpoints or simulated Players do not establish pixels.

[D15's data-only direction](design-decisions.md) is selected for this PR. [D14, D16 and D17](design-decisions.md) remain open for command trust, Runtime withdrawal and mixed-version rollback. A remote action and automatic health frontier must stay disabled until those choices, exact fallback/capacity and physical qualification gates are satisfied.
