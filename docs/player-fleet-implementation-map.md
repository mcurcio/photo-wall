### First integrated outcome and sequence

**M1 is a software lifecycle milestone, not a physical boot/display claim.** A runnable scenario composes real domain/application services with explicitly injected process, clock and display adapters:

1. New boot and no app: HostCore can report; DisplayHost requests a base diagnostic and reports presentation as unknown until backend confirmation.
2. Cold authorization names one exact verified app environment. Broker records its action and starts that environment; app process existence alone does not admit its surface.
3. Matching OutputKey/process/epoch/configuration and a backend presentation observation admit the candidate. One Output's observation does not admit another Output.
4. Independent process-exit evidence invalidates its admitted surface and requests the diagnostic. Host reporting remains callable. A network disconnect without exit evidence preserves valid local presentation until its own authority/lease rules say otherwise.
5. Failed or superseded background staging leaves the old process/surface unchanged. Receipt, initiation and later observations remain separately visible in the Central evidence projection, including reordered deliveries.

N1 defines the interfaces first. N2/N3 implement the stateful behavior next. N6 then assembles and runs this scenario, with tests/verification deliberately deferred until these contracts and implementations are stable. The next milestones are independently executable Linux service isolation and cold launch (M2), an actual release-built Debian closure (M3), and a real compositor backend (M4). A fake or recording compositor proves only software transitions; it cannot complete M4. A base GTK diagnostic client alone does not implement protected admission, stacking or buffer evidence.

Final verification includes focused domain/fault traces, the repository's pytest/Ruff/docs checks and database integration when configured. Linux packaging/process checks, exact-image boot, physical Pi/panel behavior and mixed-serving/rollback certification each retain their own evidence and limitations. No test success is asserted by this dispatch plan.

### F3 app observation slice: module contract

The base-owned OS agent samples the data-only executor's selected root and current systemd process through the existing read-only `AppEvidenceCollector`. It sends schema-2 observations to `/v2/appliance/check-ins`: all schema-1 fields plus one bounded `app_evidence` value containing `kernel_boot_id`, `installed_sha256`, `running` (`sha256`, `pid`, `start_ticks`, `invocation_id`), and named installed/running unknown reasons. The collector's boot ID must equal the report's boot ID. A sampling failure still produces a base check-in with unknown app evidence; it cannot silence OS liveness. The observer owns transport and sequence; the executor owns installed-root verification; neither owns acceptance or commands.

Central admits schema 1 and 2 through one quota, offer-correlation, and sequence boundary. Schema 1 stays byte-for-byte valid. An additive observation migration stores optional app fields; old rows project unknown. An agent retries the same sample on schema 1 only when a located Central returns the canonical unsupported-route response for v2. Other errors never cause downgrade. Both versions return the same receipt vocabulary and share the per-boot sequence high-water mark, so a mixed pod cannot count two accepted reports for one sample.

The fleet projector chooses the same most recently received boot claim for base, installed, and running facts, and exposes digest, process identity where present, age, boot ID, source `serial_claim`, assurance `t0_unverified`, and `boot_linkage: claim_only`. Unknown collector reasons are diagnostic, not proof of absence. A later old-boot report remains visibly ambiguous with the latest offer. Equipment labels these as **reported** installed/running facts and never offers an action or marks an artifact accepted from them. This slice is complete in software when v1/v2 mixed Central behavior, absent/invalid collector evidence, stale sequence, delayed old-boot claims, and strict no-command receipts pass ingress/database/agent checks. Physical Pi output and command trust remain separate gates.

App evidence sampling has a short independent deadline and at most one in-flight collector. The OS agent reports `evidence_unavailable` if the collector is slow, while still sending its base check-in; it never reuses an old app sample as if it were current. A completed late sample is discarded. The collector takes short read-locked snapshots of the terminal journal, selected digest and attempt identity before and after root verification and PID1 sampling. Digest-named published roots are immutable to the executor; verification and systemd calls run outside the mutation lock. If the snapshots or process identity differ, the result is unknown. An exclusive activation/recovery lock refusal named `executor_busy` is transient: the provisioner retries the same exact local operation with bounded waits and watchdog renewal rather than treating contention as an app failure. All other executor errors keep their existing recovery-required behavior. Tests must simulate slow collection and concurrent activation to prove OS telemetry cadence, coherent snapshots and the one-writer mutation invariant.

Narrowing GC early could evict bytes still needed for rollback. Existing pre-session attempts also retain a null issuing session after the additive migration; an attempt at the same offer and policy revision cannot be rebound to a new session. Command activation must first quiesce those legacy rows or add an explicit unstarted-attempt supersession transaction without rewriting history.

The original exact-byte and outcome-report paths still require the issuing OS session. A separate **unmounted recovery data adapter** now accepts only an injected current T1/T2 carrier principal and a short-lived CAS lease over the original immutable attempt. Historical drains have no `fleet_drain_id` and are ineligible. Admission requires the matching `stop_committed` drain, its exact UUID link, the immutable stop permit, the current device generation, unreleased exact target/fallback roots and no explicit terminal lease revocation. The lease exposes only those two retained payloads and append-only claims; per-carrier report sequence continues across lease renewal and resets for a newly verified boot. The original issuer identity remains frozen, and neither claims nor a lease certify accepted bytes, permit another stop or select another target. The unmounted internal issuer now populates `fleet_drain_id` atomically with the ready-to-stop permit. No production verifier mounts these routes, and closing new-command admission must leave this narrow repair path available on a certified binary. A healthy fallback process still requires a fresh command before it can be stopped again.

A separate 2026-09-29 [built-base service probe](../scripts/os_agent_service_probe.py) is staged for CI. One container boots the final squashfs to `multi-user.target` with the provisioner masked, checks the agent's enablement link, and requires a schema-2 report without manually starting the agent. A second container starts the installed OS-agent unit under container systemd, records its process identity and first schema-2 report, starts the provisioner against a deliberately corrupt Player package, and requires a later `app_integrity` report from the same agent process and incarnation. Its local HTTP recorder isolates service continuity; it does not qualify Central persistence, a Pi boot, display output or mixed pods.

The unmounted internal `FleetCommandLifecycle` now creates one immutable command from a current explicit/override maintenance request, a rooted exact AppAttempt, and a prepared unbound drain under the default-closed deployment gate. A separate ready-to-stop transaction records an immutable permit and the drain/attempt stop commitment together. Exact replay checks the current carrier, gate and deadlines after waits; an already issued permit can replay despite a later desired-policy change, while a pre-stop command cannot proceed under that change. Migration 052 rejects a new unbound stop commitment without the matching permit in the same transaction, and migration 050 freezes prepared unbound identity/snapshot and the entire committed drain. These are internal transaction seams, not a production command route or proof that the OS stopped. A prepared command that never reaches stop still needs authenticated base-journal no-stop reconciliation before its drain and roots can be released; timeout alone is insufficient. The operator status view separates these durable records from OS claims and unknown physical output.

## Current seams and proposed owners

This retained predecessor planning section describes V1 seams and the original V2 proposal. Use the current node status and remaining-work table above for implementation state; historical future-tense wording here does not remove completed V2 work.

If an artifact is absent, return named unavailable for the same offer. A T0 rate-limit response must preserve base provisioning.
3. Project fleet status from separately timestamped OS, app and Output facts. The latest receipt from boot A after boot B's offer does not prove A is current; show its boot and uncertainty. 4. Activate F3 desired policy only after exact digest/size, release-source and base/app ABI provenance are available.
