# Player fleet implementation map

**Status:** source-grounded implementation proposal for review, not completed work or qualification. **Scope:** F0–F4/F6 in the [production-readiness intake](production-readiness-v0.13.md). The [control-protocol design](player-protocol-compatibility-design.md), [fleet-control design](player-fleet-control-design.md) and [red/blue safety contract](player-fleet-red-blue-refinement.md) own behavior. This page maps that behavior onto current modules and migration slices so agents can claim bounded work without treating an unaccepted decision as code policy.

## Dependency order and claimable slices

| Slice | Module boundary and deliverable | Gate before a stronger claim |
|---|---|---|
| F0a: published-app recovery | One pure Central state projector feeds REST and WebSocket; Registry refuses Identify for unnegotiated sessions. Legacy wire state has exactly four fields. | Exact published v0.12/v0.13 package fixtures against warm/cold sessions, bound readiness and both transports; a compatibility-safe serving and rollback binary. |
| F0b: negotiated application control | Registry owns epoch-scoped schema selection and applied-control evidence; a shared protocol contract owns hello, delivery challenge and acknowledgment; Player service negotiates before its first state read. | Concurrent hello/read and re-enrollment tests, duplicate/replayed ack tests, and all Central replicas able to honor persisted selections. |
| F1/F2: observational base | Additive Central boot-offer/check-in records and one read-only status projector; initramfs hands an exact offer reference into the new root; a base-owned agent reports independently of app install. | Old Central/base compatibility, stage-one restart and real switch-root readback, report ordering, spoofed serial treated as claim, missing-package/failed-app visibility. No remote action follows a check-in. |
| F3: desired app and operator view | Fleet policy owns fleet target and per-device app override separately from base pin; catalog resolves immutable compatible artifacts; Equipment UI shows desired, offered, installed, running and assurance/age. | Legacy aliases explicitly unverified, missing mirror visible, override on an incapable base shown as `queued, unenforceable`; no claim that promotion updates a running process. |
| F4/F6: managed activation/recovery | One base executor, data-only artifact contract, durable Central attempt and Runtime drain, base display host, exact digest fallback and cohort acceptance. | D14–D17 decisions; approved command path with accurately stated assurance if remote actions are enabled; physical two-Output qualification; mixed-binary rollback enforces active fences. |

The F0a and F1 observational slices can proceed independently. F0b and F3 can expand records and UI before F4 is activated. A T0 serial-only base never earns command or automatic frontier authority from a fresh check-in.

## Current seams and proposed owners

- `central/coordination.py` owns plan delivery, readiness, offers and commits. Its rich internal delivery should pass through one app-protocol projector before `central/app.py` REST or WebSocket serialization. `central/registry.py` owns bearer/epoch validation, per-epoch schema selection and Identify; it must recheck identity under its player-row lock, then release that lock before coordination delivery. A negotiated challenge binds an epoch and projected state digest; only a matching, once-consumed applied acknowledgment refreshes control acceptance.
- Central fleet policy and status need a narrow module boundary separate from registry and catalog. Catalog owns release discovery, exact byte availability and the legacy manifests; fleet policy owns desired revision, immutable BootOffer/AppAttempt, assurance and observation reducers. SQL records need transaction ports rather than direct catalog-to-Runtime writes. Existing `known_good_tag`, `last_good_tag`, `boot_outcome` and automatic promotion are legacy tag-based evidence, not accepted exact-digest fallback. Additive migration must keep old routes and record their weaker provenance.
- `appliance/netboot_init.py` currently transfers resolver/modules at switch-root; the proposed boot handoff adds a validated exact offer reference. `appliance/provision.py` now installs via `dpkg` and exits. The new base owns a resident read-only agent, a single supervised executor/cgroup with its own mutation journal, and the display host. Observation sequence state is separate from package mutation state. The current `.deb` contains root `postinst` and Player/Weston units; a data-only payload requires a new base and build contract while old boot trees keep their legacy cold path.
- Runtime owns equipment withdrawal and maintenance fencing. Today `Coordinator` serializes its operations, while Registry binding, calibration, Identify and retirement have separate transactions. A shared coordination→Runtime→registry entrypoint must fence old delivery as well as new offers, commits and leases. The persisted barrier names every Output, Frame/binding generation, calibration revision, Run participant and Actuator. `stop_committed` survives timeout/restart until reconciliation or explicit recovery; partial Output handoff never clears other fences. The lifecycle owner, not the installer, decides multi-participant Run effects.
- The console currently reads inventory/Runtime in one operator snapshot and boot facts separately. Fleet status either joins them in one read transaction or shows distinct read times. `OS telemetry unavailable`, `boot linkage unknown`, and `fallback unverified` remain visible during migration.

## Verification and decisions

Use controllable-clock tests for lock ordering, replay, acceptance, expiry and crash reconciliation. Use exact release packages for the F0 compatibility matrix, staged old/new boot trees for rollout, and physical Pi/panels for switch-root, package continuity, first-buffer handoff and visible diagnostics. Exercise an agent that stays healthy while its executor hangs, a cache loss after stop, a tag alias moved to new bytes, and one Output ready while another stalls. Record test artifacts and limits in [evidence](evidence/README.md); green Central endpoints or simulated Players do not establish pixels.

[D14–D17](design-decisions.md) remain open for command trust, artifact format/capacity, Runtime withdrawal policy and mixed-version rollback. A remote action and automatic health frontier must stay disabled until their governing decisions and qualification gates are accepted.
