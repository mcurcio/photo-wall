# Red/blue refinement of Player fleet architecture

**Status:** design proposal for owner review; staged implementation is not deployed or physically qualified. **Scope:** F0–F4/F6 in the [v0.13 readiness intake](production-readiness-v0.13.md). Three red reviewers attacked the [control-protocol](player-protocol-compatibility-design.md), [fleet-control](player-fleet-control-design.md), and [first adversarial review](player-fleet-adversarial-review.md) proposals. Three blue reviews composed corrections, followed by a red challenge of those corrections. This page records the prior fleet red/blue contracts. The [Player node domain model](player-node-domain-model.md) owns the 2026-09-30 target refinement, including HostCore/AppManager/DisplayHost separation, release-built Debian closure, and immediate operator reboot. Where this page describes a data-only final artifact, one OS agent or T1/T2 as mandatory for remote commands, it describes the staged PR/earlier proposal rather than the updated target. The owner selected a weaker trusted-LAN/serial command model, with separate boot-scoped reboot and app-effect scopes; this does not authenticate a physical Pi. The linked proposals own their feature-specific behavior.

## What the exchange changed

| Red counterexample | Blue contract, then final red correction |
|---|---|
| Serial-only PXE can issue a token to an impostor; HTTP discovery can redirect to a different installation. | Separate observational T0 from command-capable trust modes. A managed network port identifies an **attachment**, not a physical Pi. T1 also needs protected boot-data delivery and an authenticated Central audience from its trust anchor; otherwise it is T0. |
| A Player `.deb` can run root scripts and replace the agent or Weston while an allegedly independent OS agent runs. | The PR staged a validated data-only payload. The updated owner-selected target keeps the `.deb` as dependency-authoring input but resolves/configures its complete closure before release into an app-private root; a confined broker activates that root without host-root package scripts. Legacy `dpkg` operation carries a weaker continuity claim. See the [node domain model](player-node-domain-model.md#debian-closure-and-app-effects). |
| A legacy `known_good_tag` can resolve to new bytes after catalog sync changes a tag's digest. | Accepted fallback and cache retention use immutable exact digests, size, ABI and provenance. Historical tag-only health is `fallback_unverified`; it cannot authorize automatic rollback. |
| Cold provisioner and resident agent can start concurrent `dpkg` processes; an agent crash may leave a child alive. | One base-owned executor/cgroup handles cold and online transactions. It writes intent before side effects, inspects surviving children and package state on restart, and admits one mutating attempt per boot. |
| Desired r2 arrives while r1 is stopping/installing. | Cancel r1 before stop; after stop, restore stable service if still possible; during mutation, finish/repair r1 or restore exact fallback before starting r2. r1 health does not satisfy r2 desired policy. |
| A maintenance permit is granted while idle, then a Run starts before stop; or Central times out after authorizing stop while the agent is paused. | Runtime owns a durable equipment drain serialized with offers/commits. Once stop is authorized, `stop_committed` **never** time-releases into new Run admission; reconcile the matching attempt or require explicit recovery. |
| Drain blocks all plans until the new app shows a frame, but the new app needs a plan to render. | In `starting_new`, allow only the new candidate or restored-fallback epoch to prepare/test render behind the base diagnostic; keep public commitments blocked. Per-Output handoff opens the affected Output only after its current app buffer acknowledgment. An unbound/empty/black plan has an explicit app-owned handoff frame. |
| An idle canary accepts control yet renderer fails on first Run; a 1080p panel does not qualify a dual-4K fleet. | Split control compatibility, rollback eligibility, Output observation and physical qualification. Fleet promotion is scoped to declared Output/mode/capability cohorts; untested cohorts remain unqualified. |
| Old Central can read new tables yet ignore an active update fence on rollback. | Rollback is **behaviorally** compatible with active attempts and all legacy routes, or mutating attempts are quiesced and safe policy restored before old binaries serve. Schema readability alone is insufficient. |
| A later rejected delivery leaves an older `applied_at`, or a delayed report from boot A arrives after an offer for boot B. | Keep the old acceptance as historical evidence and show the latest control result separately. Sequence orders claims only within one boot; neither receipt time nor offer order establishes the current physical boot under T0. |
| An offer survives in PostgreSQL after its bytes disappear from a serving pod, or its row is deleted and the same boot nonce is selected again. | Root exact bytes separately from the offer identity; verify or rehydrate on the serving pod and lease the open file through streaming. Expiry refuses an old nonce rather than selecting a new pair. |

## Trust and channel contract

The [separate loader-OS and app channels](player-fleet-control-design.md#separate-loader-os-and-application-channels) remain mandatory. Their credentials, protocol versions, command scopes, storage and revocation are independent. Shared hostname/discovery does not grant shared authority. A base check-in is a bounded observation; it never returns a command or refreshes the app session.

| Mode | Permitted claim | Command consequence and limit |
|---|---|---|
| **T0 — current trusted-LAN serial path** | Zero-touch boot, app enrollment and OS **observational claims**. Central can select an initial app on an operator-pinned/frozen boot path. | No device-authenticated remote reboot/update, automatic health frontier from fresh serial reports, or physical-device failure attribution. Freeze new automatic latest-verified promotions during migration; label historical `known_good_tag` as legacy/unverified. A new device can still boot from a deliberately selected safe baseline. |
| **T1 — managed network attachment** (proposed option) | A trusted switch/gateway binds requests to a commissioned access session, strips client identity headers, and sends stage one protected boot data. Stage one authenticates a stable Central installation audience before credential exchange. Protected stage one obtains the one-shot boot credential **before the app starts** and binds it to the access session, base-agent-held ephemeral key, device lifecycle generation, boot reference and installation audience; it cannot be issued or replaced by another process on that attachment, including the `wall` app after agent restart. | Commands are authorized for the **attachment**, not proven physical Pi or software. A replacement on the same port inherits the attachment unless a separate identity check intervenes. Base agent key material is inaccessible to the unprivileged app. Competing claimants, boot-path substitution or lost audience authentication force T0/ambiguous status. No fresh port check-in clears an unresolved stop. |
| **T2 — commissioned hardware identity** (optional) | A per-device nonexportable key proves possession under a Central challenge; authenticated Central and optionally verified/measured boot add their respective guarantees. | Key possession alone does not attest running software. Hardware, recovery, rotation and commissioning must be specified without removing the T0 zero-touch appearance path. |

Current `/v1/locate` identity JSON checks API shape, not installation authenticity, and the existing trusted-LAN path permits HTTP/cross-host redirects ([decision 0014](decisions/0014-reaching-central-from-every-boot-stage.md)). An OS command credential must never follow that unauthenticated relocation. T1 needs a named boot trust anchor and protected boot-data path; placing a TLS pin inside a substitutable unsigned boot tree is insufficient. If the owner accepts weaker T0 command risk, that must be an explicit, accurately named decision and cannot be called device-authenticated control. Until a mode is accepted and qualified, F4's remote command capability remains unavailable. F0 repair and F1 observation do not depend on this choice.

T0 intake needs atomic quotas across replicas for reports per claimed device, all reports, new serial claims and retained history. Size the global report budget above the supported fleet count times the report cadence (128 Players at ten seconds already produce 1,105,920 ordinary reports per day), with room for phase changes. Bound per-boot history and expire old observations; return a named rate-limit receipt with retry guidance without blocking base provisioning. A serial spoofer can still consume a quota or impersonate an observation. These limits protect Central resources, not device identity or command authority.

One `DeviceLifecycle` owner increments the equipment generation on retirement/replacement and revokes app epoch, future OS command issuance/admission and queued actions in the same Central transaction. Read-only history remains. An already delivered `stop_committed` command cannot be recalled remotely: the agent rechecks generation online before a new stop if available, while Central keeps the durable drain until the effect is reconciled or explicitly recovered. A partitioned executor already mutating may complete local repair; it cannot start another action after retirement. A fresh serial/port report is not a replacement identity or a reason to clear an uncertain command.

## Artifact, boot and update contracts

- `ArtifactRef(kind, digest, size, ABI, provenance)` identifies immutable bytes. A tag is a display alias, not a health key, rollback target or cache root. Digest proves byte equality, not authorship; trust in release source and Central audience is separate. Publish and verify bytes before advertising availability. Durable offers, active attempts, accepted fallback and offline rollout obligations root exact digests for garbage collection. Each serving pod must open or rehydrate the frozen digest and size, reject a mismatch, and hold a file/stream lease against GC until its response ends. A mirrored catalog row or database reference alone does not establish that bytes are present on that pod; a miss returns named unavailable without changing the offer.
- `BootOffer(installation_audience, device_generation_or_claim, kernel_boot_id, boot_nonce, offer_id)` selects one exact base digest and **initial app** digest with both policy revisions, app-policy source (`explicit`, override or legacy promotion) and compatibility/ABI basis. Revision zero on a legacy fallback must not later appear as an explicit fleet choice. Stage one creates the nonce once in validated initramfs `/run` before requesting bytes; its own process restart reuses it and a kernel reboot changes it. Stage one must explicitly transfer a validated offer reference into the mounted base root and prove readback after `switch_root`; the current code transfers resolver/modules only. All retries return the same pair or a named conflict. The initial app is served by offer reference, not re-resolved through a mutable global manifest. Retain the nonce/selection identity independently from payload bytes: after an approved retention horizon, a compact tombstone may refuse that old nonce, but deletion must never permit a different pair for the same boot. T0 alone cannot prove that a claimed physical boot ended, so the expiry and offline obligation rule needs an owner decision. This is an offer, never proof of complete HTTP delivery or physical boot.
- `AppAttempt(boot_ref, attempt_id, desired_revision, target_artifact, fallback_artifact)` is a separate immutable same-boot update transaction compatible with the observed base digest. A later app target does not rewrite the initial BootOffer. Central commits one durable command ID and fences before any replica exposes it; replicas return the same action on retry. The agent journals receipt and progress before effects and deduplicates by device generation, boot, attempt and command ID. Exactly-once HTTP delivery is unnecessary; one idempotent effect per attempt is the goal. A lost reboot/install acknowledgment yields `unknown`, not a newly minted command.
- One **base-owned** package executor and systemd cgroup own cold and online fetch, verify, activation, repair and rollback. The provisioner becomes a request adapter or is retired. The executor records intent before stop/mutation, holds the local exclusive transaction, waits for or terminates any surviving child on restart, inspects package/active-root state, and resumes/repairs the same attempt before admitting another. Its root-owned `/run` mutation journal and verified files survive process restart, not reboot. The observational agent keeps a separate root-owned sequence record with one writer/lock for each record. Preserve bounded provisioner/watchdog liveness: an agent heartbeat cannot mask a stalled or dead executor, and network retry must not be mislabeled as installer crash. Central retains exact fallback bytes for cold boot.
- The PR stages `pw-player-data-v1`, a bounded data-only archive extracted by the base executor into immutable digest-named RAM roots. Its ABI, capacity refusal and exact fallback roots are software work, not the selected final package format or physical continuity proof. The owner-selected target is a release-built Debian dependency closure in a new typed artifact/offer/attempt/command schema; see the [node domain model](player-node-domain-model.md#debian-closure-and-app-effects). The legacy root-running `.deb` path remains continuity-unqualified. Before any healthy-app stop, the executor must still validate exact roots and capacity and recheck the current permit.

A desired-policy revision can supersede a prepared attempt before stop. Once stop is committed, it cannot start a second mutating attempt: restore the old app to accepted control if no package mutation occurred, or finish/repair the immutable attempt or accepted fallback until stable. Then evaluate the latest desired revision. Command expiry prevents **new admission**; it does not abandon half-configured package state. An agent crash with a surviving `dpkg` child cannot release ownership to a second installer. A reboot destroys volatile staging; Central records the old attempt as unconfirmed until matching evidence resolves it and chooses only an exact, obtainable, compatible accepted fallback or `recovery_required`. A legacy T0/v0.12 device with only tag-based history has no newly qualified automatic fallback, so its **first** transition to the new base/payload path is a cold PXE/physical or out-of-band boot, or a separately commissioned T1/T2 path; it is not promised a safe online update from the old base. The cold path establishes the first qualified digest before online activation is enabled.

A prepared online command that never reaches stop needs a separate **no-stop reconciliation**. A changed desired policy, a local staging refusal, lost dispatch response or deadline alone does not release its drain or exact roots. The current verified OS carrier must report its base-owned executor journal with no `intent_stop`, the same boot/attempt/command and active accepted fallback root/process; Central must also see fresh applied old-app control. Under Coordination→Runtime→fleet→device→Player→session→attempt→drain locks, the lifecycle owner verifies that no stop permit exists, advances Runtime at a post-lock cut, aborts the prepared drain, revokes/releases only that attempt's roots and appends an immutable `no_stop_confirmed` outcome in one transaction. If carrier identity, journal, process or control evidence is missing, the fence and roots remain for explicit recovery. This is the next implementation slice; the staged issuer does not yet provide it.

## Runtime drain and display handoff

A maintenance snapshot or expiring permit alone cannot make a physical stop atomic with Central. Runtime/coordination owns a **durable drain barrier** under the same serialization boundary as new offers, existing-plan/commit/Identify delivery, commits, binding and calibration/Identify writes, and leases. Current Registry writes use separate transactions, so implementation must provide one coordination→Runtime→registry lock order across these paths before it exposes a stop permit. The barrier records each affected Output, Frame/binding generation, calibration revision, Run participant and Actuator; one Output handoff cannot clear another's fence or settle a cross-Output Run. The barrier covers all Outputs on the device and the declared effect on each affected multi-participant Run; it never directly finishes or cancels a Run. A prepared barrier that has **not** authorized stop may abort under Runtime lock after its agent authorization expires and clock margin passes; restore/confirm old app authority and valid offers before releasing the drain. An authorized stop cannot use that abort path. Calibration previews and Identify cues are fenced or ended at admission so they cannot replay in a new epoch. The base diagnostic draws in raw Output coordinates.

Runtime admission consumes one immutable constraint for the current drain target set under that same transaction, including recursive Scene participants and Actuators. Scheduled, queued, manual, forced, restart and nested-child admission all use the same guard; a restart must check before canceling an existing Run. The constraint carries into detached projection so an operator cannot see a projected Run that execution would refuse. At drain preparation, persist Runtime advancement to a clock sample taken after the Coordination and Runtime locks, **before** inserting the barrier. Before abort or reconciliation removes a barrier, advance again while it is still active. These two time cuts prevent a delayed scheduler from applying a pre-drain window under a new fence or retroactively admitting a during-drain window after release. Whether a due Program is skipped once with a recorded reason or delayed remains D16; neither option authorizes a bound stop until selected and tested.

The staged D16 foundation derives an immutable `AdmissionPolicy` from active drain snapshots under the Runtime lock and carries it through pure copies and projections. `Coordinator.advance()` samples its clock after Coordination and Runtime locks, and manual, queued, forced, restart and nested activation share the same drain guard. Bound preparation still refuses while the due-Program and multi-Run/Actuator choices remain open. The recommended due-Program choice is one durable `rejected/equipment_draining` admission at its original window, never replayed after drain release; a queued manual request may wait only until its explicit expiry. These remain proposals until D16 is decided.

Default maintenance can wait for idle. An explicit interruption should name the complete recursive root Run footprint and cancel that root with all descendants as one lifecycle action; every participating Actuator needs an acknowledged safe state before stop. A later aborted package attempt cannot resurrect that canceled Run. A first implementation may retain a whole-Player public commitment fence while recording per-Output diagnostic handoff evidence; output-granular release needs a separate cross-Run guard. The operator-visible interruption and Actuator policy remain D16 owner choices.

| Barrier phase | Admission and display rule | Exit rule |
|---|---|---|
| `draining_old` | Block new public commitments to affected Outputs and apply the chosen Runtime policy to existing Runs. Keep the old app authority until withdrawal so an abandoned preparation does not strand a healthy process. | Atomically persist `stop_committed` and expose the current boot/attempt permit; or `abort_prepared` under Runtime lock after authorization expiry, confirm old app authority and resume admission. |
| `stop_committed` | Fence the old app epoch at withdrawal and keep equipment drained across Central restart, network partition and permit/ack timeout. Agent verifies current generation/boot/attempt and local deadline before stop. No new Run can commit even if the agent pauses after a 200 response. | Matching agent progress enters `starting_new`; an unknown stop stays drained for reconciliation or explicit operator recovery. Never time-release solely from silence. |
| `starting_new` | Allow only the **new candidate or freshly restored fallback epoch** to receive synthetic preparation/test state behind the base-owned per-Output diagnostic; it cannot create authored Run side effects. Public Run commitments remain fenced. An empty/unbound/black composition has an explicit app-owned handoff frame. | For each Output, a matching process/epoch/binding **and committed configuration/calibration revision** plus app-buffer handoff acknowledgment yields operational evidence for that Output. A stale calibration buffer cannot lift the diagnostic. A stalled Output retains the diagnostic and commitment fence; cross-Output Run policy remains Runtime-owned. |
| `operational` | Remove the diagnostic only for qualified Outputs and resume their new commitments subject to current bindings, Run/lease generations and participant policy. Other Outputs retain their drain; a multi-Output Run still obeys its participant policy. | Reconciliation persists a stable app/fallback outcome and closes only the resolved Output fences; a later fault is a new equipment event. |

The app-buffer handoff acknowledgment is operational evidence, not proof of visible pixels. Physical panel qualification remains a separate gate. Do not release an active or ambiguous barrier merely because Central restarted, a timer expired, or the same port reported a new boot. Reboot/watchdog recovery is bounded only when a new boot request actually occurs; a hung kernel may require power or out-of-band intervention.

## Acceptance and status ladder

| Fact | Evidence allowed to establish it | What it cannot establish |
|---|---|---|
| `ControlParsed` | Current authenticated app validates an identified delivery. | Executor adoption, rollback eligibility, output. A missing executor reports `parsed_execution_unavailable`. |
| `ControlApplied` | Current app epoch acknowledges successful local adoption of the identified delivery after executor action, joined to the OS-observed launched process when attempt acceptance matters. Delayed/replayed acknowledgments are historical. | Plan/media readiness, visible pixels or OS command authority. |
| `AppRollbackEligible` | Exact installed artifact and allowed inventory, new service invocation/process path, a local OS-agent-to-app proof binding enrollment key/epoch to that invocation, sustained control and no startup/renderer fault; a bound device also passes a bounded representative readiness check after maintenance. | A quiet or unbound app with control only is not newly eligible. This is operational evidence on a trusted host, not cryptographic attestation against compromised OS. |
| `OutputQualified` | Current bound Output IDs, modes, binding generations and new app presentation/handoff evidence for the declared capability cohort. | Player reports cannot prove physical scanout. One 1080p/single-Output canary does not qualify a dual-4K cohort. |
| `FleetFrontierQualified` | **Accepted T1/T2 command/boot trust mode**, base self-check, compatible app acceptance, Output qualification for the declared rollout cohorts and separately recorded physical evidence; T0 retains only an operator-selected baseline without claim-derived automatic promotion. | Unknown/unmeasured profiles remain unqualified. An operator may choose an explicit limited promotion with the untested envelope shown; the system cannot silently claim fleet-wide qualification. |

The local app proof uses a protected, base-owned socket to bind the app enrollment key to the actual peer PID/cgroup, systemd invocation and process start identity. `SO_PEERCRED` alone identifies the process that connected; a passed socket can have a different later writer. The staged `SOCK_SEQPACKET` service therefore requires kernel `SCM_CREDENTIALS` on both packets, agrees them with the connecting peer and process samples, and lets only an injected protected-context sink store the result. Admission checks the current Player MainPID and UID before a bounded, queue-free worker takes the socket; a short first-packet deadline prevents idle connections from serially blocking proof. Returned `SCM_RIGHTS` descriptors are closed before rejecting ancillary data. Admission is only a resource guard; the verifier and sink recheck the exact current context before recording. No socket unit is enabled until that sink and T1/T2 context provider exist. A self-reported app tag, boot ID or attempt ID is insufficient. Legacy apps without that proof retain legacy status and cannot qualify a **new** automatic rollback target.

A single read-only status projector joins current OS and app facts by boot, service incarnation and epoch **when those references exist**. The current operator inventory/Runtime snapshot is one MVCC read but boot facts are read separately; the projector must use one transaction or show distinct as-of/read times; per-Frame Output facts additionally require binding generation. Legacy app evidence without an OS boot/incarnation link remains visible under current app authority with `boot linkage unknown`, never as a fabricated exact join. An unbound app has no Frame binding generation to require. A fresh base report from boot B plus a linked app report from prior boot A yields `base heard; app current state unknown`, with A shown as historical. Keep an older applied-control acknowledgment and its time as history if a newer delivery reports rejection or `parsed_execution_unavailable`; the latest result is the current diagnostic, and an old `applied_at` must not refresh it. Under T0, display a recent report as the latest **claimed** boot with its boot ID and receipt age, not as the current physical boot. A delayed A report after a B offer or report remains historical/ambiguous; a serve sequence and Central receipt order cannot settle physical boot order. Observation source, assurance tier and Central receipt time remain visible. Silence, timeouts and missing renderer evidence never become observed failure or confirmed presentation.

## Rollout and decision gates

1. **F0 first:** expand the database and deploy the exact legacy state projection to every serving Central replica before a Player sends hello or expects acknowledgment. Keep a repaired rollback artifact and test published v0.12/v0.13 Players through ingress, mixed pods, REST/WebSocket and bound/unbound cases; a request may reach any old or new pod during rollout. Only after every routable pod understands persisted negotiation may a new Player require it. An older `applied_at` remains historical after a later rejection. A rollback binary must enforce active update fences on **all** legacy routes before F4 is enabled; if it cannot, quiesce mutating attempts and restore qualified policy before rollback serves traffic. Database readability alone is insufficient.
2. **Expand and observe:** add readable tables/columns and compatibility adapters before enabling new behavior. An old Central must tolerate the expanded schema while it remains routable. Mount and validate production F1 check-in/offer routes only after bounded T0 intake, exact offer retry, serving-pod byte checks and the initramfs-to-base handoff work in the actual boot tree. An isolated helper or unmounted router is not production F1. Enable honest F2 status without command authority; old bases show telemetry unavailable and delayed T0 claims show uncertain physical boot. Freeze/relabel T0 automatic base frontier and legacy tag-only known-good behavior before presenting new trust claims.
3. **Canary the base boundary:** introduce independent HostCore, AppEffectBroker and DisplayHost base services, plus a versioned AppManager root. The Player remains a real `.deb`; release CI resolves its full dependency closure into a sealed app-private environment under a new artifact schema. The staged data-only path is historical groundwork, not the selected target. Keep legacy boot trees and manifest behavior explicit; an app-only override on an incapable base is `queued, unenforceable`. Qualify both physical Outputs and package-failure handoff before claiming continuity. See the [node domain model](player-node-domain-model.md).
4. **Enable remote actions after the required implementation and qualification gates:** implement the selected `lan_serial` assurance in a new offer/audience/session schema with separate HostCore reboot and AppEffectBroker app-effect scopes; the staged T1/T2-only verifier cannot be relabeled. Establish command issuance/retirement rules, exact-digest retention and capability-cohort gates. Immediate operator reboot needs durable audit but no Runtime drain; D16 governs planned healthy-app withdrawal. Register base/app ABI facts with named provenance; tag equality alone is not a cross-release compatibility certificate. Fleet desired and per-device override use separate compare-and-set revisions, with a tombstone revision on override removal; explicit empty fleet policy differs from absent policy that still follows legacy promotion. An override on a base lacking the new path remains queued with capability provenance. Every serving and rollback Central binary must enforce attempts, fences and command revocation before F4 is enabled. Use expand/read-old-and-new/backfill/feature-activate/contract migrations; retire legacy routes only after staged boot trees and offline devices are accounted for.

The owner selected `lan_serial` command assurance, an immutable release-built Debian dependency closure, immediate operator reboot, continuation of the broader Run with this Player’s Output(s) interrupted, and a matching DisplayHost presentation acknowledgment before calibration Save. Planned healthy-app withdrawal and due-Program behavior remain D16 decisions; D17 mixed-version rollout, Output/mode cohorts and physical evidence remain qualification gates. The [decision register](design-decisions.md) records selected choices separately from staged code and unqualified behavior.

## Adversarial acceptance traces

Exercise at least: serial spoof, quota exhaustion and HTTP redirect to another installation; replacement on a managed port; app-as-first-credential-caller and forbidden reissue after agent restart; malicious unprivileged app requesting an OS credential; stage-one restart and boot-policy change; two Central pods with mixed protocol support/lost command response; later control rejection after an older applied acknowledgment; delayed boot-A check-in after boot-B offer; offer bytes lost on one pod and old nonce retried after retention expiry; retirement between stop response and physical stop; prepared-drain expiry with no agent action; desired r2 arriving at each r1 phase; executor crash with a surviving package child; tag moved to new digest; cache/GC loss before and after stop; rollback Central during an unknown attempt; permit response followed by paused agent/new Run; Central crash in every barrier phase; quiet canary then first Run; one good 1080p Output followed by dual-4K failure; old app report after new boot; calibration preview and committed-revision change during first-buffer handoff; Identify during update; candidate failure with fresh fallback epoch; one Output handoff stalled while another succeeds; hung base with no new PXE request. Each trace names exact boot, attempt, digest, authority epoch, binding generation and expected `unknown` or qualified outcome. Controlled-clock/software tests prove ordering and fencing; exact release artifacts and physical panels qualify delivery, first-frame handoff and pixels.

The contracts prevent weak evidence from silently becoming strong evidence and forbid automatic side effects without authority. They do not create a distributed atomic transaction across PostgreSQL, the network and `dpkg`, nor prove that hardware cannot fail. Uncertain outcomes remain explicit and recoverable.
