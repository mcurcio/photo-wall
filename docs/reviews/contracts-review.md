# Independent review of the first execution contracts

Date: 2026-09-05. Reviewer: independent requirements review agent.

Scope: [decision 0001](../decisions/0001-mvp-time-recovery-and-module-contracts.md), [wire models](../../contracts/models.py), and [clock contract](../../contracts/time.py), reviewed against the canonical [requirements](../requirements.md) and [execution contract](../execution-contract.md). This reviews current decisions and implementation; it does not treat modules that have not been implemented as defects. Files were under active implementation and the disposition below identifies fixes observed during review.

## Material findings

| ID / severity | Finding and concrete consequence | Required correction and verification | Disposition at review |
|---|---|---|---|
| C01 — High | `Observation` initially had no plan revision. Assignment uniqueness was enforced only inside a Plan, so a delayed failure/presentation observation could not be distinguished from another revision reusing its assignment ID. Applying that result to current commitment/lifecycle can invalidate or complete the wrong work. | Carry revision in every consequential observation and match authenticated Player, authority epoch, plan identity/revision and assignment before changing durable state. Test delayed results from an older revision, including an assignment whose unsecured content changed. | Root added required `Observation.revision` during review. Schema omission fixed; consumer/restart evidence still required. |
| C02 — High | Initial Readiness lacked ordering independent of wall time. A failure that invalidates authorization can be followed over the network by an older successful report, restoring authority incorrectly if the server accepts arrival order. UTC `observed_at` does not resolve clock steps/reboots. | Require a readiness sequence/preparation generation, document its scope across session/reboot, persist the accepted watermark, and reject older reports. A new session must not let an old session's report pass. Test success→failure delivered failure→success and Player restart around the same plan. | Root added required `Readiness.sequence` during review. Ordering/sequence reset policy remains to be applied by coordination. |
| C03 — High | `TimeMapping` never ages an established uncertainty sample. A clock sample remains healthy after an arbitrarily long loss of synchronization because UTC and monotonic clocks may keep advancing consistently while both drift from real UTC. A one-year `ManualClock.advance` after `establish(.01)` returned healthy with `.01` uncertainty. | Establish the trusted uncertainty source and finite refresh/expiry policy. Invalidate new coordinated readiness when the measurement becomes stale or source reports unsynchronized; retaining currently visible content is separate. Test freshness expiry while UTC/monotonic difference remains zero and refresh with an unhealthy source. | Open at review; affects the accepted D09 readiness guarantee. |
| C04 — Medium | Clock health fails open for nonfinite clock samples, and configuration limits are not validated. After establishment, assigning NaN to a controllable wall clock made `healthy()` return true because comparison with NaN is false. Establishing an invalid anchor can similarly produce a nonfinite deadline. This defeats fault simulation and the finite-time contract. | Reject nonfinite or invalid bounds/anchors/current samples, negative/nonmonotonic elapsed time and nonfinite calculated deadlines. `ManualClock` should reject invalid initial state and overflow. Test NaN, infinity, overflow and backward monotonic observations. | Open at review; directly reproduced. |
| C05 — Medium | `Readiness.failures` sanitizes values but accepts arbitrary keys. A key containing a synthetic upstream URL and token was accepted and serialized. The supposedly frozen model's failure dictionary also permits unvalidated mutation after construction. This weakens the promised neutral, sanitized diagnostic boundary. | Restrict keys to assignment identifiers and explicitly defined scope identifiers; make the failure representation immutable or revalidate at every serialization boundary. Test rejection of URL/free-text keys and mutation resistance. The transport should not log the rejected raw payload. | Open at review; directly reproduced with synthetic text only. |
| C06 — High design clarification | Decision 0001 says a Program window's start is the activation identity. Taken literally, two Programs beginning at the same instant collide, suppressing one valid activation; changing a Program revision can also accidentally relaunch an already admitted occurrence unless revision adoption is defined. | Define the durable key as at least stable Program identity plus occurrence/window start, and define whether edits affect an already admitted occurrence. Test two same-time Programs on disjoint targets, duplicate reconciliation, and configuration edits across restart. | Open wording issue; reported before registry/persistence implementation. |
| C07 — Medium | Decision 0001 makes equal-priority admission order authoritative, but the initial Layer did not carry that order. Two Players could render tied layers differently by using incidental tuple/dictionary ordering. | Carry resolved ordering, or document an explicit centrally ordered layer list and require renderers to honor it. Test equal-priority layers serialized/reordered across Players. | Root added `Layer.admission_order` during review. Schema gap fixed; application of ordering still needs a test. |

These findings were reported promptly to the root before this record was written. C01/C02/C07 consumer checks are integration follow-ups to a concrete contract fix, not claims that an absent implementation has already failed.

## Additional schema issues to address before freeze

- `Variant` accepts `video/mp4` without a duration, while `Layer.position()` only maps into the current clip when a duration exists. A finite MP4 should have a validated positive duration or an explicit alternative timing policy before Player code depends on this method. Test a covered reveal beyond the first clip duration. Define whether looping is intended: the current helper always loops when a duration exists.
- `Readiness` accepts duplicate secured IDs, prepared IDs unrelated to secured media, and failure entries that contradict prepared status. Some validation needs the authoritative Plan (black presentation has no file to secure), so the coordinator must validate those relationships before locking/committing. Duplicate list membership can be rejected directly in the models. `Commit` also accepts duplicate assignment IDs.
- The model base is frozen and forbids extra fields but is not Pydantic-strict: boolean `revision=True` becomes integer `1`. If “strict versioned transport” means no coercion, use strict numeric/boolean types and test actual JSON payloads. Otherwise change the stated contract to describe intentional coercion. This is lower severity than authority freshness and does not require changing valid JSON arrays into tuple-only inputs.

## Calibration and trust boundaries to settle before registry storage

Calibration's current convexity/crop validation is useful and no bypass was found in this scoped review. The upcoming registry decision must define the relationship among calibration content revision, binding generation, desired configuration revision and temporary preview identity. In particular, previewing revision N+1 and reverting to content N must not be rejected as stale configuration or leave the preview active after disconnect/restart. Use a monotonic desired-state/plan revision around reversible content changes; require base-revision comparison for concurrent operator commits. Test preview→revert, preview→restart, concurrent commit and replacement while a preview is pending.

Decision 0001 correctly leaves D10 issuance/rotation/artifact trust pending and prohibits permanent shared image secrets. Registration with a freshly generated key is visibility, not authority to serve Frames. The registry must bind credentials to a stable Player identity and separate retirement from mutable MAC/IP/output observations. Media authorization must consult active authority, not only possession of a valid content hash.

Define the revocation boundary during network partitions: a disconnected retired Player cannot learn immediate revocation. Existing bounded authorization can expire locally; reconnect must reject the old credential/generation before accepting new work. The D10 record must avoid promising instant physical revocation on an unreachable device while permitting offline execution. Test old authenticated sessions, old cached plans and known media hashes after replacement, both before and after reconnect/lease expiry.

## Verification performed and disposition

Read the accepted decision and both implementation files. Executed small probes through the repository Python environment for stale clock samples, NaN clock health, unsafe failure keys, mutable nested failures, duplicate readiness/commit IDs, coerced boolean revisions, and video duration omission. Those probes establish contract acceptance behavior; they do not establish registry or Player behavior. Re-read the models during implementation and observed the C01/C02/C07 schema fixes.

Disposition: fix or explicitly resolve C03–C06 and the calibration/sequence/revocation policy boundaries before freezing dependent persistence and Player handling. Then add the identified consumer tests in the owning modules. Existing positive decisions—finite durable UTC times, separate monotonic mapping, snapshot projection, secured-before-commit pinning, explicit typed participants, and neutral hash-derived media paths—align with the canonical invariants.

## Orchestrator resolution after review

The implementation now includes observation revision, readiness sequence, explicit root/descendant ordering, clock-sample expiry/finiteness checks, immutable typed failure records, video duration validation, and Program ID plus start occurrence identity. Calibration contracts carry committed settings plus explicit preview expiry and a separate configuration revision. Registry checks binding generation on calibration and transfer. Focused regression tests cover these initial fixes; coordinator/executor consumption remains an unimplemented acceptance gate, not a resolved integration claim.
