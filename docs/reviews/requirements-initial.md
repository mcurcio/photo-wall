Date: 2026-09-05. Reviewer: independent requirements review agent.

Reviewed baseline: `ae44c77e5caaee288981a7a2c84d543e3a8cbe95`. This is a read-only review of the baseline requirements and design, not acceptance of implementation. At that revision the repository contains design documents and no runnable code or qualification evidence.

The active delivery objective additionally requires one review-ready PR, a built and boot-tested image, real Immich integration with blocked Player access, and physical PXE/rendering/coordination evidence.

## Review conclusion

The proposed central application/media worker and single-process Player boundaries match the requirements. Implementation can proceed after time, recovery, authority, and adoption contracts are recorded. Portable execution can make independent progress immediately. Full acceptance cannot be established from portable tests alone: a real Immich environment, supported physical Pi devices, panels, deployment network, and actual image artifact are distinct gates. If these remain unavailable, the deliverable must remain a draft PR with exact blockers.

The scope is one Installation, two Outputs on one Pi and a second Player, narrow declared-version Immich integration, nested Scenes, a recording Actuator, bounded media preparation, central operations, appliance provisioning, and scoped update recovery. Advanced authoring, broad integrations, HDR/audio, and tight synchronization can remain deferred. Deferral does not waive the single-process native renderer, calibration workflow, basic visible coordination, or physical qualification.

## Decisions required before implementation contracts harden

| Priority / register | Decision to record | Required invariant and acceptance probe |
|---|---|---|
| Blocking — D03/D09 | Logical Run time, calendar scheduling, local monotonic time, media position, acceleration and reboot mapping. Record a single domain clock contract and a policy for wall-clock steps/uncertainty. | Never persist a process-local monotonic timestamp as a reboot-stable deadline. Covered progress derives from logical time rather than paused pipeline time. Reboot, forward/backward clock changes, and acceleration must converge to the current assignment without replaying missed cues. |
| Blocking — D03/D07 | Exact local behavior on central outage, media outage, beyond-horizon operation, Player restart and reconnect; only then storage retention and sizing. | Losing central alone does not imply blanket black. Last valid still/configured fallback survives recoverable failures; expired overlay does not remain forever. Rejoin accepts current authority rather than replaying command history. State the supported offline duration and behavior after it, separately from the approximately five-minute lookahead. |
| Blocking — D02/D03 | Assignment states and atomicity around scheduled+secured lock, commitment, release and execution reports. | Content locks when scheduled and secured, including before formal commit; crash/retry cannot reroll it. Readiness receipt, byte integrity, preroll, capacity, authorization and visible output are separate facts. Record which records share one transaction and which remote facts need reconciliation. |
| Blocking — D10 | PXE deployment trust, common artifact identity, discovery, automatic individual credential establishment, rotation, revocation and retirement. | Image contains no permanent shared fleet credential. Registration precedes binding. Initial visibility needs no device-local action. Device identity is distinct from MAC/IP/display observations. | Before registry schema — D04/D12 | Typed participants, group/descendant definition adoption, Surface coordinates, physical aperture, equipment correction and calibration preview lifetime. | Persistent Frame IDs and authored roles survive replacement. Millimeters and output pixels cannot be conflated. Parent target union does not imply current contribution. Preview does not overwrite committed state; revert and replacement revalidation are explicit. |
| Before Runtime schema — D05 | Priority, force, ties, protection, overlap, repeat activation, child lifecycle, Program end and outgoing/incoming background composition. | Manual is not implicitly force. Default repeat is ignore. Natural completion finishes current activity and children; cancellation only descends. January can advance beneath the independent overlay while December finishes according to an explicit policy. |
| Before media planning — D06/D07 | Pinned Immich version, exact query subset and permission scope; original/variant eligibility; fallback; central conversion and cache policies. | Empty results differ from upstream failure. Original orientation/quality is checked before preferences and variant choice; larger derivatives do not rescue an insufficient original. Query result changes may affect unlocked future work in the same Run; authored query edits wait for adopted revision policy. |
| Before production claims — D01/D08/D11 | Launch/database/migration tooling, hardware/software support envelope, minimum UI, native rendering path and whole-Player capacity policy. | PostgreSQL centrally and SQLite locally are architecture starting choices, not substitutes for time/recovery decisions. A simulated renderer cannot qualify GTK/GStreamer, two-output resource sharing, continuity or output timing. |

Recommended time policy for the first slice: use UTC instants for durable starts/deadlines, a separately configured Installation timezone for calendars, and an injectable clock yielding both UTC and monotonic observations. A live process anchors a synchronized UTC reading to local monotonic time; restart takes a new anchor. Persist adopted starts, lifecycle and exact locked assignments, then reconcile intended current state. Record explicit late-command and clock-discontinuity behavior before treating this recommendation as accepted. An accelerated demo needs one coherent time mapping across scheduler and executors, not a scheduler-only speed multiplier.

Recommended offline policy for the first slice: execute only already-authorized, unexpired local work; use current logical position when a covering assignment ends; retain a compatible last valid still beyond available authorized playback, otherwise use configured local fallback. Never select new upstream assets or resolve global Scene priority locally. Persist enough state for this policy and document whether an elapsed authorization ends in hold-still or configured fallback. Central reconnect supersedes offline work with a current-state snapshot validated against binding authority.

## Proposed bounded module contracts

These are review recommendations for the orchestrator to reconcile with the accepted contract; they are not alternate wire schemas.

| Owner | Inputs / outputs | Owned state and dependencies | Failure obligation |
|---|---|---|---|
| Domain clock | `now`, calendar conversion and monotonic anchor; controllable test implementation | Time meanings and conversion helpers only; no transport/rendering | Report discontinuity/uncertainty and let policy reject unsafe coordinated work. |
| Runtime | Adopted definitions + activation/events/outcomes + clock → current Run tree and typed target contributions | Run lifecycle, adopted references, logical progression, current ownership; depends on registry/definition snapshots, not Immich or GStreamer | Cancellation descends; completion waits for active work/children. Significant execution failures return here and cannot be swallowed by Planner. |
| Projection | Immutable Runtime snapshot + future instant → projected intent | No mutable live state, no external effects, no persistence writer | Projection across midnight cannot finish current Runs, launch live children or issue Actuator cues. Test snapshot equality and an empty effect sink after projection. |
| Catalog/Planner | Projected target intent + bounded catalog snapshots + compatibility profiles + existing locked assignments → revisable exact-variant assignments | Hard eligibility and selection policy have one owner; live data independent of adopted query definition | Before lock, failed acquisition may choose eligible dynamic replacement or authored alternative/fallback; after lock, preserve exact content and apply execution failure policy. |
| Coordination | Proposed assignments + per-participant readiness + authoritative bindings + time → authorization/cancel/current-state snapshot | Epoch/revision validity, secured lock, per-participant state, deadlines, required/optional policy | Stale/duplicate/reordered replies cannot authorize old content/bindings. File-ready is insufficient for playback commit. Missing required participant behavior is explicit. |
| Player executor | Upstream-neutral local plan + cache/renderer/resource observations + time → prepare/present/fallback/report | One process; accepted authority/configuration, local schedule, cache pins, current intent | Verify generation, epoch/revision and validity at action time. Late/rejoin work seeks current state; never repeats stale cues or silently rerolls assignments. |
| Renderer/cache adapters | Exact bytes, local layers, calibration and intended media positions → integrity/readiness/observed output | Renderer owns composition/calibration and persistent GTK surfaces; cache owns exact bytes, hashes and pins | Retain prior valid picture/fallback through recoverable prepare/decode failure. Byte acquisition, preroll and aggregate decoder capacity remain independently reportable. |
| Recording Actuator | Currently authorized resolved contribution at intended time → observation | Adapter records/applies target state, never priority or Scene policy | Omitted target means no command. Covered cues are not replayed; current state is applied on handback. |

Shared contract ownership should remain with one orchestrator/module. Child agents should not independently invent target IDs, time units, fallback enums, content-lock semantics, or authentication generations. Every implementation handoff needs disjoint paths and named tests for the boundary it owns.

Tests should fail on observable invariant violations rather than duplicate implementation formulas. Good adversarial probes include same checksum under a new plan revision after lock, retired binding with a still-valid session, projection that touches child state, calendar shift while background is covered, partial readiness loss after initial cache acknowledgment, and cache pressure between secure acknowledgment and commit.

## Infrastructure and owner decisions to request early

1. A reachable real Immich deployment (or permission/resources to start the declared free self-hosted version) with a synthetic fixture account, restricted API credential supplied outside Git, and a network route that permits central access while denying Player access.
2. A Linux image-build environment with enough disk for the image/toolchain, artifact storage outside Git, and a supported way to boot the exact generated Pi artifact. Record whether any available virtualization is only partial qualification; an emulator is not PXE/two-HDMI proof.
3. Two supported Pi 5 devices; two representative panels on the first and an output on the second; power/network/storage/cooling; controllable DHCP/TFTP/HTTP or equivalent Pi network-boot infrastructure, time/discovery services, and enrollment trust configuration. A camera or suitable sensor is needed for visible continuity/timing evidence.
4. Authorization/access to the provisioning network and physical bench, including the centrally prepared trust material. Public trust anchors and common configuration are distinct from private deployment signing/enrollment keys. Keep actual credentials and private media out of evidence.
5. Repository-owner choice of code license and security-reporting route before a first code release, as required by the existing [decision register](../design-decisions.md#open-source-release-preparation). Do not invent a reporting contact or impose a project license. Dependency license inventory may proceed independently.

These requests do not block domain implementation, pure tests, central packaging, synthetic fixtures, operator UI, image recipes, qualification scripts or independent review. They do block the corresponding acceptance evidence; tooling that has not executed must remain labeled unverified.

## Material risks for the final review

- **Critical: evidence substitution.** A simulated renderer, fake catalog, generated manifest or green unit suite can coexist with a nonbootable image, unusable GTK sink or broken PXE. Keep simulated, integration and physical records separate and link every acceptance claim to the appropriate executed procedure.
- **High: incomplete content-lock transition.** Locking only on final commit violates scheduled-and-secured semantics and makes precommit cache pressure/restart unsafe.
- **High: hidden-time drift.** A Player using paused pipeline position or a frozen overlay-underlay snapshot reveals stale content even when scheduler tests pass.
- **High: stale replacement authority.** Deleting a binding without generation/credential checks at execution and media delivery can allow a replaced device to act using cached messages.
- **High: untrusted bootstrap shortcut.** A common permanent enrollment secret, redirect to upstream media, or local endpoint entry can produce an apparently working demo while violating explicit requirements.
- **High: continuity claims without decode behavior.** Keeping a GTK window alive does not retain a valid picture if pipeline replacement clears it before the new media is prepared.
- **High: architectural time coupling.** Schema fields designed before reboot/clock policy may make recovery fundamentally ambiguous; test restarts at preparation/lock/commit boundaries before other modules depend on persistence.
- **Medium: bounded horizon only in name.** A five-minute timestamp limit does not bound catalog fetch size, oversized files, worker concurrency, cache pins or decoder preparation. Give each a separate limit and demonstrate pressure behavior.
- **Medium: unrelated scope taking priority.** Rich UI/authoring and extra integrations cannot compensate for an absent media worker, real renderer, appliance artifact or physical acceptance gate.

Review disposition: proceed with design decisions and implementation; acceptance unproven. A follow-up correctness review must inspect the integrated implementation and final evidence, not merely close this document's checklist.
